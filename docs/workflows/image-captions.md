# Alt и hover изображений

Дата: 09.10.2026. Канонический реестр: `src/data/media/image-captions.json`.

## Что описываем

Alt: **объект или сцена + место + страна**, когда все эти сведения есть в источнике конкретного изображения. Для простого кадра достаточно названия объекта. Целевой объем: примерно 50–160 знаков, без жесткого обрезания. Начинать с предмета изображения; убрать «на фото», номер дня, название коммерческой программы и рекламные эпитеты. Ключевые слова добавлять только там, где они естественно называют предмет.

Hover хранится отдельно в поле `hover`. Передает ту же сцену, допускает другую конструкцию и порядок слов. Новых объектов или действий в нем нет. Шаблонное начало «В кадре:» автоматически не добавляется. Использовать естественную переформулировку: «Водопады Игуасу в Бразилии» → «Бразилия: водопады Игуасу». Если естественная переформулировка не получается, одинаковый текст лучше натянутого синонима.

Для разных исходников с одинаковым описанием выбирать разные безопасные конструкции из имеющихся сведений: «Водопады Игуасу в Бразилии», «Водопады Игуасу, Бразилия», «Бразилия: водопады Игуасу». Сохранять один вариант для всех использований одного файла и записанных его улучшений с прежней сценой. Новая альтернативная генерация получает собственную идентичность. Когда естественных вариантов меньше, чем исходников, отдельные повторы остаются. Номер фото и придуманные отличия не добавляются ради уникальности.

Переформулировка не подтверждает различия сцен. Одинаковые подписи допустимы, если текстовые источники не содержат различий. Не добавлять фото в очередь Work только из-за повторяющегося alt или hover и не требовать просмотра ради уникальности текста. `sourceDescription` сохраняет исходное текстовое описание, `captionIdentity` указывает записанный исходник, `wordingChanged` фиксирует редактуру. `sharedDescriptionIdentities` и счетчик групп повторов служат справочной информацией и не блокируют использование подписей. Уточнять отдельный кадр по подписи источника, привязке конкретного изображения в Word или журналу генерации, когда они содержат дополнительные сведения.

| Известная сцена | Alt | Hover |
|---|---|---|
| Копакабана: пляж и мозаичная набережная; источник конкретной генерации в журнале фото дней | Пляж и мозаичная набережная Копакабаны, Рио-де-Жанейро, Бразилия | Копакабана в Рио-де-Жанейро: пляж и мозаичная набережная |
| Фуэрте-де-Самайпата; подпись источника места | Фуэрте-де-Самайпата в Боливии | Боливия: Фуэрте-де-Самайпата |

Название тура или текст дня сами по себе не доказывают, что изображены все перечисленные достопримечательности. Группу изображений галереи нельзя описывать одним маршрутом, выдавая его за содержание каждого кадра. Исходная база построена без открытия изображений. Каждое отдельное поручение пользователя задаёт фиксированный список просмотра. Первые 155 `imageId` и результат закреплены в `data/media/image-caption-visual-review-155.json`; следующий явно заказанный пакет из 150 — в `data/media/image-caption-visual-review-next-150.json`. Совпадение подписей не расширяет эти списки. Уже просмотренные файлы пропускаются без подбора замен.

## Устройство базы

Одна запись на точный логический путь изображения или закрепленный внешний URL. `/media/...` и `https://img.adatours.ru/media/...` обозначают один путь. Остальные внешние URL сохраняются точно, включая параметры. Совпадение названий файла не объединяет разные URL; визуальная похожесть и SHA из отсутствующего источника не выдумываются.

В записи: `id`, `src`, `alt`, `hover`, `status`, `basis`, `evidence` (точная ссылка и цитата), `alternatives`, `sourceImages`, `generationRefs`, счетчики использований и `visuallyReviewed`. Проверка только текста всегда дает `false`. Явно просмотренный кадр получает `true` только через override с доказательством по точному URL этого изображения; синхронизация сохраняет отметку, но не переносит ее на исходник или соседние файлы. Имеющийся SHA-256 берется только из подтвержденного S3 receipt.

`data/media/image-caption-usages.json` содержит каждое использование в production MD и статические ссылки из шаблонов: ID сущности, путь, слот, контекст, прежний alt, источник материала и архивный статус. Статическая ссылка шаблона учитывает запись в коде, а не число страниц, построенных этим шаблоном. Динамические excursionRef используют фото канонической экскурсии; ее изображения уже учтены у владельца. Динамические флаги телефонного поля относятся к интерфейсным элементам, а не к туристическим фото.

`data/media/image-caption-review-queue.json` содержит отдельную очередь для явно порученного Work-чату просмотра: только активные использования со статусами `text_conflict`, `context_only`, `missing_description`. У каждой задачи точный файл, все активные слоты и текстовые источники. Одинаковые подписи сами по себе не создают задачу. Архивные и неиспользуемые файлы в эту очередь не входят. По уточнению пользователя просмотр этих изображений выполняется отдельной задачей, текущий проход их не открывает.

Улучшенный файл хранит ссылку на исходник. Подпись исходника может перейти к улучшению при сохранении сцены; текст новой альтернативной генерации не переносится назад на старый оригинал. Один файл при повторном использовании сохраняет предмет описания. Окружающий текст тура не переименовывает изображенный объект.

## Статусы

| Статус | Значение | Следующее действие |
|---|---|---|
| `source_described` | В текстовой записи конкретного кадра есть описание | Можно использовать как подпись по источнику; содержание изображения визуально не подтверждено |
| `editorial_source_described` | Редактор составил подпись по указанному текстовому доказательству | Использовать закрепленные alt/hover |
| `visually_reviewed` | Кадр открыт по точному URL; alt/hover описывают видимое с подтвержденной географией | Использовать подписи; `basis: visual_review`, `visuallyReviewed: true` сохраняются при повторной синхронизации |
| `text_conflict` | Текстовые источники дают разные описания одного файла | Сверить первоисточники, сохранить решение с доказательством; предложенный alt остается черновиком |
| `context_only` | Есть только контекст страницы | Общая подпись «Иллюстрация: …» остается черновиком, требуется описание конкретного кадра |
| `missing_description` | Описания кадра нет либо несколько контекстов не позволяют его выбрать | Дополнить текстовые источники; пустое поле не означает, что фото декоративное |

Приоритет автоматического сбора: редакторская запись с доказательством → подпись из журнала конкретной генерации → подпись production-слота владельца → подписи других использований → подпись изображения в source-index. Разные формулировки одного ранга сравниваются консервативно; спорные строки не считаются готовыми. Старые подписи могут быть ошибочными, поэтому даже статус `source_described` не равен подтверждению реальной сцены. Английский промпт сохраняется как доказательство, без копирования технических требований генерации в русский alt.

Архивные изображения и неиспользуемые исходники входят в опись с отдельными счетчиками. Создание подписей не восстанавливает архивные страницы и не запускает их публикацию. Старые версии и служебные изображения без источника могут оставаться без предлагаемого alt; для них требуется текстовое уточнение, если файл снова используется как содержательное фото.

## Новое изображение

1. Зафиксировать точный файл, владельца и первоисточник: исходная подпись, текстовая привязка объекта в Word, предоставленное описание или промпт конкретной генерации. Для Word нужна привязка **конкретного встроенного изображения**, а не только имя документа.
2. Сразу записать короткое русское описание сцены. В GPT Image использовать содержание принятого промпта; указанные пожелания остаются текстовым основанием и не превращаются в визуальную проверку. Если кадр создан по нескольким материалам, перечислить ссылки на них. Цвет, погоду, людей, ракурс и действия добавлять только по имеющемуся тексту сцены.
3. У нового файла записать `alt` в production mediaObject. Редакторские alt/hover сохранить в `src/data/media/image-caption-overrides.json`, массив `images`: `src`, `alt`, `hover`, непустой `evidence: [{ref, quote}]`. При повторном подключении файла переиспользовать его закрепленное описание.
4. Для новой сцены или версии файла использовать новый путь и отдельную запись. При смене только `src` старая подпись автоматически не считается подходящей: проверить ее по первоисточнику новой сцены.
5. После изменения MD, source-index или фото-журналов один раз выполнить `node scripts/sync-image-captions.mjs --apply`. Включить реестр, таблицу использований и очередь просмотра в тот же commit. Проверка полноты: `node scripts/sync-image-captions.mjs` (без `--apply` возвращает ненулевой код для устаревшей базы).

Пример редакторской записи:

```json
{
  "src": "/media/example/new-version.webp",
  "alt": "Пляж и мозаичная набережная Копакабаны, Рио-де-Жанейро, Бразилия",
  "hover": "Копакабана в Рио-де-Жанейро: пляж и мозаичная набережная",
  "evidence": [{
    "ref": "data/media/example.json#completedAssets[0].prompt",
    "quote": "Copacabana beach and Avenida Atlantica promenade, Rio de Janeiro"
  }]
}
```

Пути примера условные. В рабочей записи использовать существующий источник и дословную выдержку.

## Применение на страницах

Для записей, просмотренных в явно заказанных пакетах, production mediaObject получает alt и hover во всех текущих использованиях файла. `src/lib/image-captions.mjs` ищет редакторский override по `src` также для строковых путей и повторных использований; URL нашего CDN и логический путь обозначают один файл. Галереи, фото дней, экскурсионные вставки, highlights и фото команды выводят hover через `title`. Контекстные черновики реестра автоматически не подключаются. `caption` остается видимой подписью и не заменяется hover. Декоративные Hero, фоны полос и служебные изображения сохраняют прежнюю роль и пустой alt без title.

Визуальный override содержит `visuallyReviewed: true` и `evidence: [{ref: <точный URL открытого фото>, quote: <фактическое описание видимого>}]`; текстовые источники и их дословные цитаты можно дополнять отдельно. Недоступный файл остается без override и без отметки просмотра, с `blocker` в закрепленной описи и очереди. Исходные 155 ID не расширяются из-за новых объектов, добавленных другими задачами.

HTML `alt` определяется еще и ролью изображения в конкретном месте. Содержательное фото получает описание; чистый декоративный фон, дубль изображения рядом с достаточным текстом, служебный флаг могут иметь `alt=""`. Это отдельное решение использования, а не отсутствие описания файла в базе. Для декоративного изображения W3C рекомендует пустой alt и отсутствие title. Источники: https://www.w3.org/WAI/tutorials/images/ и https://www.w3.org/WAI/tutorials/images/decorative/.

Hover при подключении можно вывести через HTML `title` на содержательном изображении. Он дополняет alt, не заменяет его. Важная информация о маршруте остается видимым текстом страницы. CSS background не поддерживает alt; его роль и доступное описание решаются на уровне компонента. Существующие скрытые `aria-hidden` изображения не становятся содержательными автоматически.
