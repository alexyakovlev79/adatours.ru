## Как работает каждый чат

1. Открывает **свой** `docs/plans/english-site/stage6/6-N.md` в ветке `i18n/stage6-nine-way`. Работает исключительно в ветке `i18n/stage6-6-N`, которая уже создана от общего фиксированного SHA.
2. Через GitHub скачивает ровно artifact #14018947340, извлекает `stage6-media-audit.json`. При наличии Node 24 запускает `node scripts/i18n/stage6-shard.mjs status 6.N /путь/stage6-media-audit.json` и `node scripts/i18n/stage6-shard.mjs list 6.N /путь/stage6-media-audit.json 25`. SHA-256 проверяется автоматически. Повторяет `list` после сохранения каждой партии, пока `remaining=0` либо не останутся явно оформленные REVIEW.
3. Переводит **весь отображаемый русский alt по конкретному медиа src**, беря только `ruAlts` и `ruTitles` из frozen аудита. Записывает в единственный свой `src/data/i18n/stage6-shards/6-N.en.json` элементы вида `{ "source":"stage6-shard-6.N", "sourceKey":"/media/...", "sourceAlt":"точный RU alt", "alt":"English description" }`. Если `title` по смыслу отличается, добавляет самостоятельный точный EN `title`. Не угадывает факты по имени файла и не придумывает новый сюжет.
4. Сохраняет по 10–25 описаний за коммит **только в собственной ветке**; `GitHub.update_file` — с ожидаемым blob SHA, без force. В случае сбоя перечитывает текущий собственный файл; готовые ключи повторно не переводит. Пишет `review[src]=причина` в том же файле для реальных неоднозначностей, не выдает REVIEW за готовые переводы.
5. Проверяет `node scripts/i18n/stage6-shard.mjs verify 6.N /путь/stage6-media-audit.json` и `node --test tests/i18n/media-stage6-parallel.test.mjs`, затем сообщает свою ветку, SHA, количество записей, остаток и REVIEW. Создать **не более одного** PR своей ветки в `i18n/stage6-nine-way` (если права позволяют); при отсутствии доступа достаточно ветки и точного SHA.

**Запрещено работникам:** менять общий `media-captions.en.json`, `src/lib/i18n/media-copy.mjs`, другие shard-файлы и инструкции, `main`, RU, цены, исходные изображения/файлы, `i18n/translation-mass-staging`, массовые FULLTEXT/Tour и SEO/GEO-очереди; запускать дорогой платный API-перевод, деплой, включать индексирование. Диспетчерская идентичность — закреплённая ветка и уникальный путь, а не общая арендная очередь.

## Интеграция после девяти чатов — отдельный мастер

На `i18n/stage6-nine-way` адресно объединить девять PR/веток по разным JSON-файлам без перезаписи общего словаря. Код `src/lib/i18n/media-copy.mjs` уже подключает все девять, а общий unit-test не допускает двух переводов одного src или чужой ветки. Один раз выполнить `verify` для всех девяти, проверить отсутствие REVIEW/остатков, затем подготовить **один PR в main**. Успешный preflight и отдельный EN Pages deploy с конкретным SHA подтверждают применение. После этого новый read-only `stage6-media-audit.json` определяет остаток — нельзя объявлять завершение по числу commit или числу записей.

Новый src из будущего EN-аудита назначается тем же алгоритмом, но не добавляется задним числом в замороженный набор 701 без отдельного прохода; старые ключи и история сохраняются. `noindex`/`PUBLIC_EN_RELEASE=0` остаются.
