# Schema.org / GEO — отдельная очередь данных (16.10.2026)

Команды **«собирай данные»** и **«публикуй данные»** относятся к `docs/workflows/schema-geo-knowledge.md` (v2), а не к написанию SEO-статей. Код CAS: `scripts/schema-geo-core.mjs` и `scripts/schema-geo-remote.mjs`. Источник статусов/резервов — **только** `schema-geo/staging`, `data/geo-knowledge/queue.json` + `state.json`; Google Sheets «GEO очередь/результаты/публикации» — зеркало. Сборщик берет одну пачку до 10 задач (лимит `manifest.batchSize`), срок 90 минут, сохраняет результат и закрывает только свой токен одним CAS-коммитом, main/build/deploy не трогает. Реально опубликованным результат становится после успешного Pages deploy: независимый `geo-finalize.yml` подтверждает исходный SHA или проверенного потомка с неизмененными GEO entities/receipt, даже если мастер-чат закрыт; неуспешный deploy не дает `PUBLISHED`. Существующие внешние identity/EN-реестры и единый JSON-LD renderer сохраняются. Старт с 24 стран; следующие этапы открывает мастер после пилота по manifest.maxStage. Готовый код запуска через подключенный GitHub и все процедуры — в workflow.

**GEO-решения с 16.10.2026:** для самого объекта страницы, внешнего QID / `sameAs`, координат и остальных полей сборщик сначала уточняет данные через интернет, затем принимает наиболее вероятное соответствие при оценке **от 70% включительно**. При меньшей вероятности конкретное поле пропускает; паспорт становится `READY`, если идентичность самой страницы набирает от 70%. Новые результаты используют `decisionPolicy: probability-70-v1` и служебные `assessments` с доказательствами. Для составных мест определять основной референт и допускать его QID/`sameAs` по тому же порогу. Режим и требования зафиксированы в §3.2.1 `docs/workflows/schema-geo-knowledge.md`. Старые REVIEW не изменять без повторного исследования и нового result.


**GEO-мастер (16.10.2026): ВСЕ `READY` одним релизом, лимит 20 удален.** По команде «публикуй данные» выполнить один короткий Code Mode вызов по §4.1 `docs/workflows/schema-geo-knowledge.md`: `scripts/schema-geo-publisher.mjs` только захватывает все `READY` и пишет `data/geo-knowledge/dispatch.json` вместе с блокировкой CAS. **Не загружать каждый результат через чат**: ограничение количества GitHub-вызовов делает такой способ ненадежным. Массовые файлы локально обрабатывает `.github/workflows/geo-publish.yml` / `scripts/schema-geo-ci-publisher.mjs`, формируя один main-коммит и затем явно вызывая существующий Pages `workflow_dispatch` (push от `github.token` сам не запускает deploy). `.github/workflows/geo-finalize.yml` закрывает `DEPLOYING` после полного успешного Pages run с exact receipt/SHA. Прежний `PUBLISHING` продолжать по его batchId/ownerId через `dispatchPublication`, не резервировать повторно. Не ждать Pages в чате, не запускать местный build/дублирующие тесты, не делать вторых деплоев ради синхронизации Google Sheets. Количество собираемых за раз заданий до 10 остается только у исследователей.


# Ada Tours: рабочий вход

**SEO/GEO для multi-country × интерес (16.10.2026).** Если выбран URL `/multi-country/<страны>/interests/<интерес>/` или `/multi-country/interests/<интерес>/`, обязательна предметная методика `docs/workflows/seo-geo-registry.md`, §9.5.1: полезная статья о конкретных странах **через призму одного интереса**. Разобрать реальные тематические занятия по маршруту, сезонность, межстрановые ограничения и выбор действующего тура; не склеивать типовые тексты и не предполагать, что интерес представлен в каждой стране. Очередь, права staging-писателей и отдельная публикация SEO-мастером сохраняются.

**SEO/GEO v3.5 — быстрый старт «пиши SEO».** Один вызов `functions.exec` запускает `docs/workflows/seo-geo-fast-claim.md` v1.4: до 5 URL, каждый резерв на 90 минут с продлением. Фазы 01–04 (277 опубликованных URL) пропускаются при неизменных подтвержденных blob SHA, но перечитываются при изменении. Выбор 05 → 06 → 07: при нехватке свободных URL в предыдущем этапе сразу добирать из следующего, не ждать чужих резервов. При каждом новом запуске начинать с ранних свободных `draft` (истекшие claims), затем `queued`. **Резерв выполняется одной атомарной записью только `claims.json` через `GitHub.update_file` с ожидаемым SHA файла; не переписывать мегабайтный `05-tours.json` и не собирать отдельный Git tree при захвате.** `queued` с собственным действующим claim уже означает «Пишется»; в фазовом реестре статус меняется на `prepared` только вместе с готовой статьей и снятием своего claim одним CAS content-коммитом. Старые чаты с `draft` на резерве сохраняют совместимость. Не трогать чужие действующие claims, при конкуренции по файлу максимум два повтора. После `reserved` сразу писать первую статью; `main`, Sheets, Actions и чужие тексты перед захватом не читать. SEO-мастер публикует отдельно.

**SEO/GEO — один commit на готовую статью.** После подготовки утвержденного MD одновременно записать саму статью, `work: prepared` и снять только собственный claim в одном CAS-коммите `seo-geo/staging`. Переход в `prepared` не требует отдельного preflight, двух Git-коммитов, proof-SHA, ожидания Actions или запуска сборки. Ссылки, архив и корректность HTML проверяет единственная штатная сборка мастер-чата при `публикуй SEO`; автор проверяет конкретные ссылки по текущим каноническим данным во время написания. Google Sheets — зеркало, и ее недоступность не задерживает начало/продолжение статей. Чужие активные резервы (90 минут после продления) сохранять, CAS-конфликты обрабатывать максимум двумя адресными повторами, без force push. Только мастер публикует в `main`. Детали: `docs/workflows/seo-geo-registry.md`, раздел 8.

**SEO/GEO: фильтр перед публикацией (16.10.2026).** При `публикуй SEO` мастер проверяет только уже загруженные `prepared` MD: статус, canonical URL/путь и начальный H2. Ошибочные URL остаются в staging, остальные входят в один main-commit. При Work/shell доступен одноразовый пакетный `src/lib/seo-geo-release-gate.mjs` и `scripts/check-seo-geo-release.mjs`, который дополнительно проверяет FAQ; при Code Mode — готовый in-memory JS из `docs/workflows/seo-geo-registry.md` §8.3. Новых GitHub-запросов, Actions, отдельных preflight/build и сканирования старых статей нет. Писатель проверяет H2 на своем готовом тексте перед staging-коммитом, без инструмента.

**Дополнение к написанию SEO/GEO-статей:** в новых текстах и явно заказанной редактуре проектировать обычные таблицы под ~300–340 CSS px мобильной ширины (как правило, 2 компактные колонки, не 3 длинных текстовых); подробности выносить за таблицу. Расставлять **контекстные внутренние ссылки прямо при содержательных упоминаниях** опубликованных мест, экскурсий, туров и подходящих каталогов «страна + интерес»; **в перечислениях давать ссылку на каждый доступный объект**. Нет лимита «одна ссылка на URL» или «1–3 ссылки на раздел»: полезные повторные переходы разрешены; избегать только бессмысленных дублей рядом и ссылок на архив, резерв, пустую подборку или себя. Полные критерии и примеры — раздел 12 `docs/workflows/seo-geo-registry.md`. Старые статьи без отдельного заказа не переписывать.

**FAQ в новых SEO/GEO-статьях:** если FAQ нужен, оформлять только `## Частые вопросы…` (H2) → `### Вопрос?` (H3 для каждого вопроса) → обычный абзац(ы) ответа. **Никогда не записывать в Git новые или изменённые бинарные файлы** из `public/media/` — WebP, JPEG, PNG, MP4, WebM и прочие. Все старые файлы в Git и историю коммитов сохранить, не удалять. GitHub Pages продолжает принимать только HTML/CSS/JS/SEO; медиа отдаются по `https://img.adatours.ru/media/...`.

ChatGPT Work при любой новой генерации/улучшении изображения или видеоролика использует `docs/workflows/direct-s3-upload.md`: локальный файл вне Git → одноразовый X25519 сеанс → зашифрованный временный OIDC IAM-допуск → прямой S3-upload → проверка SHA-256 → текстовый receipt в `src/data/media/direct-s3-uploads.json` → commit MD/JSON/реестров без бинарного файла. `hero.src` и прочие поля содержат прежний логический путь `/media/...`. Новым файлам всегда новое версионированное имя, S3-объекты не перезаписывать. GitHub Actions проверяет ledger и наличие файла до публикации.

Если прямой upload из конкретного чата недоступен, **сохранить задание и назвать блокер; не возвращаться к Git binary fallback, не связывать неподтвержденный S3 путь и не утверждать, что фото опубликовано**. GPT Image и финальные WebP требуют Work с локальным файлом и сетевым доступом, у GitHub connector нет команды прямой передачи бинарного файла в Object Storage.

Для выборочных видеофонов отдельного Country/Tour hero предусмотрена загрузка MP4/WebM точно так же, но проигрывание включается только в отдельной задаче. Оригинальный WebP-постер остается обязательным для LCP, SEO, мобильных устройств и `prefers-reduced-motion`. Подробнее: `docs/MEDIA_DELIVERY.md`.



## Multi-country + интерес — поддержка структуры с 16.10.2026

Перед работой с этой структурой использовать `docs/workflows/multi-country-interests.md`. Статические сочетания 2–4 основных стран + один действующий интерес строятся общим `multi-country-catalog.mjs` по активным турам. Сайт и публичные CSV пересчитываются в каждом build; после успешного deploy метаданные автоматически отражаются в main и `seo-geo/staging` без переноса статей/claims. Полная SEO/GEO-очередь включает тематические пересечения сразу после обычных multi-country. Ключ — canonical URL/ID, номер order изменяемый. Авторы/мастер пропускают `temporarily_unavailable`; история сохраняется и возвращается при восстановлении каталога. После изменения состава обычная адресная сверка таблиц сохраняет поля менеджеров, даты и редакционные статусы. Новые каталоги — производные, без source-index сущностей, выдуманных внешних пар и новых media-генераций.
