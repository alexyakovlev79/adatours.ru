# ADA TOURS — MASTER BLUEPRINT САЙТА

Версия: 1.8

Дата: 02.10.2026

Статус: действующий архитектурный и операционный контракт проекта

Заменяет: `ADA_TOURS_SITE_MASTER_BLUEPRINT_v1.7.md` и более ранние редакции.

Для стандартного добавления достаточно выбранного специализированного workflow и exact entry. Master не перечитывается целиком перед каждой сущностью: его архитектурные и дизайн-разделы используются как справочник по конкретному вопросу.

## Что изменено

- Обычное наполнение отделено от разработки шаблонов, подготовки источников, рерайта, миграции связей и обработки фотографий.
- Для каждой сущности используются заранее закрепленные входные данные. Добавляющий чат читает точную запись индекса и точные файлы; повторный поиск источников не входит в задачу.
- Тур получает все относящиеся к маршруту канонические Destination ID, включая еще не опубликованные места. Создавать страницы мест при добавлении тура не требуется.
- Ссылки и карточки места активируются при публикации соответствующего Destination. Повторно редактировать туры для этого не требуется.
- Недостающая самостоятельная Excursion, выявленная в добавляемом туре, создается в том же проходе; тур получает ее `excursionRef`.
- На этапе наполнения используются только закрепленные прямые raw URL фотографий `brasiltours.ru/image/...`. Фотографии не скачиваются и не обрабатываются.
- Чатам не назначаются визуальные проверки страниц, desktop/mobile, скриншотов, компоновки или результатов генерации. Визуальные решения и замечания дает пользователь.
- Приемка наполнения состоит из узкой машинной проверки измененных данных и результата сборки. Общий аудит сайта и старых туров не входит в добавление сущности.
- Один подготовленный набор изменений публикуется одним commit. Результат привязан к commit задачи, а не к постоянно меняющемуся последнему `main`.

## 0. Приоритеты и область применения

1. Прямое актуальное указание пользователя.
2. Этот Master — архитектура, границы задач, источники и общие правила работы.
3. Специализированный workflow выбранного типа операции — точный порядок действий в этих границах.
4. Текущая схема и общие компоненты репозитория — фактический формат данных и действующее отображение.
5. White Garnet reference — принятая визуальная система, применяемая при отдельно заказанной разработке дизайна.

Старые инструкции, примеры, handoff и комментарии не возвращают отмененные операции. Обязательного чтения всех файлов проекта перед одной сущностью нет. Правила выбранного режима полностью определяются действующими документами из раздела 2.

В обычной задаче наполнения не пересматриваются архитектура, дизайн, URL, механизм связей, схема Content Collections, общий CSS или компоненты. Дефект общих компонентов фиксируется отдельно; он не превращает добавление одной сущности в незапрошенную переработку сайта.

### 2.1. Повторное использование прочитанного

Прочитать нужную запись индекса и файлы один раз в рабочем цикле. Если точный файл уже получен в текущей среде и его версия не изменилась, использовать локальную копию. Не скачивать те же данные повторно ради другого этапа той же операции.

При возобновлении сначала использовать сохраненный ключ задачи, пути, commit и курсор. Обновить только ту запись или файл, состояние которых действительно могло измениться. Не сверять весь реестр с `main` перед продолжением одной строки.

### 2.2. Если точных входных данных нет

Отсутствующий file ID, raw URL или неоднозначный canonical ID — адресная ошибка подготовленных данных. Зафиксировать конкретное поле и сущность. Не компенсировать пробел интернет-поиском, перебором URL, выбором соседнего изображения или выдуманным фактом.

Исправление индекса является отдельной подготовкой данных. Наличие общего шаблона само по себе не разрешает публиковать выдуманные обязательные поля.

## 3. Назначение сайта и бизнес-приоритеты

Новый русскоязычный Ada Tours — сайт на Astro, GitHub и GitHub Pages. Он использует фактуру `brasiltours.ru`, утвержденные русские тексты и общую визуальную систему White Garnet. Корзины и зависимости от OpenCart нет. Основное действие посетителя — заявка или прямая связь.

Бизнес-приоритеты:

1. B2B: зарубежные туроператоры и турагентства.
2. Luxury / VIP.
3. MICE, incentive, корпоративные группы и делегации.
4. Multi-country.
5. Прямой premium B2C.

Основная география — Бразилия, Аргентина и Перу; далее остальные страны Латинской Америки. Для MICE приоритет — Бразилия, затем Аргентина, Перу и Коста-Рика. В исходной бизнес-фактуре обычные группы описаны как 40–50 человек, крупные события — 200–500, MICE/VIP — от небольших групп до примерно 50. Публичные числовые заявления берутся из утвержденного паспорта компании.

Сайт `brasiltours.ru` продолжает существовать. Массовый 301 и междоменный canonical с него на новый сайт не предусмотрены. Возможный отдельный донорский домен для постраничных 301 определяется отдельной задачей.

## 5. Сущности, идентичность и URL

Каноническая модель: Country → Destination; Tour связывается со странами, местами, темами и Excursion; коммерческие страницы связаны с Case, Review, Person и формой заявки.

Одна сущность имеет стабильный ID, независимый от URL и языка. Существующие ID и slug сохраняются. В новой записи они берутся из канонического каталога. Один продукт или одно место не дублируется из-за различий исходных URL.

Каждый Destination относится ровно к одной стране. Одноименные места из разных стран сохраняются отдельными сущностями. Бразильская сторона Игуасу — `destination_brazil_iguacu`, аргентинская — `destination_argentina_puerto_iguasu`. Тур, посещающий обе стороны, содержит оба ID. Опечатка `destination_brazil_iguazu` исправляется на `destination_brazil_iguacu`; это исправление написания бразильского ID, а не объединение двух сторон.

| Тип | RU URL |
|---|---|
| Главная | `/` |
| Страны | `/strany/`, `/strany/<country-slug>/` |
| Места | `/napravleniya/`, `/napravleniya/<country-slug>/<destination-slug>/` |
| Туры | `/tury/`, `/tury/<tour-slug>/` |
| Экскурсии | `/ekskursii/`, `/ekskursii/<excursion-slug>/` |
| Темы | `/po-interesam/`, `/po-interesam/<theme-slug>/` |
| Multi-country | `/multi-country/` |
| VIP | `/vip/` |
| MICE | `/mice/`, `/mice/delovye-delegacii/` |
| DMC / B2B | `/dmc/`, `/dmc/dlya-turagentstv/`, `/dmc/usloviya-raboty/` |
| Доказательства / редакционные материалы | `/cases/`, `/reviews/`, `/team/`, `/about/`, `/articles/` |
| Служебные страницы | `/contacts/`, `/privacy/`, `/personal-data/`, `404` |

Тур не вкладывается в URL одной страны: multi-country остается самостоятельным продуктом. Дополнительные коммерческие landing pages создаются только по отдельной задаче с самостоятельным содержанием.

RU работает в корне. Будущие `/en/` и `/cn/` используют тот же internal ID и локализованные названия/URL. При обычном добавлении RU-сущности переводов не создавать.

## 6. Связи: что хранится и что вычисляется

### 6.1. Канонический каталог мест и отложенная публикация

Канонический каталог Destination содержит ID и будущий URL каждого предусмотренного места независимо от наличия опубликованного content MD.

При сборке тура:

1. взять полный набор реальных мест маршрута из подготовленных данных;
2. сопоставить его с каноническими Destination ID;
3. записать все относящиеся к маршруту ID в `Tour.destinations`;
4. не создавать страницы мест и не удалять ID только потому, что страница еще не опубликована.

Машинная проверка валидности `Tour.destinations` обращается к каноническому каталогу, а не требует существования MD каждого места. Неизвестный каталогу ID — ошибка; известный, но еще не опубликованный Destination — нормальное состояние.

Публичные ссылки и карточки используют только доступные активные Destination. Текст маршрута и дней сохраняется полностью, включая еще не опубликованные места. При появлении Destination следующая сборка автоматически активирует соответствующие ссылки, карточки и обратные связи. Редактировать для этого старые Tour не требуется.

У экскурсии связь с Destination необязательна, если выбранная каноническая запись сознательно не задает конкретное место. Такое намеренно пустое значение не является пропуском, не создает задачу поиска и не заполняется догадкой. Если место известно, используется его единственный country-specific ID.

Добавление Destination не запускает сканирование всех туров по названиям, общий аудит географии или ручное заполнение обратных списков. Исправление исторически неполных relations выполняется отдельно по явной задаче.

### 6.2. Destination → связанные материалы

Действующий `DestinationLayout.astro` получает:

- туры — из `Tour.destinations`, до 3 по принятому `priority`;
- экскурсии — из `Excursion.destination`, до 6;
- «Куда поехать дальше» — по совместной встречаемости мест в `Tour.destinations`, до 10.

Алгоритм рекомендаций:

1. Активные RU Tour, где есть текущий Destination ID.
2. Уникальные остальные Destination ID каждого такого тура.
3. Один ID учитывается максимум один раз на тур.
4. Текущее место исключается.
5. Для публичных карточек остаются опубликованные активные Destination.
6. Сортировка: число общих туров по убыванию, затем русское название.
7. Не более 10 результатов; при отсутствии результатов блока нет.

Межстрановые рекомендации разрешены. Страна и URL карточки определяются собственным `countryId` рекомендуемого места. Универсальный заголовок — «Куда поехать дальше».

`relatedDestinations`, `featuredTours` и `featuredExcursions`, если они остаются в старых данных, не являются источником этих автоматических списков. Не заполнять и не дублировать их ради рекомендаций.

### 6.3. Tour ↔ Excursion

Самостоятельный экскурсионный продукт хранится в одной canonical Excursion. Тур хранит ее ID и позицию в программе.

```yaml
- excursionRef: excursion_source_park_jekzoticheskih_ptic_v_iguasu
  places:
    - "Фоз-ду-Игуасу"
```

У самостоятельной экскурсионной карточки нет `day`, собственного `title`, `text`, `image` или `images`. `Itinerary.astro` получает title, полный body (либо lead при отсутствии body) и hero из Excursion.

Если такая экскурсия еще не существует, она создается сразу по специализированному workflow из закрепленного самостоятельного источника либо из конкретного фрагмента собираемого тура. Пустые заглушки и ссылки на несуществующие Excursion запрещены.

Обычное упоминание объекта в тексте дня не делает его отдельной экскурсией. Самостоятельный продуктовый модуль определяется по структуре исходной программы. Вынесение такого модуля сохраняет его исходную позицию и удаляет только дублирующий текст/фото модуля; сведения о других событиях дня сохраняются.

Поддерживаемый встроенный вариант — `contentBlocks` с `type: excursion` и `excursionRef`. Самостоятельные вставки между днями оформляются отдельными itinerary-item.

Один и тот же экскурсионный продукт использует один stable ID во всех турах. Добавление новой экскурсии не поручает чату заново разбирать весь архив туров: используются готовые mappings, а историческая миграция относится к отдельной задаче.

### 6.4. Excursion → другие экскурсии

`ExcursionLayout.astro` вычисляет блок «Другие экскурсии, которые можно добавить к поездке» по общим активным RU турам:

- refs собираются из `itinerary[].excursionRef` и `contentBlocks` типа `excursion`;
- одна экскурсия учитывается максимум один раз в одном туре;
- текущая экскурсия исключается;
- для публичного списка остаются существующие активные Excursion;
- сортировка — число общих туров по убыванию, затем русский title;
- максимум 10; если пересечений нет, блока нет.

Географического fallback «то же место / та же страна» нет. Ручной `relatedExcursions` не создается. Рекомендации являются результатом структурированных relations, а не отдельным редактируемым источником истины.

## 7. Текст и факты

### 7.1. Два источника с разными ролями

Original snapshot определяет исходные факты и полноту: маршрут, дни, длительность, даты, цены, валюту, отели, питание, перелеты, трансферы, экскурсии, билеты, гидов, включенные и исключенные услуги, ограничения и условия.

Approved rewrite / V2 определяет утвержденный публичный русский язык. Он не переписывается заново ради production-разметки. Существование V2 означает готовый вход для импорта, а не команду пропустить сущность.

Для подготовленной сущности точная запись индекса указывает выбранный текст, его роль и необходимые структурированные поля. Читать `text.selected` и использовать уже подготовленные значения; не восстанавливать каркас с нуля. Если конкретное необходимое поле отсутствует или возникло реальное противоречие, обратиться только к соответствующему фрагменту exact original, указанному в записи. Уже выполненную и сохраненную сверку не повторять. Отсутствие детали в V2 не разрешает потерять известный факт из original.

Реальное содержательное противоречие фиксируется адресно. Для разрешения не использовать интернет, новые факты или догадку. Не переносить ошибку V2 в production молча.

### 7.2. Правила переноса

- Сохранять все дни и исходный порядок самостоятельных модулей.
- Сохранять цены, валюты, даты и услуги в точном значении; актуальность цены не придумывать.
- Не смешивать публичные V1-блоки с V2. Уже хороший утвержденный текст не подвергать общей стилистической чистке.
- Не сокращать V2 ради удобства разметки и не наращивать текст для заполнения шаблона.
- Имена, ID, slug, source URL и будущие production URL брать из закрепленных данных.
- Нормальные русские названия и допустимые кириллические формы сохранять. Служебная латиница в URL, ID и путях не является дефектом.
- Не добавлять в публичный текст упоминания исходника, рерайта, миграции, разработки, проверки или принимающей стороны как маркеры пересказа.
- Применять `docs/workflows/writing-rules.md` к реально создаваемому или исправляемому публичному тексту.

Для уже качественного текста редакторская задача и production-сборка остаются разными операциями. Если пользователь отдельно поручил редакторскую правку, источники синхронизируются по соответствующему workflow; обычный импорт не открывает такой проход автоматически.

## 8. Фотографии при наполнении

### 8.1. Только готовая ссылка

Из записи индекса взять уже выбранный raw URL:

```text
https://brasiltours.ru/image/...jpg
https://brasiltours.ru/image/...png
https://brasiltours.ru/image/...webp
```

`/image/cache/` полностью запрещен как рабочий и production source. Разрешенный raw WebP отличается от производного cache URL. Не перебирать расширения и не угадывать исходный путь при добавлении сущности.

Raw URL записывается в существующий media-slot. Фото не скачивается, не загружается в GitHub/Drive, не конвертируется, не улучшается и не заменяется другим кадром. GPT Image не вызывается.

Подготовка и проверка raw URL выполнены при составлении индекса. При добавлении проверяются строковое соответствие закрепленной записи и допустимый формат URL. Отдельно обращаться к каждому внешнему изображению и проверять его отображение не требуется.

Уже улучшенный локальный asset сохраняется. Не возвращать его к исходному внешнему URL и не затирать изменения параллельного фотопрохода.

### 8.2. Состав media

Состав и роли изображений закреплены заранее в индексе:

- Country — source hero и дополнительные фото существующих видимых блоков; вся старая slider/gallery не переносится.
- Destination / Excursion / Theme — предусмотренные текущим шаблоном hero, feature blocks и gallery по готовому mapping.
- Tour — source hero и фото обычных дней; самостоятельные экскурсии используют canonical `Excursion.hero`.
- Отдельный блок «Фотографии маршрута» на Tour не создается.

Не начинать при импорте новую инвентаризацию, выбор «лучших» кадров, подсчет отбраковки или запись отдельного CSV rejects. Исторические решения о media хранятся в подготовленных данных и не принимаются повторно.

Слабая резкость, старое сжатие или качество raw-фото не препятствуют наполнению и не создают задачу поиска замены. Отсутствующий обязательный URL — ошибка входных данных; размытие известного изображения относится к отдельному улучшению.

### 8.3. Отдельные задачи с фотографиями

Команда «улучши фото» использует текущий source, реестр улучшений и отдельный workflow. Обычно обрабатывается до 10 уникальных фотографий за проход; если на текущей странице осталось меньше, очередь продолжается по принятому порядку. Повторное улучшение исключается по реестру.

Скачивание, GPT Image, подготовка WebP, обновление `src` и реестра выполняются только в этом режиме. Агент не делает визуальную приемку результата и не запускает повторную генерацию по собственной оценке красоты. Следующее изменение изображения выполняется по конкретному замечанию пользователя; технические ошибки инструмента обрабатываются по фотопроцессу.

Изображения впечатлений создаются только по отдельному запросу. Отсутствие картинок у highlights не блокирует обычную публикацию тура: используется предусмотренный текстовый режим.

Завершение photo/highlights определяется техническим результатом записи файлов и соответствующего реестра по их специализированным workflow. Для этих режимов не добавляется отдельное ожидание Actions/deploy или контроль страниц. Результат в отчете соответствует фактической стадии записи.

## 9. Короткий цикл добавления сущности

Этот раздел применяется к наполнению Country / Destination / Tour / Excursion / Theme. Отдельные операции с фотографиями завершаются по разделу 8.3 и своим workflow.

1. Определить конкретный ID или следующую строку заданной очереди.
2. Прочитать точную запись индекса и только названные в ней файлы. Использовать уже полученные локальные копии.
3. Взять действующий формат сущности из ее шаблона/схемы; не изучать заново архитектуру сайта.
4. Перенести готовый текст, фактические поля, raw URL и первичные relations.
5. Для Tour включить будущие канонические Destination ID без создания мест; создать отсутствующие самостоятельные Excursion.
6. Сохранить весь готовый набор одним commit. Не публиковать промежуточные полуготовые варианты.
7. Получить результат одного штатного Actions run для commit задачи: `npm run build` включает узкую offline-проверку данных и сборку, затем выполняется предусмотренная workflow публикация.
8. Не дублировать этот шаг локальным build, дополнительным валидатором или проверкой публичного сайта.
9. Обновить только затронутые строки реестра и mappings, которые действительно изменились.
10. Сообщить названия, публичные URL и фактический статус.

Количество сущностей определяется запросом пользователя. Одна задача не расширяется в аудит ранее добавленных материалов. При команде «дальше» используется сохраненный курсор соответствующего режима.

### 9.1. Что проверяет машина

Узкая проверка выполняется один раз внутри штатного `npm run build`, без сетевых запросов. Один успешный Actions build достаточен; отдельного локального прогона перед ним не требуется. Машина проверяет:

- корректный синтаксис MD/frontmatter и соответствие действующей схеме;
- уникальность ID и production-пути;
- соответствие ID, страны и slug места закрепленному каталогу;
- существование связанных стран и допустимость ID мест, включая еще не опубликованные места из каталога;
- отсутствие повторов в `countries`/`destinations` тура и наличие страны каждого места в `countries`;
- существование всех опубликованных Excursion, на которые ссылается программа тура, включая созданные в этом commit;
- отсутствие `/image/cache/` в активном контенте, шаблонах, подготовленных записях источников и реестре фотографий;
- существование локальных фотографий, на которые ссылается активный контент;
- успешное выполнение штатной сборки.

Неизмененные шаблоны не проходят повторную приемку из-за нового MD. Общие ограничения данных обеспечивает код сборки; чат не воспроизводит их вручную на десятках страниц. Текст и фотографии переносятся из выбранной записи источников. Дни, порядок, длительность и условия тура сохраняются при этом переносе; валидатор не сравнивает смысл произвольной прозы, не сверяет фотографии с донором и не определяет самостоятельные экскурсии вместо создающего тур чата.

### 9.2. Визуальных заданий для чатов нет

Чаты не открывают страницы для проверки desktop/mobile, не снимают скриншоты, не измеряют отступы, crop, шрифты, симметрию колонок, видимость фото или состояние раскрытых карточек. Не назначать это Work или другому чату.

Описание принятого дизайна ниже задает поведение компонентов; оно не является списком действий после добавления очередной сущности. Пользователь смотрит результат и при необходимости дает конкретное замечание.

### 9.3. Commit и публикация

Зафиксировать SHA собственного подготовленного commit. Успешной публикацией считается deploy этого commit либо его потомка, который содержит неизмененные целевые файлы задачи.

Новый несвязанный commit параллельного чата не требует повторного анализа или новой приемки. Если pipeline объединил изменения, использовать итоговый deployment с нужными файлами. Не скачивать весь deployment artifact и не преследовать постоянно меняющийся последний HEAD ради стандартного добавления.

Не выполнять последовательно local build → второй Actions build → live-проверку. При реальной ошибке штатной сборки исправляется только ее причина и повторяется тот же машинный шаг. Не запускать произвольные дополнительные проверки «на всякий случай».

## 10. Реестр и продолжение работы

Основной лист `Страницы`:

| Колонка | Поле |
|---|---|
| A | URL нового сайта |
| B | Встречный URL `brasiltours.ru` |
| C | Тип страницы |
| D | Название |
| E | Статус |
| F | Дата добавления |
| G | Принята |
| H | ID / служебная пометка |
| I | Источник / комментарий |
| J | Запись источников: точная ссылка на JSON сущности в репозитории |
| K | Текст: точный выбранный файл на Google Drive |
| L | Hero: закрепленный raw URL; пусто при сохранении существующего улучшенного фото без raw-источника |

Обновлять существующую строку по ID; не создавать дубль для переименования или смены URL. `Дата добавления` ставится при первой публикации и впоследствии сохраняется. `Принята` принадлежит Анне и ее сотрудникам: чат ее не заполняет сам.

J–L — справочное отражение `data/source-index/entries/<id>.json`. Для известной сущности эти константы уже заполнены и не переписываются при каждой публикации. При появлении новой экскурсии из тура добавить ее запись источников и заполнить J–L в той же пакетной записи реестра; L остается пустой, если новый raw-источник не требуется.

`Запланирована` означает, что entity и будущий URL определены, но публикации еще нет. `Добавлена` означает опубликованную сущность. Для очереди туров `Уникализировано` отмечает публикацию с готовым V2. Исключение из релиза отражается отдельным действующим статусом.

Обновление идет после результата публикации только по затронутым строкам. `page_texts_newstep` меняется, если в задаче действительно создавался или исправлялся редакционный источник; простой импорт готового V2 не требует его повторного сохранения.

Сводка формируется из реестра. Не пересчитывать весь лист вручную после одной сущности. Общая синхронизация — отдельная задача.

Для продолжения достаточно сохранить: режим, последний ID/строку, следующий ID/курсор, commit, целевые пути и конкретный незавершенный шаг. Handoff не повторяет Master и не заменяет запись статуса в реестре.

Итоговый отчет короткий: что добавлено, какие URL, commit и статус. Не приписывать выполненную визуальную приемку и не добавлять оговорки о ее отсутствии.

## 11. Принятая визуальная система

White Garnet — визуальный референс. GAEO.ru и IndexResearch.ru служат референсами организации кода и технической дисциплины, но не оформления Ada Tours.

Сохраняются:

- hero около 85–100vh;
- фотографии на всю ширину и управляемое кадрирование средствами существующих компонентов;
- overlay около 35–45%;
- крупная геометрическая типографика;
- теплый белый, темный текст и золотой акцент;
- минимальное количество элементов интерфейса;
- асимметричные редакционные композиции и крупные цифры;
- editorial itinerary accordion;
- крупные блоки CTA;
- эксперт, команда, отзывы и связанные путешествия.

Базовые цвета и размеры сохраняются как принятые дизайн-ориентиры:

```css
--color-bg: #fffcf8;
--color-surface: #ffffff;
--color-ink: #1a1a1a;
--color-ink-deep: #131412;
--color-muted: #c5c5c5;
--color-gold: #f2cc67;
--color-gold-hover: #e6ba43;
--color-gold-soft: #f7e0a4;
--color-champagne: #e9d5a2;
--color-gold-deep: #c89a20;
--container-max: 1200px;
--gutter-mobile: 45px;
--hero-height: 100svh;
```

Исходный типографический ориентир: desktop H1 около 80/80, H2 около 70/84, highlight 60/70, крупные числа 120, body 18–20; mobile H1 около 45/52, H2 43/52, highlight 36/42, числа 70, body 16–18. Действующие значения находятся в коде и при наполнении не меняются.

White Garnet использует Futura PT / близкую геометрию. Выбор действующего шрифта и лицензирование относятся к разработке дизайн-системы. Не искать шрифт и не сравнивать его заново при добавлении страницы. Фотографии и чужие font-файлы White Garnet не переносятся.

### 11.1. Общие элементы

Header: страны, туры, интересы, VIP, MICE, агентства, о компании и единый поиск. На hero — прозрачная шапка; после scroll допустима принятая светлая полупрозрачная поверхность. Полный список стран находится в соответствующем каталоге/overlay, а не одной строкой меню.

Основной CTA — «Оставить заявку». WhatsApp, Telegram и телефон — дополнительные способы связи. Не выводить четыре равнозначные яркие кнопки.

Принятые компоненты глобального интерфейса, каталогов, editorial-блоков, туров и доказательств переиспользуются. Новое содержимое не требует новых компонентов.

### 11.2. Структура страниц

| Тип | Состав существующего шаблона |
|---|---|
| Главная | Hero, editorial statement, приоритетные страны и multi-country, VIP/MICE, выбранные направления, доказательства, Анна, CTA |
| Country | Hero, intro, места и впечатления, сезонность, туры/экскурсии/темы, практические сведения, FAQ и CTA — по действующей схеме |
| Destination | Hero, имеющиеся facts, «Зачем ехать», body, featureBands, gallery без дублей, автоматические туры/экскурсии/рекомендации и форма |
| Tour | Hero, stats, вводный текст, highlights, itinerary, маршрут, принятые сервисные блоки, цена, включено/исключено, CTA и связанные туры |
| Excursion | Hero, stats, body, gallery, цена, включено/исключено/условия, автоматические рекомендации и форма |
| Commercial | Конкретная услуга, аудитория и география, фактура, случаи из практики, отзывы и запрос предложения |

Шаблон не обязывает выдумывать отсутствующий текст. Если необязательных данных нет, блок обрабатывается существующей логикой шаблона.

### 11.3. Поведение тура

Это контракт общих компонентов, не приемочный перечень для каждого нового MD:

- обычные дни имеют `day` и номера `01`, `02` и далее;
- самостоятельные экскурсии не имеют номера и метки `ДОП.`;
- itinerary свернут по умолчанию; фотографии остаются видимыми;
- media — сосед `<details>`, не вложенный скрываемый элемент;
- desktop от 1100px использует две колонки; свернутые фотографии — `16:9`, раскрытые — гибкие;
- свернутый desktop `summary` резервирует 126px, mobile — 76px; принятые промежутки 18/18px и 10/10px;
- mobile использует одну колонку и фото на ширину viewport;
- горизонтальных разделителей карточек нет;
- `IncludedExcluded.astro` задает одинаковый display-шрифт, равные колонки и симметричные линии;
- `InlineMarkdown.astro` обрабатывает имеющийся в V2 `**bold**`; новый renderer не нужен;
- в pricing — «СТОИМОСТЬ», подтвержденная цена `от $...` и «Заказать этот тур»;
- технический `priceNote` не рендерится рядом с CTA; дополнительные оговорки ChatGPT не добавляются;
- публичное значение формата индивидуального тура — «Частный»; уточнения о групповых экскурсиях остаются в содержании.

## 12. Поиск и производные страницы

Pagefind строит единый статический индекс Country / Destination / Tour автоматически после Astro build. Добавление сущности не требует ручного search-файла, обновления отдельного списка поиска или нового исследования поисковой логики.

Поисковая запись использует ID, тип, title/name, реальные `searchAliases`, URL, страны, канонические места, темы и другие принятые структурированные поля. Длинный narrative не подменяет эти поля.

Приоритет — точное имя, начало имени, aliases, связанная география, остальные разрешенные поля. Фильтры:

- «Все» — общий структурированный поиск;
- «Страны» — название и aliases страны;
- «Места» — название, aliases и связанная страна;
- «Туры» — title, aliases, страны, места, маршрут и темы.

Случайное упоминание в описании не создает попадание в typed-фильтр. Ввод от двух символов; тип сущности показывается один раз. Отдельные EN/CN индексы появятся с соответствующими версиями.

Списки стран, мест, туров, экскурсионные связи, sitemap и рекомендации строятся из данных. Не поддерживать вторые ручные списки тех же отношений. Фильтры не создают тысячи индексируемых комбинаций URL.

## 13. SEO, фактура, формы и служебная архитектура

### 13.1. SEO/GEO

Общие шаблоны обеспечивают title/description, canonical, один H1, breadcrumbs, OG, semantic HTML, alt и внутренние ссылки. Sitemap генерируется без draft, noindex, фильтров, поиска, технических страниц и 404. Robots не блокирует полезные поисковые и AI crawlers без отдельной команды.

Структурированные данные определяются общими компонентами: Organization / TravelAgency, WebSite, BreadcrumbList, Person, TouristDestination / Place, применимые Offer, реальные Review, видимый FAQ и Article. Не добавлять выдуманный AggregateRating, цену, отзыв или компанию ради разметки.

Обычное наполнение не требует изучать Schema.org или менять schema-renderer. Это отдельная техническая задача при изменении общей реализации.

Ключевые факты компании происходят из единого утвержденного паспорта: название, история, даты, контакты, география, языки, сервисная модель, B2B-условия, подтвержденные числа и внешние профили. Не выбирать самостоятельно между историческими противоречиями 2005/2007, количеством клиентов, годами работы или обещаниями 24/7.

### 13.2. Формы и аналитика

Форма сохраняет имя, контакт, email, пожелания и согласие в принятом объеме. Служебные поля: entity/page/tour ID, locale, UTM и referrer. B2B/MICE могут содержать компанию, формат запроса, размер группы, даты и страны.

GitHub Pages остается статическим; endpoint формы внешний и задается конфигурацией, например `PUBLIC_LEAD_API_URL`. Секреты — только серверная сторона/Secrets. Аналитика подключается единым config/component. Создание одной страницы не меняет backend, legal, consent или счетчики.

404 — отдельная страница с корректным статусом, поиском и навигацией. Доступность меню, focus, Escape, семантики, reduced motion и контраста обеспечивается общими компонентами. Они не проходят ручной повторный обход после каждого добавления контента.

### 13.3. Будущие задачи запуска

Переключение домена, DNS/HTTPS/CNAME, внешняя форма, legal, аналитика, перенаправления с отдельного донора и обновление ссылок в публикациях выполняются отдельными явно заказанными задачами. Они не являются предварительным условием публикации очередной сущности на текущем GitHub Pages.

## 14. Готовность результата и границы проверки

Сущность завершена в режиме наполнения из раздела 9, когда:

1. Использованы точные закрепленные входные данные и сохранен публичный текст/критические факты.
2. Content MD соответствует действующей схеме и канонической идентичности.
3. Первичные relations полны и валидны; будущие Destination допустимы, отсутствующие Excursion — нет.
4. Подключены закрепленные raw URL либо сохранены действующие улучшенные локальные assets.
5. Один штатный Actions build со встроенными offline-проверками завершен успешно.
6. Подготовленный commit опубликован, затронутые строки реестра синхронизированы.
7. Пользователь получил ссылки и фактический статус.

Финальная резкость фотографий и будущие замечания пользователя к оформлению относятся к своим отдельным проходам. Статус наполнения не зависит от самостоятельной визуальной оценки чата.
