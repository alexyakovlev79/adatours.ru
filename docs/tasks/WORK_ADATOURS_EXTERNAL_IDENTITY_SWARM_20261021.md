# WORK — Рой обратной сверки внешних URL Ada Tours (30 × 20)

**Версия:** 1.0 · 21.10.2026. **Статус:** рабочий рой, изолированная feature-ветка.  
**Команда запуска:** «Рой ADA: сверяй внешние URL. Работай по docs/tasks/WORK_ADATOURS_EXTERNAL_IDENTITY_SWARM_20261021.md в репозитории alexyakovlev79/adatours.ru, ветка feature/external-identity-swarm-20261021. Забери одну свободную партию до 30 URL, сохраняй каждую сверку и продолжай до конца партии автоматически. Чужие резервы не трогай. Brasiltours.ru не проверяй.»

## 1. Границы и источники истины

- Репозиторий **alexyakovlev79/adatours.ru**.
- **Единственная рабочая ветка агентов:** **feature/external-identity-swarm-20261021**. Отведена от последнего подтвержденного состояния `external-identity/staging`, commit `48e10cbb4d1e27c60e83b0b4322df5b7b255d891`.
- Диспетчер: `scripts/reverse-identity-swarm-core.mjs` и `scripts/reverse-identity-swarm-remote.mjs`.
- Очередь: `data/external-identity/reverse-swarm-20261021/manifest.json` и отдельный файл `batches/<batchId>.json` на **каждую** партию. Агенты меняют **только файл собственной зарезервированной партии** через GitHub contents-CAS по blob SHA.
- Семантические правила сверки — `docs/workflows/external-identity-reverse.md`; описи источников и исторические проверки — `data/external-identity/reverse-v1/`.
- Источник выбора: **внешний URL → конкретный RU canonical**; нельзя выбирать RU-цель по одному похожему slug.
- На старте роя заморожены **1 540 еще не закрытых URL / 52 партии**: VIP 1072 (36 партий), EN 468 (16). Ранее закрытые **400 VIP** и **330 EN** статусов не входят в очередь. Файлы старого `state.json`, прежние результаты и отчеты №1–8 не меняются.
- Один чат берет **ровно одну** свободную партию **до 30 URL**, проверяет все оставшиеся в ней задачи, сохраняет каждую сразу и останавливается. **10–20 одинаковых чатов запускаются параллельно:** номера вручную распределять не нужно. Последние партии доменов содержат 22 и 18 URL соответственно.
- Запрещено менять `main`, `external-identity/staging`, старый `reverse-v1/state.json`, Google Sheets, маршруты, content MD, robots, рабочие 301, Schema.org/sameAs, SEO-реестры или чужие batch JSON. **Никаких force push, ручных переименований URL и запуска деплоя.** Финальная интеграция — отдельный мастер.

**Изменение области по прямому указанию пользователя, 21.10.2026.** Все 1 421 URL brasiltours.ru исключены из ручной сверки. Контент нового сайта создан из этого источника: связи уже есть в source-index и миграционном реестре либо отсутствуют. Отсутствующие связи допускается выявлять только машинным сопоставлением, без повторной смысловой проверки URL агентами. Не выдавать одно лишь старое sourceUrl за заново подтвержденный independent sameAs. В manifest домен перечислен только в excludedDomains, никаких br-батчей в текущей очереди нет. Старые снимки и реестры остаются нетронутыми.

## 2. Почему чаты не мешают друг другу

**Фиксированные независимые партии:** `vip-001` включает первые оставшиеся VIP URL 401–430, `vip-002` — 431–460 и т.д.; аналогично EN по оставшемуся инвентарю. Каждый URL присутствует ровно в одном файле. В manifest зафиксированы исходные Git blob SHA инвентарей и state, диапазоны и размеры партий. Рой не пересортировывает очередь после начала.

`claim` ставит lease **только внутри одного batch-файла**, ownerId+token+generation+expiresAt; CAS по file SHA означает, что из двух одновременных претендентов выигрывает один. Другой перечитывает файл и берет следующий доступный. Запрос распределяет стартовые попытки по разным партиям, а не отправляет все 20 чатов к одному первому URL. На конфликты GitHub ref/contents применяются ограниченные CAS-повторы с новым чтением; результаты других файлов не перезаписываются.

**Lease 90 минут**; продлевать свой каждые 30–45 минут или при остатке менее 20 минут. Просроченный lease можно перехватить: ранее сохраненные результаты отдельных URL остаются неизменными, новый агент продолжает только `queued`. Просроченный бывший владелец больше не может записывать новые решения. `release` досрочно освобождает недоделанный batch, сохраняя выполненные URL.

Результат **каждого URL записывается сразу** через `submit` в тот же JSON атомарно. Повтор **того же** payload возвращает `already_saved` или `saved_after_uncertain_response`; попытка переписать уже проверенный URL другим выводом отклоняется. Время проверки, владелец, доказательства, RU URL и commit SHA сохраняются. Исходные файлы `reverse-v1/results/` не перезаписываются.

## 3. Один запуск в новом чате: резерв

В доступном Code Mode выполнить **один раз**. Каждому чату нужны уникальные ownerId и token; после вывода **сохранить обе строки и batchId** для всех последующих вызовов этого чата. Не использовать одни и те же ownerId/token в разных чатах. Не делегировать claim другому чату.

~~~javascript
const repo='alexyakovlev79/adatours.ru';
const ref='feature/external-identity-swarm-20261021';
const paths=['scripts/reverse-identity-swarm-core.mjs','scripts/reverse-identity-swarm-remote.mjs'];
const [a,b]=await Promise.all(paths.map(path=>tools.mcp__GitHub__fetch_file({
  repository_full_name:repo,path,ref
})));
const core=new Function(a.result.content.replace(/^export /gm,'')+
 ';return {SWARM_ROOT,BRANCH,LIMIT,LEASE_MINUTES,STATUSES,DOMAINS,stamp,hashString,requireIdentity,batchPath,validateBatch,batchIdMatchesDomain,summary,leaseIsActive,claimBatch,changeLease,validatedResult,submitResults};')();
const swarm=new Function(b.result.content.replace(/^export /gm,'')+
 ';return runReverseIdentitySwarm;')();
const ownerId='reverse-worker-'+Date.now().toString(36)+'-'+Math.random().toString(36).slice(2,14);
const token='reverse-lease-'+Date.now().toString(36)+'-'+Math.random().toString(36).slice(2,14);
text({ownerId,token,result:await swarm(tools,core,{action:'claim',ownerId,token})});
~~~

При `reserved`, `reclaimed` либо `resumed`: получил свою **одну** партию `batchId`, `remaining[]` и срок lease. Не бронировать следующую, пока эта не завершена. При `scan_more` повторить claim **с теми же ownerId/token** и `cursor` / `scanned` из ответа до получения партии либо `no_claimable_batch`; не объявлять все 52 партии выполненными по одному неудачному поиску. Если потерян именно ответ о резерве, сначала `recover`, не создавать новый owner/token.

**Важно:** Code Mode начинает новый изолят для нового вызова. Повторно загружать две программы как в коде выше, но **вместо генерации** ownerId/token вставлять точные строки из первого вызова. Не генерировать новую пару при `submit`, `renew`, `release`, `recover`.

## 4. Сверять по смыслу, а не по совпадению слов

Проверять текущую активную RU-страницу/каноническую source-index entry, полный предмет страницы и исходные доказательства, включая сохраненные `title`, `h1`, `snapshotHttp`, `pageType` и точный `snapshotFile` из frozen inventory. Если доступен исходный приватный HTML-снимок, использовать его; при отсутствии не утверждать, что он просмотрен. Точные ID, тип, назначение, география, программа, маршрут, длительность, существенные условия и состав каталога имеют приоритет перед похожими названиями.

- **vipdeluxetravel.ru:** `redirect_ready` только когда подтверждены релевантная существующая RU-цель, тот же объект/намерение и доказательства. Это **подготовка будущей карты 301**, не включение 301. Пустой HTML при HTTP 200 у старых `/packages` / `/ekskursii` не подтверждает прежний ассортимент: можно принять географию/тип и существующий непустой RU-каталог, но нельзя заявлять равенство товарного состава. При отсутствующем активном целевом каталоге — `review`, решение «страница места или 410» отдельно, **не перенаправлять на несуществующий URL или главную**.
- **adatours.com:** `matched_exact`/ `sameAs` только при подтвержденной идентичности самой сущности или действительно той же программы тура/экскурсии. Историческое происхождение из `sourceUrl` само по себе еще не доказывает идентичность текущего продукта. Статья об объекте не является `sameAs` самого Tour. Состав и фильтры каталога должны совпадать, иначе `review` / `checked_no_confirmed_pair`.
- **Общие состояния:** `checked_no_confirmed_pair` — проверено, подтвержденной пары нет; `review` — неоднозначность/нужно редакционное решение; `retry` — реальная техническая невозможность проверки; `excluded` — подтвержденный технический дубль/robots/non-content. Не путать `retry` с отсутствием пары, сохранять точные причины.
- В `evidence` для `matched_exact` / `redirect_ready` минимум **2 конкретных проверенных основания**: одно об исходном объекте, одно о его действующей RU-сущности/странице. Не выдумывать HTTP-проверки, маршруты, названия, цены или выполнение 301.

## 5. Сохранять каждую проверку немедленно

После каждого URL выполняй `submit` на **тот же** `batchId`. В том же Code Mode вызове, где есть `core`, `swarm` и сохраненные значения, пример:

~~~javascript
text(await swarm(tools,core,{
 action:'submit',
 ownerId:'СКОПИРОВАННЫЙ_OWNER_ID',
 token:'СКОПИРОВАННЫЙ_TOKEN',
 batchId:'vip-001',
 results:[{
  sourceUrl:'ТОЧНЫЙ_SOURCE_URL_ИЗ_remaining',
  status:'redirect_ready',
  ruUrl:'https://adatours.ru/ТОЧНЫЙ-КАНОНИЧЕСКИЙ-АДРЕС/',
  evidence:[
   'Конкретное проверенное доказательство идентичности исходной страницы.',
   'Проверенная действующая RU-сущность, stable ID и совпадение географии/назначения.'
  ],
  note:'Подготовлен кандидат на будущий 301; сам редирект не включен.'
 }]
}));
~~~

Пример выше — **схема вызова, не готовый результат**. Для `review` / `retry` / `excluded` / `checked_no_confirmed_pair` передавать `ruUrl:''` и `note` от 28 символов с конкретной причиной (у `excluded` также evidence). Диспетчер сам назначит `relation: sameAs` / `redirect_301`; не вписывать свое отношение. `submit` принимает 1–10 URL за вызов, но стандарт роя — **по одному URL**, чтобы не потерять уже выполненные проверки при зависании.

Успех: `saved`, `saved_after_uncertain_response` или `already_saved`. По первому успешному ответу фиксировать commit SHA. При неопределенном результате повторить **тот же payload** с тем же batchId и ownerId/token. Не искать новую партию и не повторять исследования до подтверждения отсутствующей записи. `completedAt` в batch и `queued:0` подтверждают закрытие партии первого прохода, даже если в ней есть `review` / `retry`.

## 6. Продление, возобновление и раннее завершение

Используй один и тот же bootstrap кода из §3, подставив сохраненные ownerId/token без генерации.

- Продлить: `swarm(tools,core,{action:'renew',ownerId,token,batchId})`.
- Восстановить после обрыва: `swarm(tools,core,{action:'recover',ownerId,token,batchId})`. Если batchId потерян, `recover` допускает поиск по собственным ownerId/token без него. Использовать только `remaining[]`; сохраненные URL не перепроверять.
- Освободить досрочно: `swarm(tools,core,{action:'release',ownerId,token,batchId})`. Делать лишь при остановке, а не после каждого `submit`.
- Общая сводка для координатора: `swarm(tools,core,{action:'status',from:0,count:10})`, затем from=10,20,…,50; суммировать `done`, `queued`, `review`, `retry` и занятые партии. `overview` дает неизменные размеры первоначальной очереди.

По окончании одной партии **остановиться** и дать отчет: batchId, домен, диапазон исходных позиций, число URL, `matched_exact` / `redirect_ready` / `checked_no_confirmed_pair` / `review` / `retry` / `excluded`, commit SHA, незавершенные задачи и факт освобождения lease. Не спрашивать подтверждения между URL внутри партии.

## 7. Координатор и итоговая интеграция (отдельно от агентов)

Все 52 batch-файла — source of truth **новой** проверки; неизмененный `reverse-v1/state.json` в feature-ветке — frozen baseline для защиты старых результатов. Агентам **нельзя** переносить свои решения туда или в `external-identity/staging`. Мастер после волны/общего завершения:

1. Получает точные статусы и Git blob SHA затронутых batch-файлов; экспортирует только сохраненные записи. Требует уникальность source URL и исходную принадлежность к frozen inventory. Для каждой записи сверяет неизменность статуса, evidence и checkedAt. Все `review` / `retry` оставляет как такие статусы, не преобразует в подтвержденный 301/sameAs.
2. На актуальном `external-identity/staging` сравнивает каждую source URL со свежим `state.json`: для несуществующей записи делает вставку, для идентичной — пропуск, конфликт с независимо проверенным результатом — отдельный `REVIEW` и ручное разрешение; **никогда не затирает** прежний status. Переносит сохраненные batch-результаты и provenance с точными blob SHA и commit, сохраняя прежние reports/receipts.
3. Записывает согласованный пакет в staging через CAS, без force и без изменений production; после этого формирует RU-first/source-first отчеты. Лишь отдельная финальная публикация проверенных `matched_exact` может изменить JSON-LD; лишь отдельный релиз проверенных `redirect_ready` с реальной HTTP-проверкой целевых URL может включить 301 на VIP-домене. `review` / `retry` не включать.
4. После подтвержденной интеграции один раз синхронизирует Google Sheets по source URL и RU canonical, не по прежним номерам строк. Сбой Sheets повторяет **только отражение**, а не сверку или CAS-коммит.

Чтобы не было двух независимых активных диспетчеров на одни URL, на время роя **не запускать старую команду «сверяй дальше»** против `external-identity/staging`. Рой и исходная очередь не меняют прошлые 400 проверок.

## 8. Безопасность и ограничения

Каждая партия изолирована, но GitHub API имеет общий предел запросов и может возвращать `429`/`403`/secondary rate limit. При таком ответе не создавать новые ownerId/token, не переходить к другому batch и не считать статус сохраненным. Продлить lease, если срок еще действует; при устойчивом ограничении зафиксировать последнее подтвержденное состояние, освободить lease при возможности и завершить чат. Запуск 10–20 чатов поддерживается протоколом CAS, но фактическая скорость зависит от GitHub-квот и продолжительности смысловой проверки.

**Запрещено:** использовать один токен в нескольких чатах, менять чужой batch, пытаться отправить URL вне `remaining[]`, перезаписывать подтвержденный результат, трактовать `review` как «готово к 301», создавать выдуманный RU canonical, ждать согласия пользователя на каждый следующий URL, писать в production до отдельного мастера.
