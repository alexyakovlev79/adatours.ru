# Ada Tours — исправление фотографий в днях туров

Версия: 1.1 · Дата: 08.10.2026

Репозиторий: `alexyakovlev79/adatours.ru`, ветка `main`.

Рекомендуемый путь в репозитории: `docs/workflows/tour-day-photo-repair.md`.

При подключении файла к репозиторию добавить в таблицу входов `AGENTS.md` строку «Исправить дубли и заполнить фото дней тура → `docs/workflows/tour-day-photo-repair.md`». Само создание или загрузка этой инструкции не запускает обработку туров: нужна команда пользователя на исправление.

Версия 1.1 уточняет отдельные вызовы генератора, состав передаваемого задания, запрет нарезки коллажей и продолжение после неудачной генерации. Если пользователь приложил эту версию, а в репозитории осталась 1.0, при следующем запуске исправления синхронизировать рабочую инструкцию с приложенной версией, сохранив выполненные операции и журнал.

## 1. Когда применять и какой результат получить

Применять по командам пользователя: «исправь фото у следующих 10 туров», «исправь фото у следующих 50 туров», «исправь фотографии по дням этого тура» и продолжению такой задачи.

Число в команде означает **число туров**, а не фотографий. В каждом выбранном туре обработать все обычные карточки дней. Карточка «Дни 5–8» считается одной карточкой: ей достаточно одного изображения.

Готовый тур соответствует всем условиям:

- у каждой обычной карточки дня есть минимум одно работающее изображение;
- фотографии разных дней этого тура различаются; переименование, изменение размера или обрезка одного кадра различием не считаются;
- внутри одной карточки тоже нет повторов одного изображения;
- новые изображения соответствуют точной стране, месту и содержанию дня;
- изменения опубликованы, затронутые реестры обновлены.

**Вставки с самостоятельными экскурсиями исключены из этого прохода.** Изображения таких вставок не участвуют в поиске дублей, генерации и проверке уникальности. Совпадение фотографии обычного дня с фотографией экскурсионной вставки допустимо в рамках этой задачи. Hero тура, общая галерея и highlights также находятся вне сравнения. Между разными турами уникальность не требуется.

## 2. Приоритет этой инструкции

Это отдельный режим исправления иллюстраций по прямому поручению пользователя. Для него разрешены:

1. Удаление лишних повторяющихся фотографий из обычных карточек дней.
2. Создание новых кадров через GPT Image, в том числе на основе уже улучшенной фотографии.
3. Самостоятельная визуальная приемка результата чатом и исправление выявленных дефектов.
4. Заполнение уже запланированных страниц мест коротким самостоятельным описанием и подходящим изображением, созданным в этом проходе.

Эти разрешения заменяют противоречащие им ограничения `photo-enhancement.md`, `destinations.md`, `destination-reservations.md` и `master.md` **только в границах данного процесса**. В частности, здесь не действуют обязательное сохранение прежнего кадра, пропуск всех `-enhanced-` и ожидание материалов Анны для указанного в разделе 9 случая. Пользователь уже разрешил генерацию, приемку, публикацию и создание таких страниц мест; повторное согласование каждого фото или места не требуется.

Сохраняются общие контракты архива, stable ID, английских URL, схемы контента и автоматических связей. Программа, цены, даты, последовательность карточек и тексты существующего тура сохраняются. Изменения фотографий не запускают миграцию экскурсионных вставок.

## 3. Выбор туров и продолжение после остановки

Использовать свежие данные `main`. Точные ID и `contentPath` брать из `data/source-index/catalogs/tours.json` и `data/source-index/entries/<tourId>.json`; текущие изображения и программу — из production MD.

Порядок выбора:

1. Явно указанные пользователем туры имеют приоритет.
2. Для «следующих N» продолжить сохраненную очередь именно исправления фото дней.
3. При первом запуске использовать порядок строк листа `Страницы`, уже закрепленный в `entry.sheet.row` / `registryRow`. Записи без номера строки идут после них, по stable ID. Зафиксировать этот порядок.
4. До применения лимита исключить архив по `data/catalog-archive.json` и статусу сущности, черновики и туры без опубликованного MD.
5. Пропустить уже успешно обработанные туры, если программа и набор фотографий их обычных дней с тех пор не изменились.

Обычная очередь `scripts/photo-queue.mjs` ищет неулучшенные исходники и сама по себе для этой задачи не подходит: здесь обрабатываются также дубли уже улучшенных фото и пустые дни. Сохранять ее правила исключения архива, но выбирать туры по правилам этого раздела.

Тур, уже удовлетворяющий условиям, записать как «проверен, изменений не требует» и учитывать в выбранных N. Тур с блокером тоже сохраняет свое место в выбранном наборе, но выполненным не считается. Сообщать раздельно число выбранных, завершенных и заблокированных туров; дополнительные туры взамен заблокированных самовольно не добирать.

Ввести журнал `data/media/tour-day-photo-repair.json` (это новый служебный файл данного workflow, создать при первом запуске). Хранить версию процесса, очередь и курсор, tour ID, точный contentPath, отпечаток проверенной программы/слотов, операции по карточкам, готовые asset-пути, результаты приемки и блокеры. Для карточки фиксировать позицию в itinerary, обозначение дня/диапазона и название; если у проекта есть стабильный ID карточки, использовать его. При изменении структуры заново сопоставить карточку по содержанию, а не писать по старому индексу.

Для каждого результата сохранять входной reference, страну, место, точный текст реально переданного инструменту запроса, номер попытки для этого слота, файл результата и этап. Если инструмент возвращает ID вызова или измененный им промпт, сохранить их тоже. Фраза в сообщении пользователю перед генерацией не заменяет запись фактического запроса. Готовый принятый кадр после обрыва переиспользовать. Завершенный тур повторно не генерировать. Статус публикации подтверждать штатным Actions/deploy соответствующего commit, а не одним наличием записи в журнале.

Работать последовательно по турам. По умолчанию каждый законченный тур с возникшими страницами мест публиковать одним логическим пакетом, чтобы не держать все 50 туров до последнего commit. Если пользователь явно задал другой размер партии, соблюдать его. Сохранять полученные изображения и рабочий прогресс по мере генерации; при длительном проходе сообщать краткий статус. Одна завершенная партия не отменяет оставшуюся часть запроса.

## 4. Инвентаризация обычных карточек дней

Прочитать выбранный MD и фактический контракт `src/content.config.ts` / `Itinerary.astro`. Учесть все поля изображений, которые реально отображаются внутри обычной карточки дня, включая локальные блоки контента, если они есть. Поиск только по одному имени поля недостаточен.

Исключить самостоятельные вставки с `excursionRef`, в том числе `contentBlocks` типа `excursion`. Обычный номерной день с текстом об экскурсии остается обычным днем: слово «экскурсия» в заголовке не исключает его из обработки. У старой локальной вставки без `excursionRef` определить ее роль по структуре; при неоднозначности зафиксировать конкретную карточку для разбора, сохранив остальную работу.

Составить компактную рабочую таблицу: карточка/день, название, страна, точное место, краткое содержание дня, все текущие image-src, владелец слота, количество фото, группа дублей, действие. День с пустым массивом изображений или отсутствующим полем считать днем без фото. Если путь есть, но файла нет или он не декодируется, такой слот не обеспечивает карточку рабочим изображением и также требует восстановления.

### Что считать дублем

- Один и тот же asset/src, включая абсолютный URL и его локальный путь с учетом текущего base path.
- Одинаковые байты или одинаковое декодированное изображение под разными именами.
- Копии того же кадра после изменения размера, сжатия, кадрирования или обычного улучшения; использовать точный mapping реестра и визуальное сравнение.

Для подозрительных разных файлов применять визуальное сравнение или контактный лист. Контактный лист — временная техническая сборка миниатюр уже существующих файлов для проверки; его можно собрать локальным скриптом. GPT Image для создания контактного листа не вызывается. Он не передается генератору как reference и не служит источником картинок для публикации. Перцептивный хеш может найти кандидатов, но близкое значение само по себе не доказывает дубль. Два разных ракурса одного места допустимы. Разные результаты творческой генерации от общего reference тоже допустимы, если это действительно разные кадры.

Нормализовать только подтвержденные эквивалентные адреса. Не срезать произвольно параметры версии или менять регистр пути. Само совпадение названия места или `alt` дублем не является.

## 5. Сначала удалить лишние повторения

Удалять повторяющийся кадр из карточки, если после удаления у нее остается хотя бы одно другое работающее фото. Уникальные дополнительные фото сохранять.

Порядок нужен, чтобы не удалить все экземпляры сразу:

1. Внутри каждой карточки оставить один экземпляр каждого кадра.
2. Для каждой группы повторов между днями определить карточку, которой исходный кадр подходит лучше всего. При равной уместности предпочесть карточку с единственным фото, затем более раннюю по программе.
3. В остальных карточках удалять повтор по одному, каждый раз пересчитывая остаток. Если другое фото остается — удалить повтор. Если повтор уже стал единственным — сохранить слот для замены через GPT Image.
4. В сохраненной карточке исходный кадр оставить. В результате удаления ни одна ранее иллюстрированная карточка не должна остаться пустой.

Пример: одинаковый кадр стоит в дне 1, дне 3 и вторым фото дня 4. У дня 4 удалить повтор, оставив Игуасу. Между днями 1 и 3 выбрать наиболее подходящее использование исходника; для другого дня создать новый кадр. Не требуется перегенерировать все экземпляры группы.

Удаляется ссылка из целевого MD, а не общий файл на диске: этот asset может использоваться в других днях, турах или сущностях.

## 6. Подготовить задания GPT Image

### Один вызов — один самостоятельный кадр

**Для каждого нового фото выполнить отдельный вызов GPT Image.** Если нужно пять кадров, нужны минимум пять отдельных успешных генераций; неудачные попытки считаются дополнительно. Каждый принятый результат — самостоятельное полноразмерное изображение одной сцены. При наличии параметра количества результатов указать `1`.

Генерировать последовательно: одно задание → один вызов → приемка → сохранение результата → следующее задание. Список туров и дней остается рабочим планом чата и не отправляется генератору одним запросом.

**Запрещено создавать общий коллаж, сетку, контактный лист, инфографику, раскадровку или изображение всего маршрута, а затем нарезать его для разных дней.** Запрет действует и для большого исходного полотна. Изменение размера вырезанного фрагмента не превращает его в самостоятельную генерацию. Если GPT Image вернул коллаж, результат отклонить целиком и применить порядок повторной попытки из раздела 7.

### Передать только задание на выбранную сцену

Для каждого оставшегося повторения, требующего замены, передать генератору **само текущее дублирующее изображение** как reference, а также точную страну, точное место и краткое описание конкретного дня. Загрузить общий reference один раз и использовать уже полученный файл для всех нужных вариантов.

Для дня без рабочего фото создать изображение по стране, месту и содержанию дня. Если пригодного reference нет, использовать генерацию по тексту.

В явно передаваемом генератору запросе оставить одну страну, одно выбранное место/объект, краткое содержание только этого дня и одну нужную сцену. Номер дня, название всего тура, его длительность, полный MD, программа остальных дней и перечень требуемых фотографий остаются в журнале. Формулировать запрос как создание фотографии; задача верстки страницы, карточек и маршрута генератору не передается.

Сравнение с другими днями выполняет сам чат при выборе сцены и приемке. Вместо списка фотографий остальных дней передавать только конкретное указание на нужную композицию, например «вид с уровня набережной в сторону холмов».

В вызове явно выбрать только reference текущего слота. Скриншоты сайта, контактные листы, предыдущие неудачные коллажи и изображения других стран во вход этого вызова не включать. Для генерации без reference не запрашивать включение последних изображений беседы. При наличии локального файла использовать его точный путь через поддерживаемый инструментом механизм; если выбрать нужный reference однозначно нельзя, сохранить ограничение для конкретного слота. Не подменять вызов командой «доработай последнюю картинку», если последняя картинка — коллаж.

Географию определять по программе и каноническому каталогу `src/data/catalog/destinations.json`, включая aliases. Для мультистранового тура страна всего тура не заменяет страну конкретного кадра. У Игуасу различать бразильскую и аргентинскую стороны. При нескольких остановках выбрать одну явно посещаемую локацию и указать ее в промпте; фото не должно изображать коллаж всего маршрута.

Краткое описание дня: 2–5 предложений о фактическом месте, посещаемых объектах и занятиях. Оно служит заданием для изображения и не заменяет опубликованный текст дня. Для свободного дня подойдет другой вид того же города или курорта; для переезда — подтвержденное место отправления или прибытия. Не добавлять в промпт достопримечательность лишь потому, что она популярна в этой стране. При неясной локации уточнить точный исходник программы; случайный объект не выбирать.

Перед генерацией выбрать отличающуюся сцену: например, для дня приезда — берег и прогулочная набережная, для экскурсионного дня — посещаемая гора или вид с нее. Замена должна заметно отличаться от остальных фотографий дней тура, а не только цветом неба или небольшой обрезкой.

### Промпт для замены дубля

```text
Создай ОДНУ самостоятельную реалистичную фотографию одной сцены на все полотно.
Страна: [точное название страны].
Место: [каноническое название, регион и конкретный объект при необходимости].
Контекст посещения: [2–3 предложения о программе только выбранного дня].
Нужная сцена: [выбранный сюжет и заметно отличающийся ракурс].

Приложенное отдельное фото — визуальная опора. Создай ДРУГОЙ кадр этого же
места в указанной стране с выбранной выше сценой и композицией. Точно повторять
приложенную фотографию не требуется. Сохрани узнаваемую географию и реальный
облик объекта. Не подменяй его похожим местом в другой стране.
Естественные цвета, правдоподобная перспектива и детали. Горизонтальная
композиция, предпочтительно 16:9. Один непрерывный кадр от края до края.
Без текста, номеров дней, логотипов, водяных знаков, рамок и полей.
Без коллажа, сетки, отдельных панелей, миниатюр и инфографики маршрута.
```

### Промпт для дня без фото

```text
Создай ОДНУ самостоятельную реалистичную фотографию одной сцены на все полотно.
Страна: [точное название страны].
Место: [каноническое название, регион и конкретный объект при необходимости].
Контекст посещения: [2–3 предложения о программе только выбранного дня].
Покажи: [одна конкретная сцена, соответствующая программе].

Сохрани реальный облик и узнаваемые особенности указанного места. Естественные
цвета, правдоподобная перспектива и детали. Горизонтальная композиция,
предпочтительно 16:9. Один непрерывный кадр от края до края.
Без текста, номеров дней, логотипов, водяных знаков, рамок и полей.
Без коллажа, сетки, отдельных панелей, миниатюр и инфографики маршрута.
```

Использовать доступный инструмент GPT Image. Если в карточке уже сохранилось подходящее уникальное фото, дополнительно заполнять удаленные слоты не нужно. Для полного прохода с файлами, репозиторием и реестрами рекомендуется Work. Название режима не заменяет требования к доступным инструментам и отдельным вызовам; обычный чат с необходимыми возможностями соблюдает тот же процесс.

## 7. Самостоятельная приемка и WebP

Чат сам просматривает каждый новый результат и принимает решение. Проверить:

- соответствие стране, месту и выбранной сцене;
- отсутствие явных ошибок в узнаваемых объектах, перспективе и деталях;
- отличие от других кадров обычных дней этого тура;
- отсутствие подписей, рамок, коллажей и заметных артефактов.

Уверенность в точной локации должна опираться на подтвержденные особенности, а не только на текст промпта. Если их недостаточно, использовать подходящий проверенный reference или адресно проверить облик конкретного объекта. Это не запускает общий поиск фотографий всего тура.

### Если получился коллаж или другой непригодный результат

Неудача относится к конкретному слоту. Две неудачные генерации в туре не являются основанием оставить остальные запланированные кадры без попыток.

1. **Первая попытка:** отдельный вызов по одному из промптов выше. При дефекте записать фактический запрос, reference, результат и конкретную причину отклонения.
2. **Вторая попытка:** проверить реально переданные данные, убрать попавшие туда другие дни/изображения и сократить задание до одной страны, одного объекта и одной композиции. Для замены дубля снова прикрепить исходное отдельное фото. Для пустого дня вызвать новую генерацию по тексту. Отклоненный коллаж во вход не передавать и не просить вырезать из него удачную панель.
3. **Третья попытка:** еще один отдельный вызов для этого же слота с максимально конкретной сценой и кратким запросом. Допустимо сформулировать его по-английски. Сохранить обязательные страну, точное место и суть посещения; при замене дубля сохранить правильный reference. Краткий пример для пустого дня приведен ниже.
4. После трех непригодных результатов **для одного слота** за текущий проход отметить этот слот заблокированным и перейти к следующим. Остальные независимые задания выполнить. Только подтвержденная общая недоступность инструмента, исчерпание лимита или системный запрет останавливает все зависимые генерации; причину сообщить точно.

Пример краткого запроса для пустого дня в Морае:

```text
Generate one photorealistic landscape photograph of the Moray archaeological
site in the Sacred Valley, Peru. Show its recognizable concentric circular
agricultural terraces in one continuous scene, viewed from the rim. This will
illustrate a visit to the archaeological site. Natural daylight, horizontal
composition, preferably 16:9, full-bleed. No collage, grid, panels, itinerary,
text, labels, borders, or inset images.
```

Техническую ошибку без изображения учитывать отдельно от визуального брака; при явно временном сбое допустим один повтор. Ограничения доступа и лимитов не обходить повторными вызовами. Успешный принятый кадр не перегенерировать ради дополнительных вариантов.

Принятый результат преобразовать в WebP без растяжения, полей и произвольной обрезки. Использовать полный отдельный результат генератора, а не превью из чата, скриншот или вырезанный фрагмент коллажа. Ориентир качества — 85–90; при необходимости уменьшить до ширины 1536–1920 px с сохранением пропорций. Меньший результат искусственно не увеличивать. Проверить декодирование и фактический формат, записать исходные и итоговые размеры в пикселях. Пропорции 16:9 запрашиваются при генерации, а не обеспечиваются искажением готового файла.

Сохранить новый файл отдельно, например:

```text
public/media/tours/<существующая-папка-тура>/itinerary-day-03-generated-YYYYMMDD-v1.webp
```

Для диапазона использовать `itinerary-days-05-08-...`; при повторяющейся нумерации добавить однозначный ключ карточки. Точное имя выбирать без коллизии с существующим файлом. В MD указывать `/media/...`, без `public` и без жестко заданного префикса `/adatours.ru`.

Обновить `alt` и зависимую подпись под фактический новый сюжет. Не переносить на сгенерированный кадр имя фотографа исходника. Историю исходника и reference сохранить в служебных данных. Новые варианты не перезаписывают общий файл, который используется другими страницами.

## 8. Реестр фото: отдельный вариант для конкретного дня

`src/data/media/photo-enhancements.json` содержит глобальные соответствия исходника и улучшенной версии. **Новый вариант для дня нельзя записать как замену прежнего общего `source → enhanced`.** Иначе следующий фотопроход снова подставит один кадр в разные дни.

Для каждого созданного asset добавить отдельную запись в существующий массив `enhancements`, сохранив остальные поля документа и чужие записи. Использовать поддерживаемый способ регистрации самостоятельной генерации: `source` и `enhanced` равны собственному новому `/media/...`, `method: gpt-image`, фактическая дата и revision. Проверить действующий validator перед записью. Пример:

```json
{
  "source": "/media/tours/example/itinerary-day-03-generated-20261008-v1.webp",
  "enhanced": "/media/tours/example/itinerary-day-03-generated-20261008-v1.webp",
  "enhancedAt": "2026-10-08",
  "method": "gpt-image",
  "revision": 1
}
```

Связь с reference, прежним src, туром, карточкой и промптом хранить в журнале этого workflow. Она фиксирует происхождение и не означает тождество двух разных сгенерированных кадров. На один физический файл — одна запись обработки; использований файла может быть несколько.

Исторические `entry.media.images` и `dayImages`, если они являются инвентаризацией донора, не переписывать под видом оригиналов. Текущие назначения хранить в production MD и поддерживаемых полях текущих media. Зафиксировать изменения так, чтобы повторный импорт не восстановил удаленные дубли.

В листе `Фото` основного реестра обновить только затронутые строки по `photo_record_id`, entity ID и слоту. Новый слот получает свою строку. Удаленный слот сохранить в истории со статусом `ARCHIVED` и комментарием «Удален повтор из карточки дня»; это не архивирование самого тура. При изменении порядковых индексов согласовать их с MD, сохранив идентичность оставшихся записей.

Для новых/замененных фото использовать действующие колонки: J — текущий путь, T — `REPLACED`, W — `public/media/...`, X — фактический production URL, Z — дата, AA — кто обновил, AB — commit, происхождение GPT Image и итог приемки. Из V убрать исполненное поручение, сохранив независимые замечания. Статус `REPLACED` сам по себе не заменяет запись о приемке.

## 9. Создать уже запланированную страницу места

Если принятый новый кадр изображает место, которое уже запланировано в каноническом каталоге/очереди, но еще не имеет опубликованной страницы, **создать эту страницу в том же проходе**. Изображение должно уверенно относиться к этому месту и подходить для его hero. Все остальные отсутствующие места маршрута этим условием не охватываются.

Сцену выбирать по программе дня. Специально выбирать только места без страницы не требуется. Создание страницы — следствие подходящего принятого кадра; проблема с этой страницей учитывается отдельно и не отменяет пригодность самого фото для дня тура.

Публикуется существующая сущность Destination под прежними ID, страной, slug и URL. Новая сущность для каждого ракурса или дня не создается. Если место уже успел опубликовать другой чат, использовать существующую страницу; ее готовый контент и hero автоматически не перезаписывать. Архивные места сохраняют архивный статус. При неоднозначном соответствии оставить конкретный вопрос в журнале.

Порядок заполнения:

1. Взять точную запись каталога, резерв и source entry, если она уже есть. Сохранить их identity и материалы.
2. Подготовить короткое самостоятельное описание места: обычно 2–3 содержательных абзаца, около 80–150 слов. Объяснить, где оно находится, что собой представляет и что там видит путешественник. Факты брать из закрепленного материала места и подтвержденной программы; при недостатке сведений адресно проверить надежный источник о самом объекте и сохранить ссылку. Объем не добирать выдуманными фактами. Текст описывает место и не пересказывает весь тур.
3. Сохранить новый редакционный материал в `data/source-index/materials/<destinationId>.md`, отдельно зафиксировать фактические источники и происхождение. Имеющийся исходный материал не затирать: при необходимости сохранить новую версию отдельным файлом с корректным указателем.
4. Создать полноценный Destination MD по действующей схеме: `id`, `locale`, `slug`, `countryId`, `name`, `summary`, `destinationType`, `status: approved`, `hero` и body. Тип брать из подтвержденных данных, а не назначать `city` по умолчанию. Необязательные факты и блоки заполнять только при наличии материала.
5. В `hero.src` поставить тот же принятый WebP, который используется в дне тура. Копировать байты в другую папку не требуется. Для новой страницы допустимо сразу хранить общий asset в `public/media/destinations/<destinationId>/` и ссылаться на него также из тура. Это одно изображение с двумя использованиями и не нарушает уникальность дней внутри тура.
6. Взять собственные `themes` места по его содержанию и закрытому справочнику; метки тура не наследовать. Обратные списки туров и экскурсий вычисляет сайт. Уже существующие связи по ID активируются автоматически.
7. Обновить source entry, `data/source-index/index.json`, `catalogs/destinations.json`, материалы и статус существующего резерва на `added` вместе с полноценным MD. При необходимости использовать штатный `scripts/sync-source-catalogs.mjs` и синхронизацию статусов резервов. Само наличие файла изображения не переводит место в опубликованные.
8. После успешного deploy обновить строку места в листе `Страницы` и в очереди материалов Анны. Снять исполненное ожидание описания/фото, указав создание в этом проходе. Сохранить старые материалы и замечания как историю.

### Происхождение сгенерированных материалов

Сгенерированный кадр регистрировать как GPT Image, а написанное чатом описание — как редакционный материал на основе перечисленных источников. Они не являются фотографией, предоставленной Анной, или снимком старого сайта. `sourceUrl` старой страницы сохранять, если он реально существует; при его отсутствии использовать `null` в JSON и опускать необязательный `sourceUrl` в MD.

На 08.10.2026 `data/source-index/entry.schema.json` ограничивает локальные текстовые указатели режимом `provided_materials`, а `provided_originals` требует `user_provided`. Перед первым созданием места в этом режиме проверить текущую схему и обслуживающие скрипты. Если отдельный режим сгенерированных материалов уже реализован, использовать его. Если нет — один раз добавить узкую поддержку редакционного текста в репозитории и GPT Image в source-index/schema/validator, сохранив строгую проверку остальных режимов. Например: `text.selected.kind: editorial_generated`, `media.status: generated`, `media.provenance.kind: gpt_image` с соответствующим `readiness.media`. Это новые значения, их нельзя просто вписать в MD/JSON без поддержки проверки.

Локальный указатель содержит точный `repositoryPath`, имя файла и `mimeType: text/markdown`; provenance — источник фактов, parentTourId при наличии и дату. Сохранить имеющийся `text.original`; если самостоятельного старого оригинала нет, явно отразить это в происхождении, используя предусмотренный новым контрактом указатель на редакционный материал. Не создавать фиктивный Drive ID, donor URL или пометку `user_provided` ради прохождения проверки.

Это допустимое техническое дополнение для выполнения пункта о новых местах; оно не меняет модель Destination, публичные URL и связи. Пока поддержка не внедрена и не проверена, готовые материалы сохранить, а создание места отметить незавершенным. Исправления фото остальных дней продолжить.

## 10. Проверка и публикация

После обработки одного тура выполнить одну целевую проверку подготовленных данных:

- количество, порядок, обозначения и тексты обычных карточек дней сохранены;
- у каждой такой карточки есть хотя бы одно доступное декодируемое фото;
- все фотографии обычных дней попарно различаются, включая дополнительные изображения; проверены также прежние копии с разными именами;
- новые результаты прошли визуальную приемку и зарегистрированы;
- каждый новый кадр получен отдельным вызовом GPT Image, сохранен полным файлом и имеет запись фактического запроса; нарезанных коллажей, превью и скриншотов среди новых assets нет;
- фотографии и поля самостоятельных экскурсионных вставок сохранены;
- MD и JSON корректны, local media-пути существуют; у созданных мест согласованы identity, материалы, source-index и резерв;
- старые общие assets и глобальные соответствия улучшений сохранены.

Подготовить один логический commit: фотографии, изменения выбранного тура, журнал, реестр изображений и возникшие страницы мест с их данными. Перед записью учесть свежие изменения `main` в затронутых файлах. При конфликте сохранить чужую работу и уже сгенерированные кадры; не повторять весь проход.

Выполнить штатные Actions build/deploy. Одна штатная сборка уже проверяет схему и ссылки; дублирующая локальная полная сборка и общий обход сайта не требуются. Если расширялся контракт source-index, проверить именно новые допустимые случаи и сохранение запретов старых режимов. Исправить конкретные ошибки до объявления публикации успешной.

Пока штатная сборка или deploy выполняется, продолжать отслеживать его до результата с разумными интервалами. Если параллельный чат создал более новый commit, проверить, что он сохраняет подготовленные изменения, и использовать успешный deploy такого commit. Сам факт новой сборки или параллельного commit не является основанием закончить задачу до синхронизации таблиц.

Если отдельные слоты остались заблокированы после предусмотренных попыток, успешные независимые изменения разрешено опубликовать как частичный результат, сохранив все незавершенные слоты в журнале. Удаление дублей и создание журнала не заменяют оставшиеся генерации. До завершения прохода выполнить все доступные независимые задания выбранного набора; каждый непройденный пункт должен иметь конкретный блокер.

После успешной публикации одним адресным пакетом синхронизировать затронутые строки таблиц:

- основной реестр `1ZPptMdEcIDA3ZFMOQcFuc5jU88LJlFw9R4URCQSBmmc`, листы `Фото` и при создании места `Страницы`;
- очередь материалов мест `1yAaGtXfnGRvZFgTpJPjaJnBQyyKpi9eXcqLfLHymKpo`, лист `Места`, только опубликованные в этом проходе ID.

Для новой страницы места использовать действующий статус `Добавлена`, дату первой публикации и stable ID; колонку G `Принята` основного реестра не менять. В очереди мест поставить `Добавлено`, сохранить историю предоставленных материалов. Если таблица недоступна, сохранить точный пакет отложенных записей. Не запускать заново генерацию и не откатывать опубликованные фотографии; сообщить отдельный незавершенный этап синхронизации.

## 11. Короткий отчет пользователю

Сообщить:

- сколько туров выбрано, сколько исправлено, сколько уже соответствовало правилам;
- сколько лишних повторов удалено, сколько новых кадров создано взамен дублей и сколько для пустых дней;
- сколько отдельных вызовов генератора выполнено, сколько кадров принято и сколько результатов отклонено; числа брать из журнала вызовов;
- какие страницы мест созданы, со ссылками;
- подтвержден ли deploy и обновлены ли таблицы;
- какие точные туры/дни или места остались незавершенными и с какого ID продолжать.

Тур с пустым днем или оставшимся повтором не считать исправленным. Публикацию фото, публикацию нового места и синхронизацию таблиц учитывать отдельными этапами: один успешный этап не скрывает сбой другого.

При продолжении частичного прохода начать с сохраненных невыполненных слотов. Уже опубликованные удаления дублей и принятые отдельные кадры сохранять. Коллажи, отклоненные предыдущим чатом, не использовать ни как reference, ни как заготовку для нарезки.
