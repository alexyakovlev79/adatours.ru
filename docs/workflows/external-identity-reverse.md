# Ada Tours — обратная сверка внешних сайтов с adatours.ru

**Версия 1.0 · 19.10.2026.** Действующий режим: **источник → adatours.ru**. Старый RU-first план и frozen-партии №001–076 сохранены как доказательства и больше не используются как источник **новых** заданий.

## Цель и область

Получить точную таблицу связей между каждой действующей страницей **adatours.ru** и адресами на **трех** сайтах Анны: **adatours.com** и **brasiltours.ru** (проверенный `sameAs`) и **vipdeluxetravel.ru** (карта 301). Один RU canonical может иметь несколько внешних URL, даже несколько URL одного домена. Для контроля сохраняется и *обратная source-first таблица*: любая старая страница без пары остается учтенной, а не исчезает из RU-first свода.

Проверять **внешние URL, а не все 5000+ RU URL**. Единица очереди: нормализованный внешний исходный URL; исходный canonical, title/H1, snapshot, тип, source ID и HTTP-статус хранятся отдельно от RU кандидатов. RU цель брать из текущего production content, source-index и канонического маршрутизатора, а не только из названия/slug.

- **adatours.com:** тот же объект (Country/Place), та же программа тура/экскурсии, та же Organization либо строго одинаковые фильтр *и состав* каталога. Только тогда relation=`sameAs`. Публикация об объекте — возможный `subjectOf`, не `sameAs` продукта.
- **brasiltours.ru:** использовать старый сохраненный обход и миграционные `sourceUrl`; историческое равенство исходника не заменяет сверку *текущей* программы. Точное совпадение → `sameAs`. Сильный кандидат сам по себе не завершает проверку.
- **vipdeluxetravel.ru:** для каждого его исходного URL найти **один обоснованный RU адрес**, отвечающий содержанию и намерению пользователя; результат `redirect_ready` подходит для будущего 301. При отсутствии релевантной цели — `review`/отдельное решение о 404/410, не перенаправлять все на главную. Фактическое включение 301 на старом домене — отдельный этап с реальными HTTP-проверками.

**Не включать** vipdeluxetravel.com или другие домены в новую очередь без отдельного указания. Старые URL после фактического 301 сохранять в истории, но не выдавать редирект за активную самостоятельную sameAs-страницу.

## Команда «сверяй дальше»: один рабочий цикл, 50 URL, 60 минут

1. Чат читает эту инструкцию, `manifest.json` и текущий `state.json` **из staging**. Генерирует **один** `ownerId` и `token`, сохраняет их в своем чате. Вызов `runReverseIdentity(tools,{action:"claim",ownerId,token,limit:50})` из `scripts/reverse-identity-remote.mjs` выбирает до **50 еще не закрытых URL одного источника**. Приоритет **VIP → EN → Brasil**, пока VIP pending_discovery — EN. Два параллельных чата выбирают разные URL посредством CAS. Ни один чат не захватывает следующую партию до завершения своего цикла.
2. Claim живет **60 минут**, в `state.records[url]` стоит `leased` с `ownerId`, `token`, `batchId`, `claimedAt`, `expiresAt` и `generation`. При потере ответа повторить **тот же ownerId/token**, сначала искать свои незавершенные leases, а не создавать новый резерв. Продление `renew` только собственных непросроченных ключей. Истекшее может забрать другой чат, но сохраненный результат не проверяется повторно.
3. Каждую страницу сверять с RU по полному смыслу; учитывать точный product ID, страну/место, маршрут/дни, программу, условия. Сохранить источник доказательства/цитируемые факты в самом result, без выдуманного совпадения. `matched_exact` / `redirect_ready` требуют действительного RU canonical и evidence. Отсутствие доказанной пары — `checked_no_confirmed_pair`, **не утверждение об отсутствии английского/старого URL**. Неадекватная неоднозначность — `review`, технический сбой — `retry`.
4. После **каждых 10** URL: `runReverseIdentity(tools,{action:"complete",ownerId,token,batchId,part:1..5,results:[...]})`. Диспетчер атомарно записывает отчет `results/<batchId>-part-N.json` и переводит только эти URL из `leased` в итоговые статусы одним CAS-коммитом staging. Повтор идентичного `part` возвращает `already_saved`; после сбоя продолжить только необработанные свои keys. Нельзя обновлять чужой или просроченный claim, пользоваться force или менять старые монолитные JSON.
5. После 50 или доступного остатка остановиться и выдать счетчики по статусам, исходному домену, SHA и еще ожидающим внешним URL. Отдельная ошибка не обнуляет 10 предыдущих. Если кончились pending, но есть review/retry, отчет должен явно об этом сказать.

**Статусы:** нет записи → `pending`; `leased`; `matched_exact` (sameAs); `redirect_ready` (готовая карта 301); `checked_no_confirmed_pair`; `review`; `retry`; `excluded` (robots/технические дубли с доказательством). Review/retry вынести в повторную адресную очередь, не приписывать URL другой странице. Все обновления lease/status — optimistic CAS GitHub, максимум три попытки. Публикация production и SEO-редактура не входят в работу сверяющего чата.

## Конечная RU-first таблица и публикация результатов

Отдельный мастер сводит из подтвержденных результатов **source-first журнал** (исходная страница, статус, RU цель, evidence, timestamp) и **RU-first представление** (RU canonical и три доменные колонки, допускающие несколько источников). Синхронизировать Google Sheets по source URL и RU canonical/stable ID, **не по прежнему номеру строки**. При сбое Sheets повторить только синхронизацию, не claim/сканирование. `sameAs` выпускать в существующий JSON-LD только из `matched_exact`, с корректным типом сущности и проверкой живой страницы; `checked_no_confirmed_pair` не публиковать. Файл для применения 301 на VIP-домене — **только** `redirect_ready`: old URL → конкретный new URL → HTTP 301; сохранение путей и исключение цепочек/петель проверять при отдельном развертывании. **Само выставление статуса не включает редиректы.**

Приемка полноты — сравнение списка всех обнаруженных URL каждого старого домена с состояниями, отдельные числа `confirmed/review/retry/pending/leased`, дата полноты sitemap/CMS; рост RU до 5227 и выше сам по себе очередь не увеличивает. В начале нового дня допускается только инкрементальное дополнение внешних URL, без перенумерации и сброса готовых evidence.

## Точный запуск в ChatGPT Code Mode

Один раз за чат: загрузить рабочий модуль **из текущего main**, создать owner/token и удерживать их до закрытия партии.

~~~javascript
const repo='alexyakovlev79/adatours.ru';
const path='scripts/reverse-identity-remote.mjs';
const f=(await tools.mcp__GitHub__fetch_file({repository_full_name:repo,path,ref:'main'})).result;
const src=f.content||(await tools.mcp__GitHub__fetch_blob({repository_full_name:repo,blob_sha:f.sha})).result.content;
const reverse=new Function(src.replace(/^export /gm,'')+';return runReverseIdentity;')();
const ownerId='reverse-'+Date.now().toString(36)+'-'+Math.random().toString(36).slice(2,14);
const token='lease-'+Date.now().toString(36)+'-'+Math.random().toString(36).slice(2,14);
const claim=await reverse(tools,{action:'claim',ownerId,token,limit:50});
text(claim); // Сохранить exact ownerId/token/batchId в текущем чате. Не генерировать их повторно.
~~~

После исследования первого десятка:

~~~javascript
// Те же reverse, ownerId, token и claim.batchId предыдущего вызова.
// На каждую исходную страницу ровно один завершенный результат.
const saved=await reverse(tools,{action:'complete',ownerId,token,
  batchId:claim.batchId,part:1,results:[
    {sourceUrl:'https://adatours.com/example',status:'matched_exact',
     ruUrl:'https://adatours.ru/example/',evidence:['точная ссылка/снимок и проверенные идентичные факты'],note:'тот же продукт и программа'}
  ]});
text(saved);
~~~

Пример above описывает **формат вызова**, не фактическое соответствие и не разрешение использовать выдуманный URL. Отправлять реальные адреса только из своего claim. Для остальных частей `part:2..5`; каждый part содержит от 1 до 10 новых source URL, в обычной полной партии — по 10. При необходимости `renew` с тем же owner/token/batchId; `release` отдает свои неразобранные URL обратно в очередь. Для диагностики без изменения очереди — `action:'status'` или `claim` с `dryRun:true`. Для спорных/сбойных задач отдельно `claim` с `lane:'review'` или `lane:'retry'`. Старые миграционные кандидаты считать подсказкой, а не `matched_exact` без исследования. После каждой готовой десятки выводить короткий факт сохранения и продолжать до конца выбранных 50, не ждать «дальше».

**Активация нового внешнего инвентаря:** добавлять его URL в versioned main и ту же точную статическую очередь `external-identity/staging` через безопасный CAS; не менять существующие source URL и завершенные статусы, не перезахватывать старые задачи. После новой инвентаризации VIP обновить `discoveryStatus` с `pending_discovery` на `partial` или `complete` только при реальном наличии source URLs и доказательств.
