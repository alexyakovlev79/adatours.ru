# Schema.org / GEO — отдельная очередь данных (16.10.2026)

Команды **«собирай данные»** и **«публикуй данные»** относятся к `docs/workflows/schema-geo-knowledge.md` (v2), а не к написанию SEO-статей. Код CAS: `scripts/schema-geo-core.mjs` и `scripts/schema-geo-remote.mjs`. Источник статусов/резервов — **только** `schema-geo/staging`, `data/geo-knowledge/queue.json` + `state.json`; Google Sheets «GEO очередь/результаты/публикации» — зеркало. **Один чат «собирай данные» обрабатывает до 50 GEO-паспортов** (`manifest.collectorChatTarget: 50`), автоматически последовательно беря до пяти резервов по максимум 10 задач (`manifest.batchSize: 10` на один claim). Резерв действует 90 минут; сначала сохранять все результаты текущей десятки, затем тем же owner/token получать следующую, без команды «дальше». Подтверждённые результаты сохраняются по одному CAS-коммиту; main/build/deploy сборщик не трогает. Реально опубликованным результат становится после успешного Pages deploy: независимый `geo-finalize.yml` подтверждает исходный SHA или проверенного потомка с неизмененными GEO entities/receipt, даже если мастер-чат закрыт; неуспешный deploy не дает `PUBLISHED`. Существующие внешние identity/EN-реестры и единый JSON-LD renderer сохраняются. Старт с 24 стран; следующие этапы открывает мастер после пилота по manifest.maxStage. Готовый код запуска через подключенный GitHub и все процедуры — в workflow.

**GEO-решения с 16.10.2026:** для самого объекта страницы, внешнего QID / `sameAs`, координат и остальных полей сборщик сначала уточняет данные через интернет, затем принимает наиболее вероятное соответствие при оценке **от 70% включительно**. При меньшей вероятности конкретное поле пропускает; паспорт становится `READY`, если идентичность самой страницы набирает от 70%. Новые результаты используют `decisionPolicy: probability-70-v1` и служебные `assessments` с доказательствами. Для составных мест определять основной референт и допускать его QID/`sameAs` по тому же порогу. Режим и требования зафиксированы в §3.2.1 `docs/workflows/schema-geo-knowledge.md`. Старые REVIEW не изменять без повторного исследования и нового result.


**GEO-мастер (16.10.2026): ВСЕ `READY` одним релизом, лимит 20 удален.** По команде «публикуй данные» выполнить один короткий Code Mode вызов по §4.1 `docs/workflows/schema-geo-knowledge.md`: `scripts/schema-geo-publisher.mjs` только захватывает все `READY` и пишет `data/geo-knowledge/dispatch.json` вместе с блокировкой CAS. **Не загружать каждый результат через чат**: ограничение количества GitHub-вызовов делает такой способ ненадежным. Массовые файлы локально обрабатывает `.github/workflows/geo-publish.yml` / `scripts/schema-geo-ci-publisher.mjs`, формируя один main-коммит и затем явно вызывая существующий Pages `workflow_dispatch` (push от `github.token` сам не запускает deploy). `.github/workflows/geo-finalize.yml` закрывает `DEPLOYING` после полного успешного Pages run с exact receipt/SHA. Прежний `PUBLISHING` продолжать по его batchId/ownerId через `dispatchPublication`, не резервировать повторно. Не ждать Pages в чате, не запускать местный build/дублирующие тесты, не делать вторых деплоев ради синхронизации Google Sheets. У исследователя за **один claim** максимум 10 задач; за **один чат** цель 50 через последовательные claim, с сохранением каждого результата.


## Обязательный GEO-сбор при создании новой сущности (16.10.2026)

При первом появлении активного MD новой Country, Destination, Tour или Excursion **в том же чате и в той же логической задаче** выполнить адресное «собирай данные» по §3.4 `docs/workflows/schema-geo-knowledge.md`. После единого content commit доказать новизну файла и исследовать конкретный ID с порогом 70%; `scripts/schema-geo-new-object.mjs` сохранит immutable паспорт, очередь и состояние в staging и **сразу** обновит обе строки Google Sheets (`GEO очередь`, `GEO результаты`) одним batch. `geoSheetSync: SYNCED` обязателен для завершения операции; `PENDING` при ошибке Sheets требует адресного повтора без повторного исследования. Статус `READY` не означает публичный `PUBLISHED`: таблицу `GEO публикации` и JSON-LD обновит будущий мастер. Отдельный GEO-проход не требует второго content commit или деплоя; пустые резервы мест и правки старых MD не запускают его. При добавлении тура исследовать и все созданные в том же commit самостоятельные Excursion/Destination, каждый под своим ID. Массовые gates сохраняются для старых задач.

# Ada Tours: рабочий вход

**SEO/GEO для multi-country × интерес (16.10.2026).** Если выбран URL `/multi-country/<страны>/interests/<интерес>/` или `/multi-country/interests/<интерес>/`, обязательна предметная методика `docs/workflows/seo-geo-registry.md`, §9.5.1: полезная статья о конкретных странах **через призму одного интереса**. Разобрать реальные тематические занятия по маршруту, сезонность, межстрановые ограничения и выбор действующего тура; не склеивать типовые тексты и не предполагать, что интерес представлен в каждой стране. Очередь, права staging-писателей и отдельная публикация SEO-мастером сохраняются.

**SEO/GEO v3.6 — 10 циклов по 3 статьи.** Команда «пиши SEO» запускает **до 10 последовательных троек без «дальше»**, максимум 30 URL на чат. На один цикл: до 3 атомарных claims на 60 минут по `docs/workflows/seo-geo-fast-claim.md` v1.5 → подготовить три `approved` MD → **один** CAS content-коммит всех статей + provenance + `work: prepared` + снятие только собственных claims в `seo-geo/staging` → **одним пакетом** J/K/M в Google Sheets по каноническому URL → автоматически следующая тройка. Не занимать будущие тройки заранее. Фазы 01–04 пропускать по неизменным опубликованным SHA, затем 05 → 06 → 07, `draft` перед `queued`. Claim захватывается одним `GitHub.update_file` по SHA только `claims.json`, не трогая мегабайтные фазовые JSON. Существующие живые 90-минутные claims не сокращать; новые/продленные по новому регламенту — 60 минут. При сбоях восстанавливать точный runId/cycle/lease/commit, не делать второй коммит; Sheets — зеркало. Публикацию в `main` выполняет только мастер.

**SEO/GEO — один commit на тройку, затем Google Sheets.** Весь набор текущего цикла фиксировать единственным удаленным CAS-коммитом `seo-geo/staging`: три утвержденных Markdown-файла, нужные provenance, три адресных `work: prepared`, снятие своих трех claims. Никаких commit по одной статье или отдельного status-коммита. Затем одной адресной операцией записать в лист «SEO-GEO тексты» по URL (E) `J=Ждет публикации`, `K=articlePath`, `M=общий SHA тройки`; если Sheets недоступен, сохранить точный отложенный пакет `PENDING` и продолжить, без повторного коммита. Писать следующий цикл сразу, пока не завершены 10 или очередь пуста. CAS-конфликт — максимум два адресных повтора без force; старые активные claims других авторов не менять. Только SEO-мастер публикует в `main` после штатного Pages deploy.

**SEO/GEO: фильтр перед публикацией (16.10.2026).** При `публикуй SEO` мастер проверяет только уже загруженные `prepared` MD: статус, canonical URL/путь и начальный H2. Ошибочные URL остаются в staging, остальные входят в один main-commit. При Work/shell доступен одноразовый пакетный `src/lib/seo-geo-release-gate.mjs` и `scripts/check-seo-geo-release.mjs`, который дополнительно проверяет FAQ; при Code Mode — готовый in-memory JS из `docs/workflows/seo-geo-registry.md` §8.3. Новых GitHub-запросов, Actions, отдельных preflight/build и сканирования старых статей нет. Писатель проверяет H2 на своем готовом тексте перед staging-коммитом, без инструмента.

**Дополнение к написанию SEO/GEO-статей:** в новых текстах и явно заказанной редактуре проектировать обычные таблицы под ~300–340 CSS px мобильной ширины (как правило, 2 компактные колонки, не 3 длинных текстовых); подробности выносить за таблицу. Расставлять **контекстные внутренние ссылки прямо при содержательных упоминаниях** опубликованных мест, экскурсий, туров и подходящих каталогов «страна + интерес»; **в перечислениях давать ссылку на каждый доступный объект**. Нет лимита «одна ссылка на URL» или «1–3 ссылки на раздел»: полезные повторные переходы разрешены; избегать только бессмысленных дублей рядом и ссылок на архив, резерв, пустую подборку или себя. Tour заранее указывает все канонические Destination ID маршрута. Для нового названия сначала сопоставить страну, имя и aliases в едином каталоге мест. Однозначно существующее место переиспользовать; только действительно новое — зарезервировать и сразу связать stable ID. Неоднозначность сообщить с конкретными кандидатами, не создавать дубль. Каждое место принадлежит одной стране; две стороны Игуасу — разные Destination.

Резерв не создаёт Destination MD, текст или фото и не публикует пустую страницу. Материалы места предоставляет Анна; описание экскурсии не становится текстом места автоматически. При заполнении сохраняются ID и будущий URL, готовые связи активируются сами. У Excursion основной `destination` задает URL; `relatedDestinations` хранит другие подтвержденные посещаемые места и дает обратные связи без переезда экскурсии. Известная экскурсия получает обе группы ID из готовой entry без нового поиска. Недостающие самостоятельные Excursion создаются вместе с туром и сразу используются через `excursionRef`.

Canonical URL вычисляет `src/lib/routes.ts`; старые плоские URL туров/экскурсий — только aliases. В туре страны основных маршрутов показаны одним уровнем через `·`, каждая ссылка отдельно. Не записывать ложную последовательность вложенных стран в breadcrumbs.

Явная глобальная миграция URL 02.10.2026 один раз меняет публичные slug; после неё использовать только закреплённые текущие поля. Все старые пути остаются redirect aliases навсегда. Архивные source URL, Drive originals и пути медиа не изменять. Языковые версии сейчас не создавать; будущие `/en/`, `/de/`, `/ka/` используют те же stable ID и английские пути объектов.

Публичные вводные и три полные словоформы каждого интереса — `src/data/interest-copy.json`; текущие количества — только расчет из активных туров. `/interests/` сортируется по количеству. География Theme — full-bleed `DestinationBand`: обложка первого тематического тура только по показанной стране, иначе `Country.hero`. Multi-country hero для фона страны не используется; географию самого кадра отдельно не определять. Распределение максимум 7 стран снизу вверх, без повторов Tour. Полный контракт: `docs/workflows/interests.md`. Hero каталога «интерес + страна» берется из `Theme.hero`. Одну нижнюю форму всегда создает `BaseLayout`; в дочерних страницах передавать `leadTitle`/`leadEntityId`, не дублировать `<LeadForm>`.

## Обязательное правило: новые медиа только напрямую в S3 (09.10.2026)

**Никогда не записывать в Git новые или изменённые бинарные файлы** из `public/media/` — WebP, JPEG, PNG, MP4, WebM и прочие. Все старые файлы в Git и историю коммитов сохранить, не удалять. GitHub Pages продолжает принимать только HTML/CSS/JS/SEO; медиа отдаются по `https://img.adatours.ru/media/...`.

ChatGPT Work при любой новой генерации/улучшении изображения или видеоролика использует `docs/workflows/direct-s3-upload.md`: локальный файл вне Git → одноразовый X25519 сеанс → зашифрованный временный OIDC IAM-допуск → прямой S3-upload → проверка SHA-256 → текстовый receipt в `src/data/media/direct-s3-uploads.json` → commit MD/JSON/реестров без бинарного файла. `hero.src` и прочие поля содержат прежний логический путь `/media/...`. Новым файлам всегда новое версионированное имя, S3-объекты не перезаписывать. GitHub Actions проверяет ledger и наличие файла до публикации.

Если прямой upload из конкретного чата недоступен, **сохранить задание и назвать блокер; не возвращаться к Git binary fallback, не связывать неподтвержденный S3 путь и не утверждать, что фото опубликовано**. GPT Image и финальные WebP требуют Work с локальным файлом и сетевым доступом, у GitHub connector нет команды прямой передачи бинарного файла в Object Storage.

Для выборочных видеофонов отдельного Country/Tour hero предусмотрена загрузка MP4/WebM точно так же, но проигрывание включается только в отдельной задаче. Оригинальный WebP-постер остается обязательным для LCP, SEO, мобильных устройств и `prefers-reduced-motion`. Подробнее: `docs/MEDIA_DELIVERY.md`.
