# Мастер: сведение и публикация мобильных hero

Работники руководствуются `WORK_ADATOURS_MOBILE_HERO_SWARM_20261023.md`. Этот мастер — отдельный запуск после подготовки всего роя или явно выбранной части. Не переносить рабочую ветку целиком в main: в ней есть резервы, а main параллельно меняется.

1. Зафиксировать head рабочей ветки и актуальный head `main`. Получить завершенные пакеты, результаты и подтверждения одного снимка ветки. Неготовые/`review`/`retry`/`stale_source` не считать опубликованными. Для повторной работы с нерешенным пакетом диспетчер имеет `requeue` с `expectedGeneration` и причиной; принятые `ready` сохраняются. Новые или замененные герои требуют отдельной новой версии очереди, не изменения замороженных заданий.
2. Построить свежую инвентаризацию **актуального main**, используя его успешный Pages-артефакт с точным commit и контрольной суммой либо чистую локальную сборку. `scripts/mobile-hero-inventory.mjs --build --write /tmp/current-main-hero.json` выполняет Astro-сборку; доступны `--dist`, `--source-commit`, `--artifact-run`, `--artifact-sha256`. HTML — язык разметки страниц. Не использовать исходный frozen-инвентарь как доказательство нынешнего состояния.
3. В checkout рабочей очереди запустить коллектор с **актуальными main** реестром и upload ledger, а не их старой копией из feature-ветки:

```sh
node scripts/mobile-hero-swarm-collect.mjs --current-inventory /tmp/current-main-hero.json --current-main ТОЧНЫЙ_40_HEX --registry /tmp/main-mobile-hero-registry.json --ledger /tmp/main-direct-s3-uploads.json --out-dir /tmp/mobile-hero-release
```

Коллектор сверяет неизменяемый blob задания, завершение пакета, поколение резерва, результат, фото, точную страницу, профиль, геометрию и ручной фокус. Скачать актуальный оригинал и проверить SHA-256 перед публикацией обязательно. Каждый выбранный мобильный файл заново скачивается и проверяется по размеру, типу и SHA-256; подтверждения лишних объектов не попадают в общий реестр. Если часть использований одного фото изменилась, их пропустить, сохранив остальные валидные использования. Коллектор сам ничего не коммитит и не публикует.

4. Изучить report: отдельно показать выбранные использования, нерешенные источники, устаревшие привязки и ошибки проверки. Готовый результат — `files.json` и текстовые `src/data/media/mobile-hero-registry.json`, `src/data/media/direct-s3-uploads.json`, `collection-report.json` в staging-каталоге. Общие реестры объединяются без потери прежних записей, конфликт одного ключа с разными байтами блокируется. Реестры пилотов остаются; runtime выбирает generic crop по точной странице, исходнику, профилю и ручному фокусу, затем сохраняет старый fallback.
5. На свежем main проверить необходимые тесты, отсутствие новых бинарных файлов в Git, реестр загрузок, сборку. Затем одним атомарным текстовым коммитом перенести **только выбранные файлы**, с проверкой ожидаемого head. Если main изменился, получить новую текущую инвентаризацию/реестры и повторить адресное сведение; не затереть параллельные работы.
6. Дождаться успешного build и GitHub Pages deploy. Проверить публичные страницы разных профилей, выбор мобильного `<source>` до479пикселей, горизонтальный оригинал выше порога, фото-запасной показ с видео, лица и короткий `photo-lead`. Только после успешной публикации записать отдельный `publication.json`: точные packet/submission IDs, source/result SHA, commit, Pages run, URL, время и действительно опубликованные использования. Состояние `ready` работника не переименовывать в `published` до этой проверки.

Массовая обработка не является новым экспериментом скорости: дополнительных замеров PageSpeed Insights (сервис Google для проверки скорости страниц) этот рой не запускает. Нельзя объявлять выигрыш скорости по одному уменьшению веса файлов.
