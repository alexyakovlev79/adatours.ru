# Ada Tours — канонические экскурсии внутри тура

Версия: 2.1 · 2026-10-02 · Репозиторий: `alexyakovlev79/adatours.ru`, ветка `main`.

Эта инструкция заменяет `ADA_TOURS_TOUR_EXCURSION_LINKING_WORKFLOW_v2.0_2026-10-02.md`. Применяется вместе с `docs/workflows/tours.md` к созданию или нормализации одного выбранного тура. Для добавления известной экскурсии из ее собственного источника использовать `docs/workflows/excursions.md`; очередь нормализации туров для такой задачи не нужна.

## 1. Область работы и источники

Общие правила и завершение задачи: `docs/workflows/master.md`. Индекс источников: `data/source-index/index.json`; выбранная запись `entry`: `data/source-index/entries/<entityId>.json`. Канонический каталог мест: `src/data/catalog/destinations.json`.

Взять выбранный тур из текущей очереди или прямого запроса пользователя. Если продолжается отдельная серия нормализации, использовать выбранную незавершенную запись `docs/TOUR_EXCURSION_MAPPING_REGISTRY.md`, а не заново обрабатывать закрытые туры. Читать полностью только целевой Tour MD и его точные готовые источники.

Открыть закрепленный текст по `entry.text.selected.driveId` / `url`; `selected.name` и `selected.kind` указывают файл и вид источника. Из выбранного текста взять формулировки, порядок дней, самостоятельные вставки и условия; фотографии — из `entry.media.images` как `{url, role, order, alt}`. Повторная обязательная сверка двух полных текстов не нужна. Если конкретное сопоставление уже выполнено и сохранено, повторять его после обрыва не нужно.

Для сопоставления экскурсии использовать компактный `data/source-index/catalogs/excursions.json` и записи только найденных кандидатов в `data/source-index/entries/`: ID, название, source URL, `countryIds`, `destinationIds` и выбранный текст продукта. Не обходить сайт донор, интернет или тексты всех остальных туров. При конкретной неоднозначности допустимо прочитать источники только этих кандидатов.

## 2. Что становится самостоятельной Excursion

Один раз просмотреть целевой маршрут целиком: обычные дни, `text`, `contentBlocks`, вложенные секции и фотографии. Найти самостоятельные экскурсионные модули как между днями, так и внутри них.

Основания: отдельный блок с названием и описанием; явно самостоятельный продукт с собственным маршрутом, механикой, длительностью или условиями; соответствующая отдельная source Excursion; явное подтверждение в original/V2. Само наличие текста в `contentBlocks` еще не делает его экскурсией.

Не создавать сущность из проходного упоминания достопримечательности, неотделимой части основной программы дня, строки highlights, included, FAQ, примечания или подписи к фотографии. Разные продукты у одного объекта не сливать: например, канатная дорога и самостоятельный треккинг — разные экскурсии.

## 3. Выбрать или создать каноническую экскурсию

Для каждого самостоятельного модуля выполнить один из трех вариантов:

| Состояние | Действие |
|---|---|
| Подходящий production Excursion MD уже есть | Использовать его stable ID и текущий канонический текст/hero |
| Экскурсия есть в реестре, MD еще нет | Сразу создать ее MD из собственного точного источника по `docs/workflows/excursions.md` |
| Отдельной исходной экскурсии не существует | Сразу создать канонический Excursion MD из утвержденного самостоятельного блока целевого тура |

Отсутствующую экскурсию нельзя оставлять локальной карточкой, только резервировать ее ID или откладывать на отдельный будущий проход. Ее реальный MD должен входить в тот же подготовленный commit, что и использующий ее тур.

При совпадении нескольких кандидатов проверить их географию, механику и известные duration/route. Совпадения одного слова в названии недостаточно. Если соответствие доказать нельзя, сохранить конкретный вопрос в `REVIEW`; не выбирать случайный ID и не создавать вероятный дубль.

## 4. Новая экскурсия из блока тура

Взять из блока title, body, географию, фото и только явно указанные price, duration, format, language, included/notIncluded и условия. Не дополнять продукт новыми услугами, расписанием, трансфером или ограничениями. Короткий обязательный `lead` составить из того же текста без новых фактов.

Stable ID и slug должны обозначать экскурсию и не зависеть от конкретного тура. Взять уже выделенные значения из индекса, если они есть. Для действительно нового продукта создать один уникальный ID, добавить его `data/source-index/entries/<id>.json` с точным родительским источником и зарегистрировать в существующем реестре. В том же prepared commit обновить `index.json` и `catalogs/excursions.json`, чтобы следующий тур мог переиспользовать эту экскурсию. При доступном Node это делает `node scripts/sync-source-catalogs.mjs` из готовых entries без сети; при работе через GitHub tools добавить только запись нового ID в указанные каталоги. Обычная публикация уже известной сущности не требует обновления этих каталогов.

Текущие обязательные поля Excursion: `id`, `locale`, `slug`, `status`, `title`, `country`, `lead`. Подтвержденные основное место и его название записать в `destination` и `destinationName`; другие явно посещаемые места — в `relatedDestinations`. Основное место задает URL, второстепенные дают обратные связи без его изменения. Для уже готовой экскурсии они берутся из `entry.relatedDestinationIds` без нового поиска. Остальные поля и типы — в `src/content.config.ts` и `docs/workflows/excursions.md`.

Canonical URL новой экскурсии вычисляет `src/lib/routes.ts`: при месте — `/<destination-country-slug>/<destination-slug>/<excursion-slug>/`, без места — `/<country-slug>/excursion/<excursion-slug>/`. Используется страна самого места, даже если продукт начинается в другой стране и место пока только зарезервировано. Иерархия URL не меняет `src/content/excursions/<slug>.md`. В новую entry и компактные каталоги записать вычисленный адрес, не старый плоский alias.

Если собственного legacy source не было, `sourceUrl` опустить; `null` в этом поле схема не принимает. `sourceSnapshot` может содержать подтвержденную ссылку на источник блока тура; отдельный source Excursion не выдумывать. Служебное происхождение из блока тура сохранить в mapping registry и колонке `Источник / комментарий`, а не в публичных `notes`. Намеренно пустой `destinationIds` у существующей канонической экскурсии допустим и не требует поиска места.

## 5. Места тура и экскурсии берутся из готового каталога

Все места выбранной программы сопоставить с единственным `src/data/catalog/destinations.json`: записи содержат `{id, name, slug, countryId, countrySlug, url, sourceUrl, aliases?}`. Взять уже известные ID из `entry.destinationIds`; для новых названий сопоставить имя и aliases в пределах подтвержденной страны. Записать полный набор канонических ID в `Tour.destinations` независимо от наличия MD мест. Основные места обычного маршрута записать также в `Tour.routeDestinations` / `entry.routeDestinationIds`. Место самостоятельной экскурсии, которая только предлагается как факультативная и не входит в основной маршрут, остается в `destinations`, но не добавляется в `routeDestinations`. Уточнение сохранить в записи источника тура того же commit. Порядок и формулировки маршрута сохраняются в `route` и `itinerary`.

Для каждой новой экскурсии также использовать канонический будущий ID в `destination`; известное название — в `destinationName`. Отсутствие Destination MD не требует создания места и не препятствует публикации тура/экскурсии. После создания этого места готовые связи активируются автоматически. Создающий место чат не должен повторять это уточнение или перечитывать тур.

Одно место принадлежит одной стране. Если тур посещает обе стороны Игуасу, в `destinations` входят два разных ID: `destination_brazil_iguacu` и `destination_argentina_puerto_iguasu`; `countries` отражает соответствующие страны программы. Сторону определять по явной программе выбранного тура, а не по общему названию «Игуасу».

Если после сопоставления подтвержденное место действительно новое и однозначное, выполнить резерв по `docs/workflows/destination-reservations.md`: добавить stable ID/будущий URL в каталог, происхождение в очередь и связь в текущую сущность. Destination MD, описание и фото не создаются. Материал экскурсии не становится автоматически статьей о месте. Если совпадений несколько либо страна/смысл названия не определены, сообщить конкретную неоднозначность и кандидатов, не добавляя вероятный дубль. Не просматривать все туры и не исправлять массово старую географию.

## 6. Как заменить локальный модуль

Отдельный элемент между днями имеет следующий вид:

```yaml
- excursionRef: excursion_rio_caipirinha_masterclass
  places:
    - Рио-де-Жанейро
```

Он не имеет `day`; рядом не остаются локальные `title`, `text`, `images` или hero этой экскурсии. `Itinerary.astro` получает название, текст и фотографию из канонического Excursion MD.

Если самостоятельный модуль находился внутри номерного дня, вынести его в отдельный `excursionRef` сразу после этого дня, перед следующим. Сохранить порядок нескольких модулей. Удалить только перенесенные дубли текста/фото и ставшую бессмысленной фразу-перечисление. Собственную программу, факты и номер дня сохранить.

Условия именно этого тура, которые не являются общими свойствами экскурсии, сохранить в подходящих полях тура. Канонизация не должна удалять оплаченный состав услуг, исключения или особые условия конкретной программы.

Схема также поддерживает существующие `contentBlocks: [{type: excursion, excursionRef: ...}]`; рекомендации умеют читать такие ссылки. Это не основание оставлять самостоятельный локальный экскурсионный текст без ссылки. Для новой самостоятельной вставки использовать описанный выше отдельный элемент.

## 7. Фото и автоматические рекомендации

Для новой Excursion брать ее собственный закрепленный raw source hero из `entry.media.images`; если она создается из блока тура, использовать закрепленную за этим блоком фотографию. Разрешены `https://brasiltours.ru/image/...` с исходным расширением; `/image/cache/` запрещен. Raw URL уже подготовлены в записи; повторно восстанавливать их или искать другие источники не нужно.

Фотографии не скачивать, не улучшать, не переносить в `public/media` и не искать замену. Уже существующий улучшенный hero канонической экскурсии сохранять. Локальные фотографии старой карточки тура удаляются из ее данных вместе с дублирующим текстом; сами общие файлы ассетов без отдельной задачи не удалять.

Если у канонической Excursion уже задано `imageTextAlign: left | right`, сохранить его. Сторона текста поверх ее фото берется у Excursion, а не у тура. Создание связи не назначает значение автоматически и не перемещает обычный текст программы вне изображения.

Блок других экскурсий вычисляется из `excursionRef` в общих турах. Одна экскурсия учитывается один раз на тур; текущая исключается; сортировка по числу общих туров, затем русскому title; максимум 10. Отдельные списки `relatedExcursions` не создавать и веса вручную не пересчитывать. Отсутствие пересечений означает отсутствие блока.

## 8. Одна сборка и одна публикация

При подготовке целевого тура один раз посчитать самостоятельные модули `N`. Им должны соответствовать `N` вставок `excursionRef`; все нужные Excursion MD существуют или создаются в этом же изменении, локальные дубли самостоятельных модулей удалены. Сохранить число и порядок обычных дней, последовательность вставок и условия тура. Это часть работы с выбранным текстом, а не отдельный повторный аудит.

Подготовить один логический commit по `docs/workflows/master.md`: целевой Tour MD, новые Excursion MD, возникшие резервы мест, уточненные записи источников и необходимые записи текущего mapping registry. В registry записать фактическое соответствие `tour_id`, `excursion_id`, позицию между днями и результат канонизации. Статус канонизации данных не является доказательством уже завершенного deploy.

Использовать один успешный Actions build этого commit. Команда `npm run build` уже включает offline-проверку схемы, references и запрета `/image/cache/`; канонические ID будущих мест допустимы, отсутствующий Excursion MD — ошибка. Дождаться успешного deploy. Отдельную локальную сборку, дополнительную проверку опубликованных страниц или повторный пересчет рекомендаций не запускать.

После успешного build/deploy один раз пакетно обновить только затронутые строки Google Sheets: целевой тур и созданные экскурсии. Реестр: `1ZPptMdEcIDA3ZFMOQcFuc5jU88LJlFw9R4URCQSBmmc`, лист `Страницы`. E — `Уникализировано` для тура с опубликованным V2 и `Добавлена` для новой экскурсии; F — дата первого добавления, H — stable ID, I — служебный комментарий; A/B/C/D — точные production URL, source URL при наличии, тип и название. Для новой экскурсии J/K/L заполнить точными указателями из ее записи источников. G (`Принята`) не менять; дату ранее опубликованной страницы сохранять. Отдельные commit/deploy для каждой новой экскурсии не нужны.

Сообщить результат выбранного тура и созданные экскурсии. Если связь неоднозначна или машинная проверка падает, исправить конкретную причину либо сохранить точный `REVIEW`; не объявлять тур полностью связанным. После прерывания продолжить текущую стадию, не повторяя закрытые сопоставления.

Новые резервы дополнительно отражаются в отдельной очереди материалов Анны по stable ID, одним пакетом затронутых строк. Это запрос самостоятельного материала места, а не публикация пустой Destination и не отдельный commit/deploy.
