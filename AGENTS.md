# Ada Tours: единая точка входа для ChatGPT, Codex и других агентов

**Назначение этого файла — маршрутизация, а не копирование регламентов.** При работе над сайтом агент сначала определяет **что меняется** и **какой результат требуется**, затем читает **актуальный профильный workflow**. Сами процедуры, команды, модели данных, условия доступа, тесты и критерии публикации находятся в документах по ссылкам ниже. Если процесс изменился, обновляется профильный документ; этот указатель меняется только при изменении адреса/назначения инструкции.

## Порядок входа: для любой задачи

1. Работай с `alexyakovlev79/adatours.ru`. Зафиксируй актуальный SHA нужной ветки: по умолчанию `main`; для явно назначенного роя или отдельной feature-ветки — указанную ветку. Читай инструкции **из той же версии**, а не из предыдущих разговоров, старых вложений Project или исторических примеров.
2. Классифицируй действие: поиск/правка данных, добавление сущности, медиа, переработка программы, изменение механизма, миграция, SEO/GEO, параллельное задание. Найди ниже **маршрут к инструкции**, открой ее текущую версию и следуй ее ссылкам на зависимости. Если задача комбинированная, применяй необходимые регламенты в установленном ими порядке; не обрывай задачу после первой операции.
3. Определи точные затронутые файлы по актуальным данным репозитория. Для сущности сначала используй stable ID / exact `contentPath`; не выводи имя файла из URL или названия. Для неизвестного раздела ищи место использования в текущем коде/данных и владельца данных; отсутствие готового примера ниже не означает отсутствие маршрута.
4. Перед тяжелой работой проверь возможности **всей цепочки**: GitHub read/write или Issue/PR, доступность исходного файла, компьютер/Node/HTTPS для бинарных медиа, разрешения на merge/публикацию. Найди предусмотренный в соответствующем workflow путь для доступных полномочий. Не заключай «невозможно» только потому, что недоступен один способ.
5. Выполняй минимальное адресное изменение. Сохраняй уже полученные файлы, результаты и receipts при сбое; не повторяй генерации или внешние действия без проверки. Отличай `подготовлено`, `загружено в S3`, `PR`, `commit/merge` и **подтвержденный Pages deploy**. Публикация подтверждается только фактическим успешным запуском.

## Где находится «ЧТО»: текущие данные и код

- Публикуемые сущности: `src/content/` (`countries`, `destinations`, `tours`, `excursions`, `people`, `themes` и др.); действительная схема полей — `src/content.config.ts`. Exact entry / исходники — `data/source-index/entries/` и каталоги. Для изменения конкретного объекта **используй именно его текущую запись**.
- Данные, которые не являются Content Collection: `src/data/` (например, `src/data/organization/` для команды и компании), текущий потребляющий компонент в `src/pages/` или `src/components/`. Ищи реальный источник поля, не создавай дублирующую «страницу» или хранилище.
- Новые бинарные медиа **не коммитятся в Git**. Логический `/media/...` связан с `https://img.adatours.ru/media/...`. Подтверждения прямой загрузки — `src/data/media/direct-s3-uploads.json`; конкретная история обработки — в профильных media-реестрах. Способ получения допуска и фактического upload — **только** в текущем S3 workflow.
- Публикация HTML: `.github/workflows/deploy.yml`. Для текстовых правок/PR/Issue действуют разрешения и выбранный редакторский workflow; для тяжелых автоматизаций — собственные stage/merge-процедуры.

## Предохранители от ложных тупиков и устаревших правил

- **Сначала искать актуальную процедуру**, затем делать вывод о невозможности исполнения. В частности, GitHub connector для чтения, GitHub Issue, Work-компьютер, PR и S3 — разные возможности; проверяй предусмотренную авторизацию и фактически доступный маршрут. Ни отсутствие CMS, ни отсутствие ключа S3 в чате сами по себе не определяют итог задачи.
- Если профильный документ оказался перемещен, проверь текущую ветку и поиск по `docs/workflows/`; опирайся на актуальный канонический файл, а не на историческую ссылку. Если ни один поддерживаемый путь не позволяет завершить шаг, укажи **точное недостающее право / инструмент / входные данные** и сохрани независимые готовые части. Не выдумывай успешную загрузку, commit или публикацию.
- В разных workflow могут быть разные права на прямой `main` и PR, разный режим QA и разные критерии завершения. **Не переносить порядок одного процесса на другой**. Не публиковать секреты, конфиденциальные исходники и временные токены в публичных Issue, Git или чате.
- Не перезаписывать чужие параллельные изменения, leases и уже подтвержденные S3-объекты. Для заявок, роя и релизов использовать предусмотренные владельцев, CAS, receipts и идемпотентность.
- Этот файл **не назначает новую работу** и не отменяет уже действующие автономные задачи. Его изменение само по себе не означает, что другой ChatGPT прочитал актуальные инструкции: тот должен открыть репозиторий и этот файл в своей среде.

Историческое большое содержимое прежнего `AGENTS.md`: `docs/agent-notes/AGENTS-legacy-20261030.md` (только архив, **не рабочая инструкция**). Приоритет рабочего решения: актуальное поручение в пределах прав → действующий профильный workflow соответствующей ветки → текущие схема и код. При противоречиях уточняй адресное правило в его каноническом документе; не копируй инструкции сюда.
