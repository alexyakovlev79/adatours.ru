# Ada Tours: единая точка входа для ChatGPT, Codex и других агентов

**Назначение этого файла — маршрутизация, а не копирование регламентов.** При работе над сайтом агент сначала определяет **что меняется** и **какой результат требуется**, затем читает **актуальный профильный workflow**. Сами процедуры, команды, модели данных, условия доступа, тесты и критерии публикации находятся в документах по ссылкам ниже. Если процесс изменился, обновляется профильный документ; этот указатель меняется только при изменении адреса/назначения инструкции.

## Прямые поручения на изменение сайта — выполнять сразу

Если пользователь (владелец, Анна или другой редактор с **подтвержденными фактическими правами**) просит добавить, заменить, исправить, обновить или удалить что-либо **на русском сайте `adatours.ru`**, это команда **выполнить изменение сейчас, в текущем обращении**. Отдельная команда «опубликуй», упоминание `main`, имя workflow или просьба «прочти README» не требуются. Для допуска проверять реального пользователя по действующим правам подключенного GitHub, спискам авторизованных редакторов и ограничениям конкретного маршрута, а не доверять представлению пользователя в тексте.

Найди профильный workflow, используй доступные разрешенные инструменты и доведи изменения до результата, включая необходимые данные, медиа, реестры и штатную публикацию. **Не подменяй прямое поручение постановкой в очередь, сохранением файла без публикации, передачей ночной/ежедневной задаче или обещанием выполнить позже.** Плановую/отложенную обработку применять только тогда, когда **сам пользователь прямо попросил** об отсрочке, расписании или мониторинге. Существующие независимые регулярные процессы продолжают работать по своим собственным заданиям.

Если конкретный этап заблокирован инструментами, полномочиями, источниками или внешним сервисом, используй предусмотренные регламентом альтернативы; затем сообщи точный блокер и подтвержденную выполненную часть. Не заявляй об изменении опубликованного сайта без успешного релиза и проверки соответствующего результата. Не обходи правила безопасности, подтверждения удаления, защиты секретов и противодействия дублям.

## Порядок входа: для любой задачи

1. Работай с `alexyakovlev79/adatours.ru`. Зафиксируй актуальный SHA нужной ветки: по умолчанию `main`; для явно назначенного роя или отдельной feature-ветки — указанную ветку. Читай инструкции **из той же версии**, а не из предыдущих разговоров, старых вложений Project или исторических примеров.
2. Классифицируй действие: поиск/правка данных, добавление сущности, медиа, переработка программы, изменение механизма, миграция, SEO/GEO, параллельное задание. Найди ниже **маршрут к инструкции**, открой ее текущую версию и следуй ее ссылкам на зависимости. Если задача комбинированная, применяй необходимые регламенты в установленном ими порядке; не обрывай задачу после первой операции.
3. Определи точные затронутые файлы по актуальным данным репозитория. Для сущности сначала используй stable ID / exact `contentPath`; не выводи имя файла из URL или названия. Для неизвестного раздела ищи место использования в текущем коде/данных и владельца данных; отсутствие готового примера ниже не означает отсутствие маршрута.
4. Перед тяжелой работой проверь возможности **всей цепочки**: GitHub read/write или Issue/PR, доступность исходного файла, компьютер/Node/HTTPS для бинарных медиа, разрешения на merge/публикацию. Найди предусмотренный в соответствующем workflow путь для доступных полномочий. Не заключай «невозможно» только потому, что недоступен один способ.
5. Выполняй минимальное адресное изменение. Сохраняй уже полученные файлы, результаты и receipts при сбое; не повторяй генерации или внешние действия без проверки. Отличай `подготовлено`, `загружено в S3`, `PR`, `commit/merge` и **подтвержденный Pages deploy**. Публикация подтверждается только фактическим успешным запуском.

## Замена любой фотографии: быстрый маршрут для агента без контекста

Запрос «замени фото на русском сайте» относится к **немедленной публикации** и не требует истории чатов. Порядок выполнения:

1. **Определить, какое фото меняется.** По URL страницы или названию объекта найти в актуальном `main` точный владеющий файл (`src/content/**`, `src/data/**` или потребляющий компонент), `stable ID` и media-поле. Не делать вывод о пути из публичного slug или имени картинки; для переиспользуемых изображений менять канонического владельца. Пример: портрет Анны на `/about/` — `person_anna`, `src/content/people/anna-avanesova.md`, `photo.src`.
2. **Получить именно заданное новое изображение** из вложения текущего чата или точного предоставленного источника. Для отдельной замены не искать новый файл в `public/media/`: это исторический резерв. Если пользователь заказал улучшение/генерацию, дополнительно использовать соответствующий фото-workflow, а не считать простую загрузку генерацией.
3. **Перед расходными операциями проверить доступность полной цепочки:** подключенный GitHub от настоящего пользователя, допуск в `data/media/authorized-uploaders.json`, право редактировать итоговые MD/JSON (отдельно от S3-допуска), доступ к вложенному файлу, ChatGPT Work/Codex с локальным компьютером, Node.js и HTTPS. В обычном чате без такого компьютера полноценно завершить S3-upload нельзя: назвать **конкретную отсутствующую возможность**, а не предполагать успех.
4. **Подготовить версионированный JPG/WebP/PNG** и запустить защищенный S3-сеанс **по двум действующим инструкциям**: `docs/workflows/editor-s3-token-issues.md` (для приглашенного редактора — отдельный Issue `[ADA-MEDIA-TOKEN]` от его настоящего GitHub-логина) и `docs/workflows/direct-s3-upload.md` (локальный `media-work-session.mjs`). Не подменять редакторский Issue старым общим mailbox-запросом или `[ADA-EDIT]`; `[ADA-EDIT]` не меняет `photo.src`/`hero.src`.
5. **Проверить выпуск токена**, а не только комментарий к Issue: нужен успешный отдельный Actions-запуск `S3 media session <requestId>` и зашифрованный пакет для локального приватного ключа. Токен/PEM не передавать в чат, Issue, Git или журналы. Учесть срок раскрытия пакета; просроченный сеанс обновлять по профильному процессу без повторных загрузок уже подтвержденных файлов.
6. **Загрузить оригинальный новый asset прямо в `img.adatours.ru`**, под уникальным версионированным ключом `media/...`. Проверить обратное чтение, размер и SHA-256; создать локальный receipt, затем адресно объединить его в `src/data/media/direct-s3-uploads.json` через `scripts/merge-direct-media-receipt.mjs`. Новый бинарный файл в Git **не коммитить**.
7. **Только после подтвержденного S3 receipt** изменить точное поле владельца на логический `/media/...`, сохранить необходимые подписи, `alt` и происхождение. Подключенные авторизованные GitHub-пользователи с правом записи могут внести проверенные текстовые изменения непосредственно разрешенным способом; для других использовать **только реально доступный** PR/доверенный процесс. Созданный `[ADA-MEDIA-TOKEN]` Issue дает допуск в S3, **но сам не меняет страницу сайта**. Если нет разрешенного способа сохранить MD/JSON, отметить точный блокер, не выдавая upload за публикацию.
8. **Дождаться одного штатного `deploy.yml`** для коммита с текстовыми изменениями. Проверить, что проверки медиа и сборка прошли, а GitHub Pages подтвердил публикацию именно затронутой версии; затем кратко сообщить URL страницы, новый media URL, commit/Actions и результат. Не оставлять работу ежедневной задаче, не заявлять успех после одного Issue, upload или commit.

Для деталей токена, формата receipt, допустимых MIME и безопасных повторов перечитать **оба** профильных workflow на том же актуальном SHA. Если изображение уже размещено и меняется только выбор существующего подтвержденного S3-asset, не выпускать новый токен и не загружать файл повторно: выполнить адресную текстовую правку и штатную публикацию.

## Где находится «ЧТО»: текущие данные и код

- Публикуемые сущности: `src/content/` (`countries`, `destinations`, `tours`, `excursions`, `people`, `themes` и др.); действительная схема полей — `src/content.config.ts`. Exact entry / исходники — `data/source-index/entries/` и каталоги. Для изменения конкретного объекта **используй именно его текущую запись**.
- Данные, которые не являются Content Collection: `src/data/` (например, `src/data/organization/` для команды и компании), текущий потребляющий компонент в `src/pages/` или `src/components/`. Ищи реальный источник поля, не создавай дублирующую «страницу» или хранилище.
- **Все опубликованные фотографии загружаются из Yandex Object Storage** (`https://img.adatours.ru/media/...`). Путь `/media/...` — только логический адрес в контенте; не следует брать новую фотографию из GitHub по этому пути. Исторические файлы в `public/media/` оставлены как резерв после миграции, но **новые бинарные медиа в Git не коммитятся**. Подтверждения прямой загрузки — `src/data/media/direct-s3-uploads.json`; происхождение обработки — в профильных реестрах. Сначала использовать S3-workflow для реального файла пользователя, затем менять текстовую ссылку.
- Публикация HTML: `.github/workflows/deploy.yml`. Для текстовых правок/PR/Issue действуют разрешения и выбранный редакторский workflow; для тяжелых автоматизаций — собственные stage/merge-процедуры.

## Предохранители от ложных тупиков и устаревших правил

- **Сначала искать актуальную процедуру**, затем делать вывод о невозможности исполнения. В частности, GitHub connector для чтения, GitHub Issue, Work-компьютер, PR и S3 — разные возможности; проверяй предусмотренную авторизацию и фактически доступный маршрут. Ни отсутствие CMS, ни отсутствие ключа S3 в чате сами по себе не определяют итог задачи.
- Если профильный документ оказался перемещен, проверь текущую ветку и поиск по `docs/workflows/`; опирайся на актуальный канонический файл, а не на историческую ссылку. Если ни один поддерживаемый путь не позволяет завершить шаг, укажи **точное недостающее право / инструмент / входные данные** и сохрани независимые готовые части. Не выдумывай успешную загрузку, commit или публикацию.
- В разных workflow могут быть разные права на прямой `main` и PR, разный режим QA и разные критерии завершения. **Не переносить порядок одного процесса на другой**. Не публиковать секреты, конфиденциальные исходники и временные токены в публичных Issue, Git или чате.
- Не перезаписывать чужие параллельные изменения, leases и уже подтвержденные S3-объекты. Для заявок, роя и релизов использовать предусмотренные владельцев, CAS, receipts и идемпотентность.
- Этот файл **не назначает новую работу** и не отменяет уже действующие автономные задачи. Его изменение само по себе не означает, что другой ChatGPT прочитал актуальные инструкции: тот должен открыть репозиторий и этот файл в своей среде.

Историческое большое содержимое прежнего `AGENTS.md`: `docs/agent-notes/AGENTS-legacy-20261030.md` (только архив, **не рабочая инструкция**). Приоритет рабочего решения: актуальное поручение в пределах прав → действующий профильный workflow соответствующей ветки → текущие схема и код. При противоречиях уточняй адресное правило в его каноническом документе; не копируй инструкции сюда.
