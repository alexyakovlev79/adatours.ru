# ADA TOURS — реестр очереди экспертных SEO/GEO-текстов

**Версия:** 2.5 · **Дата:** 2026-10-14  
**Статус:** единый рабочий регламент очереди, подготовки SEO/GEO-текстов в параллельных чатах и отдельной пакетной публикации мастер-чатом. Два режима команд определены в разделе 8.

## 1. Где находится реестр

- Канонический машиночитаемый индекс: `data/seo-geo/registry/index.json`.
- Семь исходных очередей: `data/seo-geo/registry/01-countries.json` … `07-excursions.json`.
- Google Sheets, таблица **«Ada Tours — реестр страниц нового сайта»**, лист **«SEO-GEO тексты»**: https://docs.google.com/spreadsheets/d/1ZPptMdEcIDA3ZFMOQcFuc5jU88LJlFw9R4URCQSBmmc/edit#gid=1993101426.
- Основной лист `Страницы` — независимый реестр публикации самих объектов; его статусы не означают завершения SEO/GEO-статьи.
- Таблица является удобным зеркалом очереди; JSON в GitHub — источник для автоматизации. Сверять по **каноническому URL**, а не по физическому номеру строки в Google Sheets.

Начальная очередь содержит **3805 URL**. Источники первого среза: каноническая опись `data/external-identity/index.json` (11.10.2026), подтвержденные VIP-каталоги `data/external-identity/vip-catalogues.json` (12.10.2026), основной реестр `Страницы` и актуальные каталоги `data/source-index/catalogs/`. Это фиксация источников, а не утверждение, что все URL работают в данную минуту. Более поздние изменения нужно учитывать дополнительно.

## 2. Неизменяемый порядок приоритетов

| Этап | Содержание | Начальная очередь |
|---|---|---:|
| 01 | Страны: `/country/`, затем сами страны | 25 |
| 02 | Интересы: `/interests/`, 14 интересов, их собственные каталоги | 41 |
| 03 | Страна + интерес: `/interests/<theme>/tours/<country>/` | 119 |
| 04 | Страна + интерес + VIP: `/vip/<country>/interests/<theme>/` | 92 |
| 05 | Туры: общие, страновые, VIP и связанные каталоги, затем отдельные туры | 1692 |
| 06 | Места: каталоги и отдельные страницы мест | 1018 |
| 07 | Экскурсии: каталоги и отдельные экскурсии | 818 |

Работать по полю `order` строго сверху вниз. Внутри этапов уже закреплен начальный порядок стран и интересов; новые строки вставлять в **свой этап**, сохраняя правильную сортировку. При необходимости пересчитать числовые `order` во всех семи JSON-файлах и в таблице; текущий `order` не является постоянным ID. Стабильный ключ — **канонический URL**, а для сущности дополнительно ее существующий stable ID.

Страница `/interests/coffee-tours/` восстановлена 14.10.2026 по прямому поручению Алексея как 14-й интерес `theme_coffee`; историческая строка №40 сохранена и возвращена в очередь. Новая сущность сама по себе не запускает написание SEO/GEO-статьи.

**Специальные страницы MICE, DMC, делегаций, B2B, юридические, кейсы, команда и другие самостоятельные коммерческие разделы НЕ входят в эту очередь.** Их тексты ведутся отдельно по собственным заданиям. Из общих коммерческих хабов в эту очередь входят `/vip/` и `/multi-country/` как часть этапа туров.

**Приоритетные сочетания Multi-country (15.10.2026).** Непосредственно после готового хаба `/multi-country/` в этапе 05 стоят **199 действующих страниц** (51 пара, 72 тройки, 76 четверок). Вначале пары, затем тройки и четверки, внутри размера по убыванию числа действующих туров. Это отдельные индексируемые статические каталоги, но еще **не написанные SEO/GEO-статьи**. Сортировка по полю `order`; URL — алфавитные английские slug, названия страниц — страны в том же порядке. Сверять с активными `routeCountries ?? countries` через `buildMultiCountryCombinations`; если URL исчез при архивировании/изменении географии, сохранять его историю и переводить в `temporarily_unavailable`, не удалять. Новые непустые сочетания помещать в эту группу с синхронизацией Google Sheets. Не создавать записи для `/page/N/`.

## 3. Первая страница каталога и пагинация

**Жесткий запрет:** на `/page/2/`, `/page/3/` и следующих страницах не создаем отдельные SEO/GEO-статьи, не дублируем FAQ, не заводим строки в этой очереди. Текст принадлежит только корневому URL каталога, то есть первой странице. Пагинация остается независимой, с действующими canonical, каталогом и навигацией.

При синхронизации отфильтровать любой URL, соответствующий `/page/[0-9]+/`, до постановки в очередь. Не объединять его с первой страницей под видом второй самостоятельной статьи.

## 4. Никогда не удалять историю

- Если URL исчез из sitemap, исчезло последнее предложение, объект перенесен в архив или временно отсутствует, **оставить строку в JSON и таблице**.
- Установить `work: temporarily_unavailable` либо `archived`, зафиксировать причину в примечании/журнале. Не стирать прежние MD, источники, дату публикации и коммит.
- Если появляется новый canonical URL, сохранить историческую строку старого адреса, отметить ее как замещенную и добавить новую, связав их в примечании. Не возвращать старый адрес в индексируемые страницы ради очереди.
- При повторной доступности исходной страницы вернуть ее статус в рабочий и продолжить с сохраненного результата, не начинать текст с нуля.
- Обновление по текущему sitemap/source-index выполняется **только добавлением новых адресов и актуализацией признаков**, никогда полной заменой массива текущим списком.
- Архивные туры/экскурсии сохраняются в реестре, но не публикуются заново; действующий архивный контракт сайта имеет приоритет.

### 4.1. Архивирование тура или экскурсии: связанные SEO/GEO-тексты

Архивируется только `Tour` или `Excursion` по `docs/workflows/archive.md`; Country, Destination и Theme не архивируются. Архивную строку сохранять (`work: archived` в соответствующем JSON, `J = Архив` в листе `SEO-GEO тексты`), включая `articlePath`, историческую дату и SHA. Статусы других страниц, в которых была рекомендация, не сбрасывать.

**Архивация требует содержательной правки в том же релизе:** найти прямые и прежние URL архивируемого тура/экскурсии, stable ID в `catalog.tourTable` и упоминания в опубликованных `data/seo-geo/articles/**/index.md`. Переписать только затронутые фразы: при подтвержденной активной замене переформулировать рекомендацию и поставить ее каноническую ссылку; иначе удалить обещание доступной поездки и связать абзац естественно, сохранив остальные факты и действующие ссылки. Снятие гиперссылки без изменения утверждения о продаваемой программе — ошибка. Не придумывать эквивалентность продуктов и не удалять историю SEO-статьи.

Работающие параллельно авторы могут держать `prepared` в `seo-geo/staging`. Перед архивным commit проверить их на устаревшие предложения; исправлять лишь без нарушения чужих CAS/claims. При неразрешенном конфликте SEO-мастер задерживает публикацию конкретной подготовленной статьи до исправления, а не перезаписывает чужую работу. При обычной команде «пиши SEO» перед окончательным staging-коммитом еще раз сверять упомянутые продукты с актуальным архивом `main`. Мастер при сборке SEO-пакета повторяет эту проверку для всех переносимых статей. Штатный валидатор `scripts/check-seo-geo-pages.mjs` отвергает ссылки на архивные URL, несмотря на их существование; он не заменяет смысловую редактуру фраз без ссылок.

## 5. Статусы и реальная последовательность работы

| JSON `work` | Лист Google Sheets | Действие |
|---|---|---|
| `queued` | В очереди | Можно брать по приоритету |
| `waiting_for_page` | Ждет страницу | URL еще не подтвержден, проверить при появлении |
| `draft` | Пишется | Работа начата, готового материала еще нет |
| `prepared` | Ждет публикации | Подтвержден удаленный content-коммит с полноценным MD, сайт еще не опубликован |
| `published` | Опубликовано | Размещен в индексируемом HTML; сохранены дата и commit |
| `paused` | Отложено | Прямое решение отложить, хранить причину |
| `temporarily_unavailable` | Временно недоступна | URL пропал; строка остается |
| `archived` | Архив | Пропускать без удаления |
| `not_in_active_theme_registry` | Вне активного справочника | Исторический резерв, не публиковать без пересмотра модели |

Статус «Текст готов» в старых строках таблицы — исторический синоним `prepared`; при следующем адресном обновлении такой строки заменить его на «Ждет публикации», только если полноценный commit подтвержден. Сам текст в черновике без коммита не дает права на этот статус. Публикация (`published`) фиксируется только мастер-чатом после успешного GitHub Pages deploy.

`availability` — отдельно от `work`: наличие исходной страницы не означает написанный SEO/GEO-текст. `vip_checked_2026_10_12` фиксирует подтвержденный VIP URL на дату среза; `inventory_2026_10_11` означает наличие в описи, а не сегодняшнюю HTTP-проверку. Не заменять исторические даты проверки текущей без фактической проверки.

## 6. Обязательное обновление при создании страницы или SEO/GEO-материала

**При создании новой Country/Theme/Tour/Destination/Excursion или нового непустого каталога:**

1. Вычислить канонический URL действующими route helpers / генератором Astro, исключить `/page/N/` и специальные разделы.
2. Найти URL в семи файлах. Если найден — **актуализировать его наличие, сохраняя статус редакционной работы и историю**. Если не найден — добавить в соответствующий этап; для нового тематического или VIP-пересечения нужна реально существующая непустая подборка, не теоретическое сочетание 24 × 13.
3. При добавлении новых записей расположить их в правильном этапе, обновить `order` во всех затронутых этапах, `totalRows` и `orderFirst/orderLast` в `index.json`.
4. Синхронизировать те же URL, названия, ID, этапы, порядок и признаки наличия на листе `SEO-GEO тексты`, **не затрагивая** листы `Страницы`, `Фото`, `Сводка`.
5. Не создавать статью автоматически лишь потому, что появился новый тур/место: это отдельное назначаемое редакционное задание.

**При подготовке/публикации длинного SEO/GEO-текста:**

1. По команде «пиши SEO» сначала проверить и восстановить незавершенные резервы, у которых истекли 60 минут без продления и нет подтвержденного готового коммита (раздел 8.2). Затем **одним CAS зарезервировать до 3 пригодных URL по `order`**: сначала просроченные незавершенные, затем свободные `queued`. Недоступную страницу адресно отметить и перейти к следующей.
2. Перед написанием прочитать существующий публичный текст страницы, реальные программы Ada Tours и тематически соседние посадочные. Выделить уникальные вопросы страницы, без повторов родительского хаба.
3. Готовить материал самостоятельно: использовать данные сайта, надежные открытые источники и собственное исследование ChatGPT. **Ответы Анны и ее сотрудников, дополнительная редакционная подготовка с их стороны и ожидание подтверждения от Анны не являются условием выполнения.**
4. Вместе с реальными фактами сохранять проверяемые ссылки на источники и дату проверки в рабочем материале. Не выдавать придуманные отели, конкретный класс сервиса, включенные услуги, цены, условия или гарантии за факты Ada Tours. Если сведений нет, сократить или иначе сформулировать раздел, а не выдумывать факты.
5. Следовать общим `docs/workflows/writing-rules.md`. Объем определяется полезностью, для приоритетных хабов возможны 8–18 тыс. знаков и больше при достаточной фактуре; квот на количество символов нет. FAQ только с реальными ответами, не вместо содержательной статьи.
6. Полный материал должен попасть в серверный HTML (допустим видимый пользователю сворачиваемый блок); он не должен подгружаться исключительно по нажатию. Добавление этого компонента/шаблонов — отдельный шаг разработки, не считать наличие MD публикацией.
7. Пишущий чат сначала сохраняет полностью готовый MD в `seo-geo/staging` с `work: draft`, затем получает успешный `ada/seo-link-preflight` по SHA content-коммита. Только следующим CAS-коммитом с `preflightCommit` и `preflightArticleBlobSha` присваивает `work: prepared` и статус «Ждет публикации» в Google Sheets, сохраняя путь MD, время и полный SHA в служебном комментарии. **Только мастер-чат** после успешного общего deploy меняет `work` на `published`, указывает дату и полный SHA опубликованного коммита. Строку Sheets всегда искать по URL в колонке E.
8. Если Google Sheets недоступен, сохранить конкретную задачу синхронизации в комментарии/рабочем журнале и повторить позже. Готовый материал и commit не пересоздавать ради ошибки записи в таблицу.

**Автоматическая проверка:** до `prepared` работает staging-preflight `ada/seo-link-preflight`, затем штатный `npm run build` сначала выполняет `tests/seo-geo.test.mjs`, а после Astro-сборки — `scripts/check-seo-geo-pages.mjs`. Проверка и публикация HTML через `.github/workflows/deploy.yml` запускаются только одним пакетным обновлением `main` от мастер-чата; писатель их не вызывает.

## 7. Начальное состояние очереди

Очередь и фактические SEO/GEO-статьи — разные сущности. Единый renderer подключен к Astro; опубликованные статьи читаются из `data/seo-geo/articles/<canonical-segments>/index.md` только при `status: approved`. Пока для страницы нет такого готового MD, дополнительный блок отсутствует. Статус `published` ставится лишь после успешного деплоя полной статьи, а не после появления базовой страницы.

Срез может устареть: при появлении новых туров, мест и фильтров строки добавляются, но исчезнувшие никогда не удаляются. Если новый источник расходится со старым срезом, отмечать дату и основание обновления без молчаливого перезаписывания редакционной работы.

## 8. Команды и разделение ролей: авторы и мастер-чат

**Этот MD — единственная подробная инструкция SEO/GEO-процесса.** Отдельных регламентов для стран, интересов, VIP, туров, мест и экскурсий не создавать. Вход для любого нового чата — `AGENTS.md` и этот документ. Сохраняются прежние требования к глубине, источникам, интенту, содержанию статического HTML и порядку очереди из разделов 1–7 и 9–15.

**Две роли и две ветки:**

- **Пишущий SEO-чат:** получает «пиши SEO» или «дальше» в уже начатом SEO-проходе; единственная рабочая ветка для SEO-материалов — **`seo-geo/staging`**. Он **разом резервирует 3 URL**, пишет 3 статьи последовательно без общего лимита времени, по каждой создает удаленный Git-коммит в staging и переводит строку в **«Ждет публикации»**. Каждый из трех резервов действует 60 минут с момента захвата или последнего продления; автор продлевает действующие резервы CAS. **Запрещены запись/слияние в `main`, push в `main`, pull request в `main`, `npm run build`, workflow_dispatch, ручной запуск CI/deploy, ожидание GitHub Pages и любые другие попытки опубликовать страницу.** Git-коммит должен существовать на доступной всем удаленной staging-ветке; локальный незапушенный commit не считается готовностью.
- **Мастер-чат публикации:** получает **«собирай SEO»** или **«публикуй SEO»** (равнозначные команды). Только он извлекает **все** подтвержденные готовые и еще не опубликованные SEO/GEO-материалы из общего staging-среза и отправляет единый пакет в `main` для **одной штатной сборки и одного деплоя**. Писать новые статьи вместо авторов и резервировать свободные строки для этого не требуется.

`.github/workflows/deploy.yml` автоматически запускает Pages при обновлении `main`, поэтому размещение SEO-текстов или резервов в `main` пишущим чатом нарушает этот контракт даже с `[skip ci]`. В staging push/commit **не** запускает Pages. `ci.yml` на pull_request может запустить отдельную сборку, поэтому писатели не открывают PR.

### 8.1. «Пиши SEO»: 3 последовательные статьи, без ограничения времени

**Обязательные короткие сообщения пользователю (в ходе работы, без ожидания завершения тройки):**

- **Сразу после команды, до первого вызова GitHub, Google Sheets или другого инструмента:** «Проверяю очередь SEO/GEO и активные резервы. Возьму следующие 3 доступных URL». Это сообщение о начале проверки, а не заявление о захвате.
- **Сразу после подтвержденного удаленного коммита общего резерва:** перечислить номера `order` и точные 3 URL (либо фактически доступное число), указать `batchId` и «Начинаю статью 1/3». При задержке синхронизации Sheets не откладывать этот отчет; состояние таблицы назвать отдельно.
- **После каждого подтвержденного удаленного content-коммита:** «Статья 1/3 готова: <URL>, staging SHA <SHA>. Начинаю 2/3» (соответственно для следующих). Указывать настоящий SHA, не обещать публикацию. Следующую статью начинать автоматически.
- **Если этап длится больше примерно 2 минут:** между инструментальными вызовами дать короткий фактический статус, что уже подтверждено и какой шаг выполняется. Нет гарантии сообщений во время одного зависшего инструментального вызова; не вводить отдельный фоновый таймер, не тратить время на пустые повторы статуса.
- **При конфликте записи или блокере:** назвать конкретную стадию и сохраненное состояние без заявления о завершении; остановка допустима только по реальному блокеру или после всей тройки. Полные тексты статей в чат не вставлять.

Эти сообщения **не требуют ответа пользователя и не меняют** атомарный CAS, порядок очереди, сроки резервов, требования к качеству статей или права мастера на публикацию.

**Одна команда «пиши SEO» = один пакет из 3 разных URL.** Сначала атомарный резерв всего пакета, затем последовательная подготовка статей № 1, 2 и 3. Если пригодных URL осталось меньше трех, брать только реально доступные. Для следующей тройки нужна новая команда «дальше». Ограничения на время написания пакета или каждой статьи **нет**: прежний 10-минутный таймер отменен. Отдельно действует 60-минутная защита резервов с продлением.

1. Получить свежие `main` и `seo-geo/staging`, зафиксировать UTC. Прочитать один актуальный `claims.json`, выделить просроченные кандидаты по § 8.2 и адресно подтвердить их состояние. До набора тройки восстанавливать только действительно затронутые готовые статьи или осиротевшие статусы; **не проводить общий аудит всего staging, всей истории Git и всех строк реестра**. Не перехватывать активные 60-минутные резервы других исполнителей.
2. Выбрать **3 разных пригодных канонических URL** по возрастанию `order`: сперва незавершенные просроченные резервы (по давности захвата, при равенстве — `order`), затем свободные `work: queued` по `order`. Исключить `archived`, `temporarily_unavailable`, `waiting_for_page`, `paused`, `published` и подтвержденные удаленным коммитом `prepared`, а также все чужие действующие claims. Неподтвержденную доступность конкретного URL проверить адресно. Три URL не заменять соседями, если один из уже захваченных позднее оказался трудным.
3. **До начала исследования или написания** провести **один атомарный захват сразу всех трех URL** в `data/seo-geo/claims.json` ветки `seo-geo/staging`. У каждой записи ключ — canonical URL; поля: `ownerId`, общий `batchId` пакета, `order`, `claimedAt` (UTC ISO, не меняется до смены владельца), `lastHeartbeatAt` (при первом захвате равно `claimedAt`), `expiresAt = lastHeartbeatAt + 60 минут`, `generation` / уникальный токен захвата. Записать сразу три claims и три соответствующих `work: draft` в один подготовленный Git tree/commit с ожидаемым parent SHA и безопасным CAS при обновлении удаленной ветки. При конфликте перечитать свежий HEAD staging, `claims.json` и только затронутые строки реестра; заново выбрать и захватить **всю тройку**, без частично закрепленного пакета. После первой неудачной записи разрешено **не более 2 повторных CAS-попыток**; не начинать полное чтение проекта и не вести бесконечные попытки. При повторном конфликте сообщить конкретный блокер и остановить запуск без написания незакрепленной статьи. Только подтвержденный remote commit подтверждает права автора.
4. После подтверждения этого служебного коммита **одним пакетным обновлением Google Sheets** найти все 3 строки по canonical URL в колонке E, установить `J = Пишется` и записать UTC, `ownerId` и `batchId` в служебное поле M. Google Sheets является зеркалом, а не механизмом блокировки; при сбое таблицы claims остаются действительными, отложить только адресную синхронизацию. **Сообщить пользователю о трех закрепленных URL сразу после remote SHA резерва**, не дожидаясь ответа Sheets.
5. **Писать строго по одной статье**, начиная с первого зарезервированного URL. Для каждой самостоятельно изучить текущую страницу, отличия от тематических соседей, подтвержденные факты и внутренние связи; применить §§ 9–15. Не распылять три исследования одновременно и не менять основную очередь после захвата. Закончив первую статью и зафиксировав ее, сразу перейти ко второй, затем к третьей; команды «дальше» между ними не требуются.
6. **Срок одного резерва — 60 минут, а не ограничение времени на текст.** Пока автор работает, до истечения срока он продлевает одним CAS все принадлежащие ему **незавершенные** claims с прежними `ownerId`, `batchId` и `generation`: обновить `lastHeartbeatAt` текущим UTC и `expiresAt` на 60 минут вперед; `claimedAt` сохранить. Проверять и при необходимости обновлять резерв после завершения каждой статьи и во время длительной работы, ориентировочно раз в 30 минут. Внешний таймер или фоновый процесс не предполагается: продление выполняется в рабочем цикле самого чата. Завершенные и снятые claims не восстанавливать.
7. Перед каждым content-коммитом проверить собственный еще действующий claim и конкретные затронутые файлы staging, а также архив/активность упомянутых Tour/Excursion в свежем `main`. `ownerId` и `generation` должны совпадать, 60-минутный срок не должен быть истекшим. Если срок прошел, можно повторно атомарно продлить **только если** claim еще принадлежит этому автору и никем не перехвачен; после смены владельца нельзя записывать поверх чужой работы. Подтвержденный `prepared/published` не перезаписывать.
8. **Preflight внутренних ссылок — до `prepared` (обязателен с 15.10.2026).** Сначала сохранить полностью готовую статью `status: approved` и provenance отдельным удаленным content-коммитом `seo-geo/staging`, оставив `work: draft` и собственный действующий claim. Push запускает легкий GitHub Actions `seo-geo-preflight.yml`, который проверяет ссылки по активным canonical URL свежего `main`, включая непустые тематические/VIP-каталоги. Полный `npm run build` не вызывается. Получить результат GitHub commit status `ada/seo-link-preflight` **именно для SHA этого content-коммита**. При ошибке исправить текст и повторить content-коммит, claim не снимать. Пока статус не `success`, `prepared` и «Ждет публикации» запрещены. При недоступной проверке сохранить `draft` и конкретный блокер.
9. **Только после успешного preflight** для того же неизмененного MD отдельным безопасным CAS-коммитом записать `work: prepared`, `articlePath`, `preparedAt`, `preflightCommit` (полный SHA успешно проверенного content-коммита) и `preflightArticleBlobSha` (Git blob SHA проверенной статьи) и снять **только свой** claim. Чужие draft/claims не трогать. Любая последующая правка статьи требует нового preflight. После подтвержденного второго SHA сообщить пользователю номер и URL статьи, затем продолжить следующий URL пакета.
10. Сразу после подтвержденного remote SHA адресно обновить соответствующую строку Google Sheets: `J = Ждет публикации`, `K = articlePath`, `M` — UTC и полный staging SHA, `L` оставить пустой до мастер-деплоя. При сбое таблицы сохранить точную отложенную синхронизацию и продолжить следующую статью; не повторять готовый контент или всю подготовку. Затем, при необходимости продлив оставшиеся резервы, приступить к следующей статье пакета. Невыполненную статью не маскировать статусом `prepared`.
11. Остановиться **после обработки всех трех зарезервированных URL**, а не по истечении 10, 30 или 60 минут. Сообщить для каждого URL его статус, готовый `articlePath` и SHA, конкретные блокеры и незавершенные claims с временем истечения, если они есть. Оставшиеся неполные claims сохраняются для безопасного продолжения/перехвата по § 8.2. **Автор не делает build, deploy, PR и запись в `main`.** Следующую тройку брать только по отдельному «дальше».

### 8.2. Просроченные резервы: проверка строго раньше свободных строк

**Условие перехвата:** с последнего подтвержденного захвата или продления прошло **более 60 минут** (UTC сейчас позже эффективного `expiresAt`), нет подтвержденной готовой статьи в удаленном staging/main и нет действующего продления. Приоритет имеет `lastHeartbeatAt + 60 минут`, а для старых записей без этого поля — `claimedAt + 60 минут`. Исторический `expiresAt`, вычисленный по прежним 30 минутам, **не дает права на ранний перехват**. 60 минут — время без продления резерва, **не лимит продолжительности написания**.

1. В начале нового «пиши SEO» прочитать один актуальный staging `claims.json`. Рассматривать просроченные кандидаты по старшинству **только до набора трех пригодных задач**; для каждого открывать конкретную запись `registry/*.json`, его `articlePath` и подтвержденные удаленные коммиты staging/main. Полный обход всех просроченных URL, всех реестров и всей истории Git не нужен. Если полноценный `status: approved` MD уже закоммичен и соответствует URL, не переписывать его: при отсутствии деплоя сначала выполнить preflight, затем восстановить `prepared`/«Ждет публикации» с proof-полями и снять устаревший claim; если опубликован — оставить `published`. Ошибка Google Sheets сама по себе не делает claim свободным.
2. Для реально незавершенных просроченных URL сохранить исходный порядок восстановления (старший `claimedAt`, затем меньший `order`). **При формировании новой тройки** выбрать из них первые и добрать свободные `queued` до трех. Выполнить один атомарный CAS-захват всего выбранного пакета: для перехваченных записей сменить `ownerId`, `batchId` и увеличить `generation`, записать новый `claimedAt/lastHeartbeatAt/expiresAt` на 60 минут; текущие активные чужие claims не менять. Если после подтверждения готового материала просроченных кандидатов не осталось, выбрать только очередь.
3. Использовать уже подтвержденные факты, provenance, сохраненный пригодный черновик и точный `articlePath` незавершенной записи; не создавать дубли и не затирать готовые чужие MD. Восстановленные URL входят в те же **3 последовательные статьи** нового пакета. Никаких отдельных 10-минутных мини-проходов.
4. Если claims нет, но лист/registry оставил `work: draft`/«Пишется», а достоверное время последней активности старше 60 минут, сначала проверить наличие готового удаленного коммита, затем восстановить захват этой строки по CAS с приоритетом перед свободными. Если время неизвестно, считать просрочку недоказанной, зафиксировать блокер без случайного перехвата.
5. При недоступности безопасного CAS остановиться с точным блокером, сохранив чужие и собственные результаты, а не начинать писать без зарезервированных URL. Истекший таймер **никогда не аннулирует уже подтвержденный готовый commit**. Следующие авторы повторно используют готовое и берут только реально незавершенное.

### 8.3. «Собирай SEO» / «Публикуй SEO»: единственная пакетная публикация

**Перед объединением пакета:** для новых статей, переведенных в `prepared` после введения preflight 15.10.2026, проверить `preflightCommit`/`preflightArticleBlobSha` и успешный `ada/seo-link-preflight` по неизмененному content SHA; ссылки повторно сверить с актуальным `main`. Для **исторических `prepared` без proof-полей** не придумывать задним числом успешный статус и не снимать их с очереди автоматически: мастер адресно прогоняет `node scripts/preflight-seo-geo-links.mjs --article <articlePath>` по текущему `main`, исправляет найденные ссылки в staging и только затем переносит статью. Недоступная проверка или ошибка блокирует только конкретную статью, не всю партию. Затем перечитать актуальный архив из `main`, проверить ссылки и смысл упоминаний в каждом переносимом `prepared` материале. Архивную статью не включать в активную публикацию; устаревшую рекомендацию на архивный Tour/Excursion исправить в ее staged-источнике безопасной точечной правкой или отложить именно этот URL, не теряя другие готовые материалы. Уже опубликованные страницы обновляются при самой архивации по `archive.md`.

1. Прочитать **фиксированный SHA** общего `seo-geo/staging` и свежий `main`. Найти **все** записи `work: prepared` с подтвержденными remote MD (`status: approved`) по точному каноническому URL; дополнительно сверить старые строки «Текст готов» и изменения в `main` с еще не подтвержденной публикацией. Наличие записи в claims, только текста черновика, внешней таблицы или полного коммита другого типа не означает готовность к релизу.
2. Исключить уже `published` в актуальном `main` и статьи, чье идентичное содержимое подтверждено успешным deploy. Сопоставить по `URL + articlePath + Git blob SHA`, не по имени автора или времени. Просроченные `draft` без готового коммита **не** переносить, не переписывать и не превращать в `prepared` ради сборки.
3. Для всех готовых, но еще не опубликованных URL взять из замороженного staging-среза **только** их article MD, необходимые provenance и адресные изменения `registry/*.json` по этим URL. Не сливать в `main` целиком служебный `claims.json`, чужие `draft`, несвязанные коммиты, очередные эксперименты или старую staging-копию других файлов. На текущем `main` заново проверить активность URL и совместимость с актуальным кодом/данными; не затирать чужие изменения.
4. Все изменения интегрировать в **один** подготовленный tree и **один объединяющий content-коммит** поверх свежего `main` с ожидаемым parent SHA; обновить `main` **один раз** через safe fast-forward/CAS. Если `main` сдвинулся, заново собрать изменения поверх нового HEAD, сохранив пакет и не делая `force push`. Не открывать отдельный PR или Actions run для каждой статьи.
5. Ровно это обновление `main` запускает **один штатный** `.github/workflows/deploy.yml` с `npm run build`. Мастер следит за результатом для общего SHA и при необходимости исправляет конкретную ошибку, не повторяя сборки без причины. Если готовых неопубликованных статей нет, **не делать пустой коммит и не запускать сборку**.
6. Только после подтвержденного успешного GitHub Pages deploy общего commit (либо его потомка, где целевые blob SHA неизменны) перевести затронутые записи `registry/*.json` в `work: published`, добавить `publishedAt`, `publishedCommit`, `deployRun`; адресно обновить соответствующие строки Google Sheets по колонке E: `J = Опубликовано`, `L = дата первой публикации` (существующую дату сохранить), `M = commit/run`, `K = articlePath`. **Статусы `published` не ставить заранее.**
7. Для фиксации публикационных метаданных в `main` после успешного deploy разрешен отдельный **метаданный commit `[skip ci]`**, меняющий только статусы/даты/SHA в `data/seo-geo/registry/*.json`, без новых или измененных статей. Он **не создает вторую сборку**. При конкуренции обновлять только затронутые записи поверх свежего HEAD; синхронизировать их с staging как можно раньше, сохраняя новые активные claims и подготовленные другими авторами статьи. Не трогать `L`/статус других URL. Если отражение в Sheets/metadata недоступно, сохранить точный список отложенной синхронизации и **не дублировать контент или публикацию**.
8. При ошибке сборки сохранить `prepared` / «Ждет публикации» и список точных причин; отдельный статус «Опубликовано» не присваивать. Отчет: число статей в одной сборке, URL, общий commit, ссылка на Actions и фактический статус, исключения и оставшиеся готовые материалы.

**Безопасность параллельности:** staging-резервы и content-коммиты пишутся только с compare-and-swap/проверкой ожидаемого SHA; `main` и чужие правки сохраняются. Не использовать force push, перезапись всего JSON старой копией или массовый сброс статусов. Для отдельной задачи доработки общего renderer сохраняется блокировка `__bootstrap__` в staging; авторы не правят общие компоненты самостоятельно.

## 9. Обязательное разделение поисковых целей и содержания

Это основной редакционный контракт. **Перед написанием** определить: (а) какой вопрос решает целевая страница; (б) чем она дополняет родительские страницы; (в) какие темы обязана оставить соседям. Прочитать текущее описание целевой страницы и до 2–3 ближайших тематических соседей. Не копировать и не перефразировать их материал для набора объема. Пересечение отдельных фактов нормально, **дублирующий смысловой блок — нет**.

### 9.1. Страны — этап 01

| Страница | Уникальная польза и основной вопрос | Оставить другим |
|---|---|---|
| /country/ | Как выбрать страну или сочетание стран по типам впечатлений, сезонам, масштабу поездки и логистике | Путеводитель по каждой стране |
| /brazil/, /panama/ и иные страны | Зачем ехать именно сюда; география, регионы, климат, история, природные особенности, сезонность, планирование маршрута, сколько времени выделять, практические нюансы | Подробные сравнения конкретных продаваемых туров и VIP-сервис |

**Страна** — экспертный путеводитель, а не страница продажи каждого продукта. При содержательном упоминании опубликованных мест, самостоятельных экскурсий и маршрутов давать контекстные ссылки на их собственные страницы. Для тематических отступлений (культура, история, животные, гастрономия и т. д.) при наличии действующей страницы связывать соответствующий каталог «интерес + страна», не переписывая его содержание. Правила выбора анкоров и URL — в разделе 12.

### 9.2. Интересы — этап 02

| Страница | Уникальная польза | Оставить другим |
|---|---|---|
| /interests/ | Как выбирать тематические виды путешествий и совмещать увлечения | Полный гид по каждой тематике |
| /interests/wildlife/ и другие 13 тем | Где и ради чего заниматься конкретным интересом, сезоны, форматы, подготовка и ограничения | Подробности каждой страны и отдельных программ |
| /interests/<theme>/tours/ | Как выбирать существующие тематические туры и сравнивать форматы | Энциклопедическое описание самой темы |
| /interests/<theme>/related/ | Какие интересы разумно совмещать и чем они отличаются | Полные статьи всех соседних тем |

14 интересов берутся только из **src/data/interest-registry.json**. VIP/Luxury — сервисный сегмент, не дополнительный интерес.

### 9.3. Страна + интерес — этап 03

Пример: **/interests/wildlife/tours/panama/**. Главный вопрос: какие реальные программы, регионы, сезоны и занятия по заданной теме есть **именно в Панаме**? Сравнивать применимые маршруты, логистику, условия наблюдений, ограничения. **Не дублировать** отдельный путеводитель /panama/ и глобальное содержание /interests/wildlife/. В тематическом каталоге страна иногда дополнительная: не выдавать ее за основную географию тура.

### 9.4. Страна + интерес + VIP — этап 04

Пример: **/vip/panama/interests/wildlife/**. Главный вопрос: какие **подтвержденные** премиальные тематические поездки доступны по этому сочетанию, как сравнить их программы, особенности сопровождения, транспорта и адаптации? Писать только про реально подходящие товары и проверенные опции. **Запрещено** механически склеивать общий VIP-текст с гидом по стране и общей статьей об интересе.

Важная техническая особенность: VIP-подборка в GitHub формируется по названиям и ценовым показателям, а не по наличию 5* отеля/персонального гида/яхты. **Факт попадания в VIP-раздел не доказывает конкретный уровень сервиса.** Не обещать услуги или условия без явного подтверждения в программе.

### 9.5. Туры, VIP, маршруты — этап 05

| Страница | Главный вопрос | Не повторять |
|---|---|---|
| /tours/ | Как выбрать путешествие по Латинской Америке из всех доступных маршрутов, длительности, форматов | Общие путеводители по странам |

| Отдельный /<country>/tour/<slug>/ или /multi-country/tour/<slug>/ | Для кого подходит тур, особенности нагрузки/сезона, выбор вариантов, практика и FAQ по **этой программе** | Дословное повторение itinerary, lead, включенных услуг |

Обычный каталог туров **содержит в том числе VIP-туры**; отдельного каталога «не-VIP» нет. Не выдавать обычные каталоги за выборку без VIP. Если подходит один тур, полезное компактное сравнение лучше искусственного текста на 15 000 знаков.

## 10. Откуда брать факты и что категорически нельзя придумывать

### 10.1. Коммерческая и ассортиментная конкретика — только GitHub Ada Tours

**Строго из действующих сущностей и логики сайта**, не из поисковой выдачи и чужих сайтов:

- Какие есть туры, места, экскурсии, интересы и VIP-подборки, какие именно маршруты входят в текущий каталог.
- Цены, валюта, сроки, даты, включенные услуги, название и категория отелей, частный/групповой формат, трансферы, гиды, посещаемые места, экскурсии, фактические опции.
- Подтвержденные свойства сервиса Ada Tours, условия и ограничения. Ни один атрибут нельзя выводить из названия «Luxury» или отнесения тура к VIP.

Текущий структурированный каталог и активные production MD имеют приоритет над старыми source-index срезами. Архивные/черновые объекты не использовать для заявления об активном предложении. Цену за группу не выдавать за цену на человека.

### 10.2. Энциклопедическая и природно-географическая фактура — знания модели и надежный интернет

История, культура, география, геология, природа, климат, происхождение названий, причины окраски гор, особенности национальных парков, сезонные явления и метеоданные можно самостоятельно исследовать. Предпочитать официальные, научные, профильные источники, сопоставлять спорные сведения. **ChatGPT пишет самостоятельно без ожидания Анны**: недостаток сведений о самом продукте решать адресным изучением GitHub, а не просьбой к сотрудникам придумать ответ.

Визовые правила, транспортные расписания, входные билеты, нормативы, режим работы парков и подобная динамика требуют проверки актуальности и даты. При отсутствии надежной проверки не превращать предположения в факты.

**В публичном тексте не размещать вообще никаких внешних ссылок.** Рабочие внешние источники и дату обращения сохранять в отдельной служебной provenance-записи, которая никогда не рендерится в HTML. Внутренние ссылки, напротив, широко использовать, **только с осмысленными текстовыми анкорами**, на действующие канонические URL adatours.ru. Размещать ссылки **в соответствующих абзацах и перечислениях, где назван объект или интерес**, а не только общей подборкой в конце текста. Без пустых ссылок, «нажмите здесь», голых URL и архивных целей.

## 11. Динамические переменные вместо устаревающей конкретики

Все поддающиеся надежному расчету из текущих данных **количества туров, экскурсий, мест, минимум цены, диапазоны длительности, названия и ссылки связанных туров** по возможности вычислять при **каждой статической сборке Astro** из актуального опубликованного ассортимента. Не сохранять в MD «5 туров», «17 экскурсий», «от $3218», если после появления нового тура это число потребует переписывать статью.

Обязательные правила:

- Счетчик относится к **полному** соответствующему каталогу, а не к первым 10 записям пагинации. Использовать те же фильтры по стране, дополнительным странам, интересу, VIP и архиву, что применяет сам сайт.
- Русские числа должны возвращаться с правильными падежами и прилагательными: «1 тур», «2 тура», «5 туров», «1 VIP-маршрут», «3 VIP-маршрута».
- Цены показывать только при действительно сопоставимой валюте и базе цены (за человека/за тур/за группу). Не смешивать USD и EUR, не выводить фиктивную «от» из неполных данных; условные предложения при отсутствии расчетного значения не отображать.
- Постоянные энциклопедические величины (высоты, исторические даты, климатические нормы за определенный период) оставлять проверенными фиксированными данными с источником, а не вычисляемыми счетчиками.
- При выводе данных конкретных связанных туров выбирать ссылки и ID **из действующих объектов**, избегая мертвых ссылок после изменения каталога.

**Действующий синтаксис вычисляемых переменных и условных блоков:**

~~~markdown
В каталоге представлены {{catalog.toursCountPhrase}}.
{{#if catalog.hasComparableUsdPrice}}
Стоимость программ начинается от {{catalog.minUsdPriceLabel}}.
{{/if}}

Выбрать маршрут поможет [каталог туров по Боливии](/bolivia/tour/).

{{catalog.tourTable:tour_id_one,tour_id_two}}
~~~


**Поддерживаемые переменные:** `catalog.toursCount`, `catalog.toursCountPhrase`, `catalog.placesCount`, `catalog.placesCountPhrase`, `catalog.excursionsCount`, `catalog.excursionsCountPhrase`, `catalog.hasTours`, `catalog.hasPlaces`, `catalog.hasExcursions`, `catalog.hasDurationRange`, `catalog.minDurationDays`, `catalog.maxDurationDays`, `catalog.hasComparableUsdPrice`, `catalog.minUsdPriceLabel`, `page.title`, `page.countryName`, `page.themeName`. Таблица по реальным tour ID: `{{catalog.tourTable:tour_id_one,tour_id_two}}` (от 1 до 12 ID, все должны входить в актуальную подборку). Весь контент пересчитывается при каждой штатной сборке Astro. Условные блоки поддерживают форму `{{#if catalog.hasTours}}...{{/if}}`; вложенные `if` не поддерживаются. При неизвестных переменных сборка падает с явной ошибкой, а не публикует `{{...}}`.

Должны поддерживаться: текущие количества туров/мест/экскурсий с правильными словоформами, фильтры выборок, длительность, ценовые поля при наличии оснований, название страны/интереса и таблицы по реальным tour ID с динамической стоимостью и длительностью. Синтаксис выше — **контракт будущей реализации, он пока не обязательно работает**. Если renderer отсутствует, нельзя публиковать сырой текст с {{...}} или объявлять коммит MD появлением статьи на сайте. Парсер должен быть безопасным, без выполнения произвольного кода.

## 12. Верстка, раскрытие, ссылки, FAQ и таблицы

**Один переиспользуемый компонент** для всех типов страниц. Длинный SEO/GEO-текст находится **после основного содержимого страницы и перед единой нижней формой заявки**. У конкретного тура уже существует верхний раскрывающийся lead/body: сохранить его, а новую нижнюю статью делать добавочным содержанием без дублирования программы.

- Вся статья присутствует в статическом **HTML при загрузке**, не подгружается по клику. У сворачивания только презентационная роль; нейросети и поисковики должны иметь возможность прочитать текст без пользовательского события.
- Анонс до кнопки: **полный lead или минимум 7 строк, что длиннее; последние 2 строки с плавным затуханием**, как согласовано на турах. Если статья короткая, кнопку не показывать. При отсутствии специального lead использовать первый осмысленный анонс.
- **Грамматически правильная контекстная подпись кнопки**: «Подробнее о VIP-турах в Боливию», «Подробнее о турах в Панаму», «Подробнее об экскурсиях в Рио-де-Жанейро», «Подробнее о природе Коста-Рики» и т.п. Никакого универсального «Подробнее о путешествии» для всех каталогов; падежи и предлоги уточнять для каждой страницы, не собирать строку слепой конкатенацией.
- Один H1 на странице (остается в hero). Внутри статьи H2/H3, короткие смысловые абзацы, списки, выделения и таблицы. SEO/GEO-текст **не должен создавать дополнительные картинки, фотографии, галереи, баннеры или их новые URL**.
- FAQ приветствуется, обычно 4–8 содержательных вопросов, но **не обязателен**. Формулировать вопрос естественно, ответ начинать прямым выводом, затем подробностями; не копировать из основной статьи. Внутри уже раскрывающейся статьи вторые вложенные аккордеоны FAQ не нужны. Не полагаться на FAQPage как на гарантированный расширенный результат Google.
- Таблицы сравнения маршрутов и продолжительности — по подтвержденным продуктам, их меняющиеся числа динамические. **Температура по месяцам** допустима при реально проверенной климатической норме **конкретного города/региона**, с указанием периода, единиц (°C/мм), характерного пространственного охвата; не придумывать цифры, не выдавать среднее одной станции за всю страну. На мобильных **обычная сравнительная таблица должна по возможности помещаться целиком без горизонтального скролла**; скролл сохраняется как резерв для действительно широких числовых таблиц. Правила компактного наполнения ниже.
- Внутренние ссылки в Markdown оформлять вида [VIP-туры в Панаму](/vip/panama/) с понятным анкором, проверенным canonical и смысловой причиной перехода. **Давать ссылки на объекты и тематические страницы непосредственно по ходу рассказа**, не прятать их в отдельный завершающий блок. **Никаких внешних ссылок в статье**.
- Кнопки должны работать клавиатурой, использовать состояние aria-expanded / aria-controls и иметь действие «Свернуть». При отключенном JS полезный текст должен оставаться доступным.
- **На /page/2/ и последующих сам компонент не добавлять в HTML.** Не заменять это скрытием блока через CSS или noindex, не дублировать SEO-текст на страницах пагинации.
- Не менять существующие title, canonical, H1, URL, сортировку туров или структуру каталога ради добавления статьи.

**Мобильные таблицы: проектировать содержимое под экран телефона, а не надеяться на скролл.**

- Исходить из **примерно 300–340 CSS px доступной ширины статьи** на распространенном мобильном экране; на маленьком телефоне места еще меньше. Это ориентир для редакторской компактности, не требование фиксировать ширину в Markdown или менять общий компонент.
- **По умолчанию делать 2 столбца:** короткое название региона/объекта/параметра и короткое главное отличие. Заголовки — обычно 1–3 слова, содержимое ячеек — короткие словосочетания, а не абзацы и полные предложения. Перенос на несколько строк допустим, но длинные пояснения увеличивают требуемую ширину.
- **3 столбца** оставлять только при действительно коротких значениях (сезон, число дней, цена, 1–3 слова) и кратких заголовках. Таблица вида «Регион / Зачем ехать / Что предусмотреть» с длинными текстами во всех трех колонках, как в большом гиде по Бразилии, для мобильного **слишком широкая**: делать «Регион / Главное», а логистику, погоду и ограничения раскрывать в следующих абзацах. Можно разделить одно сравнение на две узкие таблицы, если факты нельзя потерять.
- Если материал требует 4+ столбцов или много текста, сначала попробовать компактные подразделы либо список «объект → особенности», затем 2-колоночную таблицу. Горизонтальный скролл допустим **только если это действительно полезная широкая матрица** (например, 12 месяцев с подтвержденными показателями), где разделение испортит сравнение. Не сокращать важные факты и единицы измерения ради визуального приема.
- **Проверка перед сохранением статьи:** мысленно оценить таблицу при ширине контента около 320 px. Если заголовки и текст не могут разумно уместиться без горизонтального скролла, сократить формулировки или перестроить таблицу. Не вставлять внутрь Markdown HTML, `<br>`, CSS, ручные ширины, изображения или неразрывные длинные строки ради верстки. Читабельность важнее количества столбцов.

**Контекстная внутренняя перелинковка — обязательная часть каждого SEO/GEO-текста.**

- Во время работы над выбранным разделом проверять канонические адреса **упомянутых** активных объектов по актуальным данным GitHub: Country, Destination, Tour, Excursion, каталоги по стране, интересу и VIP. Использовать уже известные маршруты сайта и точные записи, **без отдельного массового аудита всех страниц**. Давать ссылку при первом **содержательном** упоминании, например `[Рио-де-Жанейро](/brazil/place/rio-de-janeiro/)`, а не ждать конца статьи с фразой «Подробности на странице...».
- Для **темы в конкретной стране** отдавать предпочтение странице **страна + интерес**, когда она существует и соответствует смыслу. Например, в абзаце о бразильской культуре уместно предложить `[культурно-исторические туры по Бразилии](/interests/culture-and-history/tours/brazil/)`. Этот URL показывает **подборку туров**, поэтому анкор не должен обещать энциклопедический путеводитель по истории страны. Для общих вопросов об интересе без привязки к стране уместна самостоятельная страница интереса.
- **Что связывать:** реальное место → каноническая страница Destination; самостоятельное занятие/экскурсия → Excursion; конкретная программа → Tour; сравнение программ → соответствующий каталог; природный или культурный тип путешествия → релевантная тема/тема + страна. Не подменять конкретное место общим каталогом, если существует его страница; не путать страницу места с каталогом его экскурсий.
- **Ссылки в перечислениях — на каждый доступный объект.** Если в одной фразе, пункте списка или сравнении названы несколько самостоятельных мест, экскурсий, туров или тематических подборок, проверить канонический URL **каждого**. Все объекты с существующими активными и релевантными страницами оформить отдельными ссылками; не останавливаться после первой ссылки в перечислении. Например: `[Сан-Паулу](/brazil/place/sao-paulo/), [Ору-Прету](/brazil/place/ouro-preto/), [Парати](/brazil/place/paraty/)`. Если подходящей опубликованной страницы нет, название остается обычным текстом; URL не придумывать.
- **Нет количественных ограничений на ссылки, в том числе повторные.** Не применять правила «один URL — одна ссылка на статью», «одна ссылка на раздел» или «не более 1–3 ссылок». Один и тот же URL можно повторно связать в другом абзаце, разделе или самостоятельном перечислении, когда ссылка полезна читателю в новом контексте. Наличие ссылки выше по тексту не является причиной оставить новое содержательное упоминание без ссылки.
- **Плотность определяется содержанием.** В каждом разделе связывать упомянутые опубликованные объекты и подходящие тематические страницы там, где переход помогает читателю. Несколько соседних ссылок **на разные объекты** в перечислении — нормальная навигация, а не ссылочный спам. Не добавлять ссылки на случайные слова и не подменять точную страницу объекта общим каталогом.
- **Избегать только бессмысленного дублирования** одного и того же перехода в соседних фразах, если он уже очевиден и повтор не добавляет пользы, и искусственного повторения анкоров ради SEO. Это не ограничивает полезные повторные ссылки на тот же URL в разных контекстах и не отменяет требование связать каждый доступный объект в перечислении.
- Ссылки должны вести на **существующую активную каноническую страницу**, а не на архив, резерв без MD, пустой фильтр, редирект, страницу пагинации, URL самой статьи или догадку по названию. Если реальной релевантной цели нет — оставить упоминание без ссылки. Внешние источники остаются только в provenance; в публичном Markdown разрешены лишь внутренние относительные пути.

### 12.1. Файлы статей и служебная информация

Писать по одной статье на URL в **`data/seo-geo/articles/<canonical-segments>/index.md`**. Пример: `/vip/bolivia/` → `data/seo-geo/articles/vip/bolivia/index.md`; `/country/` → `data/seo-geo/articles/country/index.md`. Точный путь вычисляет `seoGeoArticleFile()` из `src/lib/seo-geo.mjs`. Frontmatter содержит targetPath (строгий canonical), kind, status (`draft`, `approved`, `paused`), buttonLabel и lead. **Без `status: approved` статья не попадает в HTML.** Указатели на внешние источники и даты проверки хранить отдельно, не в рендеримом body. Неполный черновик сохранять как `draft`.

Пример полей:

~~~yaml
---
targetPath: /vip/bolivia/
kind: vip_country
status: approved
buttonLabel: "Подробнее о VIP-турах в Боливию"
lead: "Выбирайте маршруты по Боливии с учетом высоты, сезона и времени на переезды."
---
~~~

В body писать ясный текст с H2/H3, таблицами и FAQ, использовать подготовленные динамические переменные. Не считать сам по себе новый MD опубликованной страницей: нужен общий renderer и успешный deploy.

## 13. Глубина материалов, качество и отсутствие искусственного объема

Ориентиры по **знакам с пробелами** (не квоты):

| Тип | Ориентировочный диапазон |
|---|---|
| Страна, глобальный интерес, /vip/, /multi-country/ | 9–18 тыс. и более при достаточной фактуре |
| Каталог туров страны, VIP+страна, страна+интерес | 7–14 тыс. |
| VIP+интерес, VIP+страна+интерес, другие узкие каталоги | 4–10 тыс.; при небольшом ассортименте меньше |
| Индивидуальный тур, место, экскурсия | 4–12 тыс. по объему реально полезных сведений |
| Каталог с одним подходящим продуктом | Столько, сколько имеет смысл; не растягивать ради SEO |

Типичная структура: **конкретный ответ читателю в первых абзацах → 4–7 смысловых разделов с уместными внутренними ссылками прямо в тексте → сравнение альтернатив и выбор → практические нюансы/ограничения → FAQ по необходимости**. Не сводить перелинковку только к заключительному списку ссылок. Не ставить формальное количество заголовков выше здравого смысла.

Писать по правилам docs/workflows/writing-rules.md: живой русский, отсутствие канцелярита, псевдоэкспертности, повторов, искусственного набора ключей, выдуманных преимуществ и обещаний. Никаких лишних «заключений», абстрактной воды или механического переписывания других URL. Для нейросетей особенно ценны законченные самостоятельные ответы, конкретные сравнения, проверяемые факты, условия и ограничения; **не обещать** гарантированных AI-цитат или роста ранжирования.

## 14. Bootstrap единого движка и границы будущих чатов

**Реализовано в репозитории:** `src/components/editorial/SeoGeoSection.astro` (адаптивное раскрытие и затухание), `src/lib/seo-geo-articles.ts` (загрузка по canonical, вычисляемые данные и Markdown), `src/lib/seo-geo.mjs` (frontmatter, интерполяция, защита ссылок и HTML), подключение в `src/layouts/BaseLayout.astro`. Тесты: `tests/seo-geo.test.mjs`, после Astro build — `scripts/check-seo-geo-pages.mjs`. Нужный код включен в штатный `npm run build`. Одна статья — один `<canonical>/index.md`; новые статьи не требуют новых компонентов или изменения других layouts. Задача __bootstrap__ нужна снова только при фактическом отсутствии этой инфраструктуры.

1. Привязку targetPath → Article MD к существующим Astro layouts и каталогам; вывод только на page 1, после основного содержимого, до формы.
2. Универсальный адаптивный компонент раскрытия с HTML текстом без подгрузки по клику, русскими кнопками, аккуратным затуханием, доступностью и отображением Markdown-таблиц.
3. Parser разрешенных переменных и условных секций, использующий текущие getCollection, существующие helpers ранжирования, географии, интересов и VIP; без eval. Отсутствующие значения не порождают ложные цены/количества.
4. Проверки: правильный canonical, не page/N, ровно один SEO/GEO-блок на URL, ни одной внешней ссылки и изображения внутри статьи, все анкоры и пути действуют, ни одной нераскрытой переменной в HTML, отсутствие архивных и draft-материалов в публичной выдаче.
5. Один успешный build/deploy общего SEO-пакета из мастер-чата. Только мастер-чат после подтвержденной публикации отмечает `published`.

Другие чаты **не модифицируют** общие компоненты, пока __bootstrap__ занят. После завершения этой технической задачи авторам достаточно создавать SEO-статьи в утвержденном формате и сохранять их в staging; публикует только мастер-чат. При разработке новых возможностей снова использовать атомарную блокировку __bootstrap__, но не проходить этот этап перед каждым SEO-текстом.

## 15. Точечная приемка и обязательная актуализация статусов

Перед включением каждой статьи проверить:

1. URL существует как правильный canonical, активен, не /page/N/ и не архив.
2. Главный поисковый интент четко отличается от соседних страниц; нет пересказа их больших блоков.
3. Все коммерческие факты строго из GitHub Ada Tours. Никаких выдуманных цен, услуг, гарантий, вариантов размещения, продолжительности.
4. Энциклопедические факты проверены, внешние источники записаны только в служебном provenance, **не** в публичном HTML.
5. Изменяемая числовая информация динамическая там, где это возможно; грамматика и валюты верны.
6. Внутренние ссылки **распределены по содержательным абзацам**; в перечислениях отдельно связаны **все** упомянутые объекты с активными релевантными страницами, включая второй, третий и последующие элементы. Ссылки на один URL можно повторять по смыслу без числовых лимитов. Анкоры соответствуют типу цели; URL активные и канонические, нет ссылок на несуществующие или архивные объекты, внешних ссылок и бессмысленного дублирования переходов рядом.
7. Нет дополнительных картинок; H2/H3, списки и FAQ содержательные. **Обычные текстовые таблицы ориентированы на 2 коротких столбца и мобильную ширину 300–340 px**, без вынужденного горизонтального скролла; 3 столбца — только с краткими значениями, больше — только для оправданных матриц. Все факты сохранены.
8. Контекстная кнопка правильно склоняется и раскрывает текст, полный материал доступен статически.
9. Нет дублирования на пагинации и соседних страницах, все ссылки и переменные разрешаются при сборке.
10. Сохранены чужие claims, work, статусы, старые страницы и история; меняются только затронутые JSON, MD и точные строки Sheets.

**После коммита автора**: подтвердить remote staging SHA, записать `prepared` и «Ждет публикации», путь MD и время; сборки/деплоя автор не запускает. **После публикации мастер-чатом**: найти URL в точном JSON фазы и колонке E Sheets, записать `published`, путь MD, дату и полный SHA успешного deploy. Если Actions не подтвержден, оставить `prepared`. Если таблица недоступна, сохранить конкретное отложенное отражение и **не переписывать материал заново**.

**При появлении новых туров, стран, мест, экскурсий и непустых фильтрованных каталогов**: пополнять реестр строками по правильным фазам, исключать /page/N/, сохранять исчезнувшие и архивные записи. Актуализировать availability, но **не сбрасывать** редакционный статус. При появлении нового canonical вследствие миграции старый URL оставлять исторической строкой. Отдельные MICE/DMC и прочие специальные страницы не добавлять.

**Отчетность пишущего чата v2.5**: обязательны стартовое сообщение до инструментов, фактический список URL после CAS, отчет сразу после каждого из трех удаленных content-коммитов и итог после всей тройки. В итоговом отчете указать зарезервированные URL (или фактически доступное число), статус и articlePath каждого, staging SHA каждого завершенного текста, «Ждет публикации»/блокеры, истечение оставшихся резервов и следующего кандидата. Никакой 10-минутной отсечки; после тройки **ждать «дальше»**. **Отчет мастер-чата**: количество готовых URL, один пакетный main-коммит и Actions/deploy, адресные отложенные статусы. Авторам запрещено сообщать «опубликовано» до мастер-деплоя.


**Обязательная методика для каждой страницы сочетания стран.** Анализировать **каждую из выбранных 2–4 стран как единое путешествие**, а не как независимые путеводители. Давать проверяемую конкретику о въезде: разные визы, возможные однократные/многократные въезды, требования транзита, действительность паспорта, прививки/медицинские правила — **только с указанием гражданства и даты проверки, по официальным источникам**; не обещать одну визу для нескольких стран без подтверждения. Отдельно сравнивать местные валюты, применимость USD, обмен, комиссии, работу иностранных/российских карт и ограничения платежей — без общих гарантий и неактуальных курсов. Описывать различие погоды, температур, осадков, высот и сезонов **в местах и в даты маршрута** (например, тропическая Бразилия и холодная Антарктида), что взять из одежды, как упаковать багаж и какие ограничения у внутренних перелетов и экспедиций. Обязательно рассматривать аэропорты, логистику границ, стыковки, риски опозданий, страховку, допустимый темп и возрастные/медицинские ограничения. Польза должна быть уникальна для **конкретной комбинации**; противопоставлять альтернативные маршруты и длительности, аккуратно ссылаться на действующие туры без архива. Ответы и FAQ должны закрывать тревоги покупателя, а не повторять рекламные тезисы. Писать по `docs/workflows/writing-rules.md` с датами проверки меняющихся государственных/платежных правил в provenance.

**Допущение по операционной практике Ada Tours (утверждено 15.10.2026).** Ada Tours — принимающий туроператор с комплексными мультистрановыми программами; **если внутренних описаний услуги не хватает, разрешено обоснованно моделировать обычную профессиональную работу крупного мультистранового туроператора**, а не откладывать SEO-статью до ответов сотрудников. Объяснять от лица Ada Tours, как организация поездки решает конкретные сложности: заранее проверяет маршрут и условия въезда для гражданства клиента, помогает составить список документов и спланировать сроки; выстраивает очередность стран и разумные стыковки, согласует наземные трансферы, отели и местных гидов; консультирует по валютам, возможностям оплаты и резервным способам; помогает подготовить одежду и багаж для разных климатических зон; согласует при необходимости более спокойный темп и резерв времени. Это **разрешенные типовые сценарии решения задач**, а не требование искать отдельное подтверждение от Анны для каждой привычной операции. Формулировать конкретно, по делу, применительно к выбранным странам; уместны «Ada Tours помогает разобраться», «подбирает последовательность», «согласует», «предупреждает», «подсказывает, что проверить» и примеры практического процесса. Нельзя выдавать за установленный факт **неподтвержденные эксклюзивные обещания**: гарантию выдачи виз или въезда, наличие собственной визовой службы, самостоятельный обмен денег, оплату иностранной картой определенного банка, бесплатную экипировку, оформление страховки «включено», подтвержденные партнерские договоры, фиксированные условия и тарифы. Законы, визовые режимы, платежная доступность, требования здоровья и правила въезда — факты высокого риска и **всегда проверяются по актуальным официальным источникам**. Где есть неопределенность конкретного формата или персональные условия клиента, описывать проверяемую процедуру согласования, а не придумывать окончательный результат.

### 15.1. Обязательный автоматический preflight ссылок (15.10.2026)

Перед статусом `prepared` выполненный staging preflight обязателен. Для адресной проверки командой Node использовать `node scripts/preflight-seo-geo-links.mjs --article data/seo-geo/articles/<canonical>/index.md`; авторский GitHub-цикл автоматически выполняет ее на push через `.github/workflows/seo-geo-preflight.yml` и публикует commit status `ada/seo-link-preflight`. Валидатор использует production MD и действующие данные `main` и функции формирования каталогов; source-index и SEO/GEO registry сами по себе не являются доказательством существования публичной страницы. Недопустимы архивные/неопубликованные объекты, пустые пересечения, редиректы, самоссылки и пагинация. При новом переходе в `prepared` GitHub Actions дополнительно сверяет SHA коммита, Git blob статьи и успешный статус прежней проверки. Нельзя писать `prepared`, пока проверка не успешна. После обновления каталогов мастер повторно сверяет URL перед своим единственным main-коммитом; штатная HTML-проверка на деплое остается последним защитным барьером.
