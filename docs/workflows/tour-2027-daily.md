## 2. Обязательный проход обнаружения

1. Прочитать текущие инструкции, опись и предыдущий журнал. Не сбрасывать очередь неоконченных программ. Использовать реальные Drive file ID и сохраненные данные; `driveSnapshotAt` — дата снимка описи, не доказательство последней успешной публикации каждого Word.
2. Обойти корень 2027 и **все** подпапки рекурсивно. Для каждого folder ID перечислить все прямые элементы с продолжением страниц по токену, включая новые подпапки, даже если прямой `list_folder` показал только первые 100. Использовать подключенный Google Drive; подтвердить, что получен конец каждой выдачи. Сохранять `folderId`, путь папки, `fileId`, имя, `mimeType`, `modifiedTime` и доступную версию/checksum. Исключить удаленные файлы; не повторять тот же Drive file ID из нескольких путей.
**Защита рекурсивного обхода от лимита Code Mode (17.10.2026).** Нельзя перечислять все 25+ папок одним вызовом `functions.exec`: число обращений к подключенным инструментам внутри одного вызова ограничено, даже при параллельной работе. Обходи папки небольшими пачками (ориентир 4–6 папок на вызов) в нескольких последовательных вызовах; переноси неизмененные `folderId`, `pendingFolderIds`, собранные `fileId` и счетчики между ними. `list_folder(top_k=100)` не подтверждает завершение постраничной выдачи, если результат достиг лимита; для такой папки при необходимости используй `Google_Drive.search` с фильтром по точному `parent folder ID` и непрерывным `next_page_token` до конца либо пометь ее `partial` с причиной. При длительном обходе сохраняй компактный промежуточный курсор в GitHub-журнале через безопасное обновление с ожидаемым SHA (служебный commit `[skip ci]`), чтобы повтор не начинал уже пройденное с нуля. До проверки всех папок и страниц нельзя объявлять `no_changes`. При технической ошибке сохрани обнаруженное и конкретный блокер, сообщи о сбое; **не отключай и не перепланируй саму автоматизацию ChatGPT изнутри scheduled-запуска**. Следующий день продолжает недоделанную проверку по журналу.

3. Сравнить все найденные Word/DOCX с текущей описью по **Drive file ID**, именованной программе, маршруту, длительности, услугам, дате модификации и при содержательном сомнении — полному тексту, таблицам и SHA-256. Для новой/изменённой бинарной версии DOCX отдельно сравнить содержимое `word/media/*` (отсортированные имена и SHA-256), подписи и их связь с программой: одинаковый текст НЕ исключает замену фотографий. Сохранять `textSha256`, `embeddedMediaSha256`, checksum/версию DOCX и метод извлечения. Одинаковая программа под новым именем, копия, перемещение или изменение метаданных без фактической правки не создают новый Tour или новое задание на публикацию. Отсутствие предыдущего media snapshot отметить как первоначальную базу, не выдумывать факт замены всех фото.
4. PDF и другие нетуровые документы тоже фиксировать в описи обнаружения и классифицировать отдельно. PDF с самостоятельной программой отмечать как `needs_pdf_review` до подтверждения источника и подходящего процесса импорта; файлы билетов и общие прайсы не выдавать за новый Tour. Не замалчивать такие файлы, но и не создавать из них тур автоматически.
5. Новые подтвержденные программы и реальные редакции поставить в устойчивую очередь `openQueue` журнала с точным Drive ID, source version, `programKey`/Tour ID и этапом. У документа с измененным `modifiedTime` сверить **текст**, прежде чем объявить содержательное изменение. Если документ неполный или соответствие неоднозначно, указать `REVIEW` по конкретному файлу; не угадывать, не создавать дубли.
6. Завершение обхода фиксировать только если перечислены **все** папки и страницы. При ошибке в части папок установить `scanStatus: partial`, перечислить пропущенные ID и не утверждать «изменений нет». Последняя полная сверка должна оставаться прежней до успешного полного обхода.

## 3. Выполнение очереди

При КАЖДОМ запуске сначала завершить полный обзор папок 2027 и сохранить обнаруженные новые версии, а затем последовательно обрабатывать очередь: сначала ранее незавершенные, затем новые изменения. Большой незавершенный тур не должен препятствовать ежедневному обнаружению файлов. Для каждого файла сохранять стадии:
`detected → word_verified → relations_ready → interests_verified → destinations_classified → media_ready → mobile_heroes_ready → seo_facts_ready → seo_voice_ready → catalogues_ready → content_committed → actions_deployed → geo_ready → sheets_synced`.
Имеющееся готовое не пересоздавать. `done` допустим только после всех обязательных проверок текущего источника, реальной публикации контента/адресного GEO и подтверждённого чтением обновления всех затронутых таблиц. Исторические `published`, `rewritten`, `REPLACED`, `READY` не подтверждают текущую редакцию автоматически.

- Для действующего тура сохранить stable ID, canonical URL, полную программу, цены и условия, изменить только подтвержденное свежим Word. Для действительно нового продукта создать Tour; при сомнении оставить `REVIEW` без дубля. Не возвращать архивную копию при наличии активной замены; архивирование/разархивирование только по действующему `archive.md`.
- По `tour-from-word.md` довести необходимую географию, самостоятельные Destination/Excursion, двусторонние связи, интересы, изображения до готового состояния. Изображения Word улучшать/отсутствующие генерировать через GPT Image только при подтвержденном контексте. Сохранять уже полученные фото. Не считать одну нарезанную картинку независимыми фотографиями.
- Новые бинарные медиа в Git **запрещены**: прямой S3 upload на `img.adatours.ru` только по `direct-s3-upload.md`, с действительными receipt и записями provenance/реестра GPT Image. Не записывать фиктивный URL в MD и не заявлять upload, пока не проверен S3.
- Один согласованный пакет content-изменений, один штатный build/deploy; результат проверять по своему SHA и неизмененным целевым файлам. После успеха пакетно обновить только нужные строки Google Sheets, сохранять историю и столбец `Принята`.
- Если окружение конкретного scheduled-запуска не предоставляет Work-компьютер, GPT Image, Google Drive или прямую S3-загрузку, не делать ложную публикацию и не использовать Git binary fallback. Сохранить точный `blocked` + `missingCapability`, фактически завершенные стадии и очередь; доступные стадии (обход, сопоставление, учет) завершить. Не приглашать пользователя заново подтвердить уже разрешенную публикацию, но явно назвать техническое ограничение.

### 3.1. Область зависимостей и исходные факты

По подтверждённому Word сформировать адресный план: Tour; реально созданные/изменённые Excursion и Destination; все переиспользуемые места/экскурсии; окончательные источники фото; hero использования; затронутые SEO URL и GEO IDs; изменившиеся каталоги; стабильные ключи строк таблиц. Сохранить ID, source version и SHA каждого затронутого файла. Не превращать весь исторический backlog сайта в задачу одного тура.

Сверять **каждый день**, включая последний, все таблицы, включённые/дополнительные услуги и альтернативы. Если блок перенесён в `excursionRef`, доказать, что весь смысл сохранён в фактически подключённом MD. Проверка количества дней или успешный build не обнаруживает пропущенную обзорную экскурсию. Самостоятельность экскурсии определять по `tour-excursion-linking.md`; совпадение города недостаточно для переиспользования продукта с другим маршрутом. Отсутствующие самостоятельные экскурсии создавать из подтверждённого Word в текущем пакете; не прикреплять похожую экскурсию с лишними услугами.

Для географии сравнить имена/aliases в рамках страны и использовать существующие stable IDs. Внести посещаемые достопримечательности внутри полного текста дней и экскурсионных вставок, а не только города ночёвок. `destinations` содержит всю подтверждённую географию; `routeDestinations` — только гарантированную основную. Видимые вдали объекты, рекламный перечень доступных развлечений и невыбранные альтернативы не становятся обязательными посещениями. MD, exact source entry и compact catalog обновляются согласованно. Обратные связи строит сайт, вручную править соседние туры не нужно.

### 3.2. Интересы и классификация мест

Использовать текущий закрытый registry (на дату версии — 15 ID), а не копию списка из старой инструкции. Для Tour заново оценить 1–2 основных и дополнительные интересы по фактической программе. `theme_nature` и `theme_wildlife` независимы: упоминание птиц/обезьян на обычной прогулке не равно самостоятельному наблюдению за животными. Собственные темы Excursion/Destination не наследовать от Tour. Все изменённые метки одновременно записать в MD, entry и compact catalog.

Каждое новое место/резерв получает `destinationType` из действующего `destination-taxonomy.mjs` и независимый `navigationRole: hub|sight`. Для существующих мест использовать утверждённую классификацию, не переопределять её по теме текущего тура. Проверить равенство актуального MD, canonical destination catalog, exact entry и compact catalog. `npm run check:relations -- --data-only` проверяет эти зеркала; штатный build дополнительно проверяет реальные HTML-связи, фильтры, taxonomy и Schema.org.

### 3.3. Фотографии и мобильные hero

Сначала получить список уникальных кадров всей программы с учётом hero, дней и вставленных экскурсий. Original/enhanced/crop одного кадра — один кадр. Проверить фактическую запись `method: gpt-image` для каждого используемого изображения; имя `enhanced`, WebP и S3 receipt сами по себе недостаточны. Подходящий уже улучшенный снимок переиспользовать. Новые embedded-фото улучшаются через GPT Image с конкретным исходником; отсутствующий кадр генерируется как новая сцена с честным provenance. Техническая конвертация не заменяет GPT Image.

**После окончательного выбора/генерации/замены горизонтального hero сразу выполнить мобильный этап.** Определить actual page+source+profile+manualObjectPosition; проверить прежний focus; посмотреть оригинал, выбрать фокус, сделать отдельный crop без перерисовки и посмотреть cover-превью для геометрии этого блока. У людей/животных приоритет головам и лицам. При переиспользовании source/crop проверить неизменный source hash и профиль: запись для другой страницы/другого источника не подключается автоматически. Новый URL hero после GPT Image инвалидирует старую mobile mapping, даже если название страницы прежнее.

Сохранить `sourceSha256`, crop, focusReason, `visualQA`, размеры/хеши вариантов и подтверждённые direct-S3 receipts; адресно дополнить `src/data/media/mobile-hero-registry.json`. Горизонтальный оригинал остаётся для широких экранов; обычные фото дней и галереи не обрезать. Если новый производный каталог заимствует готовый hero, проверить, что существующий crop подключается к его реальному page/profile; достаточно повторного использования подтверждённых файлов, новая генерация не требуется. При видео сохранить `hero-video-covers.md`: постер первого кадра выбранного ролика и мобильное фото — разные ветви.

### 3.4. Два прохода SEO и актуальный GEO

SEO-план включает собственные страницы новых/изменённых сущностей, статьи с содержательными ссылками на изменённую программу и реально изменившиеся каталоги. Для каталогов сравнить old/new membership и доступность: изменение цены тура не означает обязанность переписать все общие статьи. Новый непустой каталог регистрируется и получает полноценный текст в текущем логическом цикле. Новые статьи с самого начала писать от лица Ada Tours; второй этап всё равно проверяет готовый результат.

**Первый проход — факты и ссылки:** маршрут, услуги, цены, даты, таблицы, перелёты, транспорт и состав подборки. Сравнить Word с соответствующим текстом, сохранить hash окончательного файла и решение `created|updated|verified_unchanged`. **Второй проход — голос:** проверить именно этот итоговый hash на прямой голос Ada Tours, читабельные мобильные таблицы, FAQ и контекстные ссылки. Не пропускать второй проход по историческому `work: rewritten`; не применять voice-only валидатор к изменению фактов, которое он по замыслу запрещает. Не занимать чужой live claim; сохранять ожидающую зависимость и продолжить независимые стадии. Даты первых публикаций и редакционную историю не затирать.

После успешного Pages deploy выполнить адресную фиксацию этих SEO-проверок через `scripts/finalize-tour-seo-review.mjs`: `planTourSeoFinalization` проверяет точные опубликованные bytes статей, provenance и review manifest, фактический успешный run, актуальные main-файлы и оба набора claims. Применить только подтверждённые CAS writes; причины `held` сохранить в очереди. `planTourSeoPublicationMirror` переносит подтверждённый статус в свежий SEO staging, сохраняя его статьи, provenance и чужую работу. У изменённой старой статьи хранить новую проверку в `currentArticleReview`, не выдавая старый `rewriteResultBlobSha` за доказательство новой редакции.

GEO: для новых Country/Destination/Tour/Excursion использовать адресный `schema-geo-new-object.mjs` после фактического creationCommit. Для существенно изменённого существующего Tour/Excursion использовать `scripts/schema-geo-word-revision.mjs` (`inspectWordGeoRevision`, затем `collectWordGeoRevision`) с точным stable ID и фактическим contentCommit по §3.5 `schema-geo-knowledge.md`. Helper проверяет изменённый MD, текущий main, source mirrors и весь гарантированный маршрут, сохраняет прежний immutable payload и ревизию, не перехватывает чужой lease. `new-object` для старого MD не вызывать. Проверять маршрутные связи и существующие внешние идентичности, не выдумывать sameAs туристических продуктов. Текущий schema renderer остаётся единственным; Trip строится из canonical MD и опубликованных Destination, паспорта служат отдельным проверенным семантическим реестром.

`READY` в GEO staging не завершает ночную программу. В этом же логическом цикле выполнить адресную мастер-публикацию требуемых результатов: `publishSchemaGeoAll(..., {ownerId, batchId, jobIds, contentCommit})`, где jobIds включают только созданные/изменённые объекты этого Word-пакета. Все выбранные results обязаны иметь подтверждение обеих GEO-строк Sheets; чужой активный release не запускается и не перехватывается. Подтвердить успешный Pages run/точные hashes, затем GEO-таблицы. Общий content release обычно один; если существующий new-object протокол требует уже опубликованный creationCommit, допустим следующий **один адресный GEO release**. Это обязательная зависимость, а не повод повторить импорт/генерацию или весь чужой backlog. Не объявлять content deploy завершением всей программы до GEO/таблиц.

### 3.5. Производные каталоги и таблицы

`npm run sync:multi-country` вычисляет сочетания 2–4 основных стран (включая подмножества тура из 5+ стран), пересечения с текущими интересами, SEO registry/order, external identity inventory и публичные CSV. Build проверяет реальный HTML; `catalog-registries` после deploy переносит точный опубликованный snapshot в main/staging с сохранением claims и статей. До завершения этого job не считать реестры сохранёнными. Исчезнувшие сочетания сохраняют историю как temporarily_unavailable; новые каталоговые ID не создают самостоятельные SourceIndex сущности или внешние sameAs.

При создании исходных сущностей использовать исправленный `scripts/sync-source-catalogs.mjs`: он сохраняет обе оси Destination и явные пустые route-массивы, признаёт S3-only фото только по валидному ledger. В том же build canonical SEO projection регистрирует новые сущности и связанные каталоги как `queued`, сохраняет редакционную историю и переносит регистрацию в main/staging. `npm run check:runtime-seo-coverage` независимо проверяет полное покрытие действующих канонических страниц. Регистрация очереди не означает готовый текст: затронутые новой программой статьи проходят оба SEO-этапа в этом же задании.

Часовая задача «Каталоги Ada Tours» может быть выключена; ночной цикл **сам** обязан адресно закрыть зеркала. По стабильным ID/URL (номера строк после сортировки ненадёжны) обновить:

| Таблица | Обязательная адресная проверка |
|---|---|
| `Страницы` | Каждый опубликованный Tour/Destination/Excursion и новый каталог; сохранить первую дату и `Принята`; статус уникальности фото дней актуален |
| `Фото` | Все новые/изменённые используемые слоты; method/provenance, `/media/` и действительный CDN URL; для S3-only не писать фиктивный Git binary path; исчезнувшие слоты архивировать |
| `SEO-GEO тексты` | Текущие URL/ID/order, статья, редакционный статус и commit; две проверки относятся к текущему hash, а не исторической надписи |
| `Места` в отдельной книге | Созданные/заполненные резервы, stable ID и фактический статус публикации; сохранить материалы/ручные пометки Анны |
| `GEO очередь`, `GEO результаты`, `GEO публикации` | Адресные job/result/release hashes и подтверждённые статусы |
| `Multi-country + интересы` | Опубликованный fingerprint I2 и завершённый K2 совпадают; K4 — фактическая дата; `Страницы` и SEO строки реально перенесены |
| `Сводка` | Формулы покрывают полный диапазон и новые строки, без ручного удаления старых записей |

Повторно прочитать записанные диапазоны. Сбой одного зеркала оставляет точный `PENDING` и ту же queue entry; следующий запуск повторяет только зеркало, без GPT Image и нового deploy. Даже при нулевой разнице сохранить проверенный диапазон/ключ и hash readback. Пустую применимую таблицу не считать синхронизированной по факту отсутствия инструментальной ошибки.

### 3.6. Исполняемый контроль и сохранение прогресса

Выполнить `node scripts/audit-tour-dependencies.mjs --tour-id <stableId> --baseline-ref <main-SHA-до-Word-изменений>`: он читает актуальные зависимости, сравнивает проекции, media/GPT Image, mobile mappings, SEO и наличие GEO. Сохранённый baseline отличает новые каталоги текущей программы от прежней SEO-очереди, в том числе каталоги экскурсий для резервов мест без собственного MD. После публикации не заменять baseline на новый HEAD. Для Word-вариантов экскурсии передать `--excursion-review <путь-к-реестру-проверки>` с точными hashes Tour/Excursion/Word и явно исключёнными destination IDs. Одно наличие текстового override не отменяет проверку связей и не позволяет автоматически перенести все места базового продукта в тур. Страницы, чей настоящий шаблон не выводит hero, получают явное `no_image`/mobile N/A, а не выдуманную обложку. Это **диагностика**, не генератор и не самостоятельное доказательство правильности смысла Word. Смысловую проверку каждого дня и кадра делает исполнитель.

У каждой новой завершённой после введения v2 программы в существующей `openQueue`/`completedQueue` должен быть `lifecyclePath: data/audits/tour-lifecycle/<programKey>-<sourceVersionKey>.json`. Это детализация той же очереди, не новая параллельная задача. Код `scripts/tour-2027-lifecycle.mjs` хранит точные source/scope fingerprints, targets и evidence по стадиям. Схему и обязательные поля брать из текущих `createLifecycle`, `stageErrors`, `recordStage`, `verifyLifecycle` и их профильных тестов; не изобретать упрощённые receipts. Для медиа хранить hashes отдельно от бинарников, для таблиц — идентификаторы/диапазоны/хеши фактического readback.

Перед content release: `node scripts/check-tour-2027-lifecycle.mjs --receipt=<lifecyclePath> --predeploy`. Перед переносом в completedQueue: та же команда **без** `--predeploy`, после реального deploy/GEO/Sheets. `npm run check:tour-lifecycle` встроен в build и проверяет, что новые завершения не подменены старой сокращённой стадией. Дореформенные записи остаются историей с точными ключами/датами, без приписывания им задним числом v2-проверки.

Статус/receipt не заменяет выполненного действия: `sourceViewed`, успешный upload или Sheets readback фиксировать только после реального подтверждения. Смена source или зависимого файла делает старую проверку непригодной; сохранить историю, повторить только затронутые работы и их проверки. По неизменному source/version повтор идемпотентен: существующие ID, фото, crop, payload и публикацию переиспользовать. Временный сбой не разрешает стирать pending стадии или обходить gate.

### 3.7. Что считать проверенным запуском

Отдельно сообщать: что нашёл полный Drive scan; какие исходные файлы действительно изменились; что исправлено/опубликовано; какие стадии закрыты реальными receipts; какие проверены переиспользованием; что осталось PENDING/REVIEW. Контроль на уже опубликованном Word не называть тестом обнаружения нового файла. Проверка старых GPT Image/crop не является новой генерацией. Успех unit-тестов и локального анализа не заменяет успешный production deploy, а текущий ручной контроль не доказывает, что будущая scheduled-среда предоставит GPT Image и S3.

После каждого запуска обновить `data/audits/tour-2027-daily-state.json` **без потери предыдущих записей и чужих изменений** (CAS/ожидаемый SHA, без force push).
