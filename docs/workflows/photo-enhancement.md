# Ada Tours — улучшение существующих фотографий

**Архив:** перед выполнением применить `docs/workflows/archive.md`. Статус `archived`/запись в `data/catalog-archive.json` исключает объект из массового наполнения и улучшения фото, даже при готовых исходниках. `--all` не отменяет архив. Существующая архивная карточка остается доступной с `noindex, nofollow`.


Адреса объектов задаются `docs/workflows/urls.md`; использовать текущий URL из entry. Смена публичного slug не переименовывает существующие content-файлы, медиа и их реестровые ID.

Версия: 2.3

Дата: 05.10.2026

Канонический документ: `docs/workflows/photo-enhancement.md`

Репозиторий: `alexyakovlev79/adatours.ru`, ветка `main`

Режим: отдельный фотопроход в ChatGPT Work, обычно до 10 фотографий.

## 1. Когда применять

Запросы: «улучши главное фото Аргентины», «улучши фотографии этой экскурсии», «дальше» в согласованной очереди улучшения. Создание страны, места, экскурсии или тура этот workflow не запускает: при наполнении подставляются готовые ссылки на исходные фотографии.

Команда «перенеси текст Никарагуа влево» относится к `imageTextAlign` в Country MD, а не к улучшению фотографии: применяется `docs/workflows/master.md`, раздел 8.4. При настоящем фотопроходе сохранять уже заданное `imageTextAlign` владельца и не назначать новую сторону самостоятельно. Замена `src` не отменяет эту настройку; текст переносится общими компонентами без изменения изображения.

Рабочий цикл: строка листа `Фото` → точный слот → канонический владелец → реестр → исходник → GPT Image или переиспользование → WebP вне Git → защищенная загрузка в S3 и SHA-256 receipt по `direct-s3-upload.md` → один текстовый commit MD/JSON → обновление затронутых строк листа `Фото`.

Этот цикл не включает визуальную приемку исходника или результата, сравнение изображений, проверку страницы, desktop/mobile, скриншоты и повторную генерацию ради качества. Поле таблицы со старым поручением «проверить качество, сюжет и crop» не запускает такую работу. Замечания пользователя об изображении становятся отдельной конкретной задачей.

## 2. Точные входные данные

| Что нужно | Где брать |
|---|---|
| Рабочая очередь массового прохода | Google Sheets `1ZPptMdEcIDA3ZFMOQcFuc5jU88LJlFw9R4URCQSBmmc`, лист `Фото`: строки `T = NEEDS_REPLACEMENT` по порядку строк |
| Сущность и production-путь уже выбранной строки | `entity_id`, URL и слот строки; при необходимости точная запись `data/source-index/entries/<id>.json` |
| Закрепленные фотографии | `entry.media.images[]`: `url`, `role`, `order`, `alt`; `url` — уже подготовленный raw URL |
| Текущий слот и его значение | Только затронутый production MD в `src/content/` |
| Уже выполненные улучшения | `src/data/media/photo-enhancements.json`, массив `enhancements` |
| Состояние текущего прохода | Сохраненный ключ задачи, выбранные сущности и слоты, результаты и следующий курсор |

Нужные записи прочитать один раз. Не читать все workflow, все исходные снимки или весь сайт. Для обычной команды «следующие N» **не пересчитывать очередь по репозиторию**: она уже материализована в листе `Фото`. Точный путь и ID выбранной строки брать из самой строки и при необходимости из exact entry; не восстанавливать их из названия по догадке. `scripts/photo-queue.mjs` запускать только при явной команде сверить/пересинхронизировать реестр либо при доказанной структурной поломке таблицы.

У нового места с `media.status: provided_originals` исходник может уже лежать в `public/media/destinations/<id>/original-...` либо быть точным публичным image-src, предоставленным пользователем. Использовать именно его; отсутствие donor URL brasiltours.ru у такого материала не является блокером. Если при заполнении места файл уже был получен из вложения или точного Drive-источника и сохранен, повторно скачивать его не нужно. Это не разрешает искать другую фотографию.

Внешний источник скачивания — только закрепленный raw URL выбранного фото. `/image/cache/` запрещен как источник скачивания, новый production `src` и вариант восстановления. Если в старом слоте остался cache URL, использовать только уже записанное соответствие этого слота точному raw URL. Не преобразовывать адрес догадкой, не перебирать расширения и размеры.

Не искать изображения в интернете, Google Images, Firecrawl, на страницах `brasiltours.ru`, на Drive, в старых CSV или альтернативных raw/preload/cache адресах. Нет точного raw URL, уже сохраненного предоставленного оригинала или однозначного соответствия слоту — записать конкретный блокер этой фотографии. Подготовка недостающего mapping является отдельной задачей.

## 3. Владелец фотографии и предел пакета

Для обычного слота владельцем остается его сущность. Для самостоятельной экскурсии в программе тура:

```text
Tour itinerary / contentBlocks
→ excursionRef
→ canonical Excursion MD
→ hero.src
```

Изменяется `Excursion.hero.src`. `Itinerary.astro` автоматически использует его в связанных турах. Не создавать локальную копию изображения или текста рядом с `excursionRef`; не переписывать все связанные туры.

Если старая карточка не имеет `excursionRef`, задача улучшения не запускает миграцию Tour ↔ Excursion. Использовать однозначно закрепленный текущий слот. Неоднозначного владельца отметить как блокер, не перестраивая архитектуру.

Для массового прохода выбрать из листа `Фото` первые N **уникальных исходников** среди строк `T = NEEDS_REPLACEMENT`, двигаясь сверху вниз. N задает пользователь; при отсутствии числа обычный размер пакета — до 10. Одинаковое значение исходника в нескольких строках считается одной фотографией и обрабатывается один раз; после подключения результата обновляются все затронутые активные строки этого исходника. Строка с поручением переиспользовать готовый `enhanced` из `photo-enhancements.json` не вызывает GPT Image.

Порядок строк листа `Фото` является сохраненным курсором массового прохода. «Дальше» или «следующие N» означает продолжить с первых еще не закрытых `NEEDS_REPLACEMENT`; уже `REPLACED` и `ARCHIVED` пропускаются. Запрос об одной конкретной странице ограничивается ее строками и сам по себе не расширяет область на весь сайт.

## 4. Механическое исключение повторов

Реестр имеет существующий контракт; не заменять объект верхнего уровня массивом и не удалять чужие записи или дополнительные поля:

```json
{
  "version": 1,
  "description": "Существующее описание сохраняется",
  "enhancements": [
    {
      "source": "https://brasiltours.ru/image/<exact-original-path>.jpg",
      "enhanced": "/media/<entity>/<slot>-enhanced-YYYYMMDD.webp",
      "enhancedAt": "YYYY-MM-DD",
      "method": "gpt-image",
      "revision": 1
    }
  ]
}
```

| Условие | Действие |
|---|---|
| Текущий `src` содержит `-enhanced-` | Пропустить обработку |
| Текущий `src` совпадает с `enhanced` | Пропустить обработку |
| Точный исходник уже есть в `source` | Подставить готовый `enhanced`, если слот еще ссылается на исходник; GPT Image не вызывать |
| Маркера и записи нет | Обработать выбранный исходник один раз |

Проверять как текущий `src`, так и закрепленный raw URL этого же слота, если mapping связывает их. Качество, размер, разрешение, дата файла, EXIF и похожесть картинок не определяют статус улучшения. Лист `Фото` — каноническая **рабочая очередь и журнал слотов**, а `photo-enhancements.json` — каноническая техническая история уже выполненных улучшений. Если строка еще `NEEDS_REPLACEMENT`, но точный исходник уже есть в `photo-enhancements.json`, новую генерацию не делать: переиспользовать готовый asset и закрыть строку.

Повторное улучшение возможно только по явной команде: «улучши заново», «включая уже улучшенные», «сделай новую версию». Тогда исходник — именно указанная текущая фотография; готовится новый `-enhanced-YYYYMMDD-vN.webp`. В найденной исходной записи сохранить `source`, заменить `enhanced`, обновить `enhancedAt` и увеличить `revision`. Не плодить независимые записи одной цепочки.

## 5. Получить файл один раз

Для внешнего изображения скачать один точный raw URL из закрепленного mapping. Для текущего локального repo asset взять именно этот файл из соответствующей версии репозитория. Локальный файл не заменять похожим внешним кадром.

В рабочем состоянии пакета сохранить соответствие `sourceUrl + checksum → локальный путь`. Если файл уже получен и соответствует этому источнику и сохраненной контрольной сумме, использовать его повторно. Один исходник, встречающийся в нескольких слотах, не скачивается несколько раз. Уже подготовленный результат GPT Image также не генерировать повторно после возобновления задачи.

После получения исходника передать его в GPT Image как edit target. Не делать отдельный MIME/EXIF-анализ, не искать оригинал большей четкости и не выполнять предварительный build.

Если точное скачивание не удалось, не повторять его циклом и не искать обходной адрес. Записать URL и техническую ошибку для этой позиции; остальные уже выбранные позиции пакета можно завершить. Успехи и блокеры хранить отдельно, чтобы продолжение не теряло необработанные позиции.

## 6. Промпт GPT Image

Передавать именно полученный исходный файл. Сохраняется базовая инструкция:

> Edit the provided source image. This exact file is the edit target. Improve image quality only: increase sharpness, clarity, local detail and cleanliness while preserving the exact same photograph. Keep the same scene, the same subjects, the same perspective and the same overall framing. Minor aspect-ratio drift is acceptable if needed, but do not create a new creative crop. Do not add, remove, replace, invent, move or redesign anything. Do not change mountains, buildings, people, vegetation, sky, water, roads, objects, colors or scene structure. Do not add any border, frame, mat, padding, blank area or letterbox/pillarbox bar. No white, gray, black or transparent strips at the top, bottom, left or right. Do not extend the canvas artificially. Do not stylize. Preserve natural photographic appearance and realistic texture. This is restoration/enhancement, not redesign.

Одна выбранная фотография — один вызов с ее собственным исходником. Не оценивать результат и не делать дополнительные варианты «на всякий случай». Если инструмент вернул техническую ошибку и не создал результат, допустим один повтор того же вызова с уже полученным файлом. Повторная загрузка исходника для этого не нужна. После второй технической ошибки отметить позицию как невыполненную.

## 7. Подготовка результата

Сохранить полученный результат в WebP. Существующий кадр не перекомпоновывать, не обрезать под отдельный экран и не дополнять полями. Небольшое изменение пропорций после GPT Image допустимо; насильно возвращать прежнее соотношение сторон не требуется. Стандарт `1536×864` другого workflow к улучшению существующих фотографий не применяется.

Готовый WebP временно хранить **вне Git**, затем загрузить **напрямую в S3** через `docs/workflows/direct-s3-upload.md` под ключом `media/<тип>/<сущность>/<слот>-enhanced-YYYYMMDD-vN.webp`. Проверить публичную HTTPS-доступность и SHA-256. В content MD оставить логический путь `/media/...`; **не создавать новый `public/media/...` файл в Git**.

Сохранить существующие `alt`, `caption`, подписи и авторскую атрибуцию. Не выдумывать автора или правообладателя; `method: gpt-image` обозначает обработку, а не авторство исходной фотографии. Не менять цены, тексты, URL, связи, общий шаблон или CSS ради замены фото.

Одна узкая техническая проверка подготовленного пакета: файлы созданы и декодируются, целевые пути существуют, JSON читается, каждый новый asset имеет одну запись в реестре, изменены только предусмотренные слоты. Это проверка данных, без оценки изображения или страницы.

## 8. Один commit и одна запись результата в таблицу

Сначала локально подготовить все успешные позиции текущего пакета:

- Verified S3 receipt для WebP и запись в `src/data/media/direct-s3-uploads.json`;
- изменения media-полей канонических владельцев;
- новые или обновленные записи `photo-enhancements.json`;
- точные изменения строк листа «Фото» и курсор продолжения.

Затем выполнить один логический цикл публикации: **только текстовые blobs** (MD/JSON/реестры/receipt) → один tree → один commit → одно обновление `main`. Бинарные WebP в Git не добавлять ни отдельным, ни общим коммитом. Без подтвержденной S3-загрузки не публиковать новые ссылки. При параллельном изменении `main` согласовать только затронутые файлы и реестр, сохранив уже готовые изображения; весь процесс обработки заново не запускать.

Операции остаются в существующем репозитории. Не создавать другой репозиторий, аккаунт или обходной способ записи ради исключения системных подтверждений. Если запрос ограничен подготовкой изменений, результатом остается готовый пакет без внешних записей.

`src/data/media/photo-enhancements.json` хранит техническое происхождение готовых assets. Лист `Фото` хранит полную рабочую инвентаризацию активных слотов и является источником очереди для следующих чатов и агентов. Обычная работа читает его, а после успешной замены пишет результат обратно в те же строки:

- spreadsheet ID: `1ZPptMdEcIDA3ZFMOQcFuc5jU88LJlFw9R4URCQSBmmc`;
- лист: `Фото`, sheet ID: `1174354857`;
- существующие ключи строк: `photo_record_id`, `entity_id`, слот и порядок.

Семантика очереди: `NEEDS_REPLACEMENT` — активный слот, который еще требует действия; точное действие находится в V «Что сделать» (`GPT Image` либо переиспользование готового asset). `REPLACED` — техническая замена выполнена и строка больше не входит в очередь. `ARCHIVED` — историческая строка, всегда исключенная. Статусы `OK`, `PENDING_REVIEW`, `REJECTED` не используются как источник массовой очереди. Новую глобальную инвентаризацию слотов выполнять только отдельной задачей синхронизации, а не перед каждым пакетом.

На пакет прочитать заголовки и затронутые строки один раз; известное соответствие строки переиспользовать. Обновлять только строки фактически измененных слотов. Совпадение одного исходника в нескольких целевых строках отражается тем же готовым asset. Новую строку при необходимости создавать в существующем формате, с точным ID сущности и слота; не добавлять колонки.

| Существующая колонка | Значение после успешной замены |
|---|---|
| J — `Текущий URL / файл` | Новый `/media/...` |
| T — `Статус` | `REPLACED`, существующее допустимое значение: факт замены, не оценка качества |
| V — `Что сделать` | Удалить исполненное или отмененное поручение из этой строки; не затрагивать отдельные актуальные замечания пользователя |
| W — `GitHub path` | Для новых S3-only файлов пусто либо `S3:media/...` в служебном комментарии; не выдумывать GitHub-путь |
| X — `Production URL` | `https://img.adatours.ru/media/...` |
| Z — `Дата замены` | Дата фактической замены |
| AA — `Проверил / обновил` | Кто выполнил обновление, без утверждения о проверке качества |
| AB — `Комментарий` | Commit, факт GPT Image-обработки или переиспользования, существенный технический результат |

Сохранить идентичность строки, происхождение, `alt`, атрибуцию и историю. Колонки M–S со старыми размерами и экранными целями не запускают измерение или подгонку кадра. U «Причина замены» не заполняется придуманной оценкой. Y «Дата проверки» не заполняется: такой проверки в workflow нет. Не выставлять `OK` как будто изображение прошло приемку.

При сбое отражения в таблице сохранить точный невыполненный пакет записи и сообщить об этом. Уже выполненный commit и реестр не откатывать; повторить нужно только адресную запись таблицы, без скачивания или GPT Image.

## 9. Завершение

Не открывать публичный сайт и не ждать отдельного цикла визуального QA. Штатный автоматический deployment не превращать в дополнительную задачу обхода страниц. Сообщать только фактически полученный статус: пакет подготовлен, commit записан или публикация подтверждена штатным процессом.

Короткий отчет: сколько фото улучшено, сколько готовых использовано, какие позиции заблокированы, записан ли результат в таблицу и откуда продолжится следующая десятка. Давать ссылку на затронутую страницу без UTM. Не называть пакет полностью выполненным, если часть позиций не обработана.

## Архивные строки фотографий

`ARCHIVED` в листе «Фото» означает, что владелец переведен в архив ИЛИ прежнего слота больше нет в каноническом MD. Архивный владелец может сохранять все фото; наличие файла не возвращает слот в очередь. Такие строки сохраняют идентификатор для истории и пропускаются. Они не требуют повторного скачивания, генерации или приемки. Фактически улучшенный действующий слот имеет `REPLACED`; этот статус отражает запись GPT Image и существующий файл.

## Владельцы фотографий в разделе интересов

У самого интереса фон хранится в `Theme.hero`. Самостоятельные GPT Image-фоны интересов зарегистрированы с `method: gpt-image`; уже полученный файл не генерируется повторно после обрыва.

У страны внутри тематической географии отдельного media-слота нет. Для максимум 7 видимых стран `coverTour` распределяется по `interests.md` снизу вверх, и один Tour становится фоном только одной страны; владельцем такой фотографии остается выбранный Tour. Если уникального Tour с `hero` не осталось, `ThemeLayout` использует `Country.hero`, владельцем которого остается Country. Локальную копию в Theme не создавать. Улучшение текущего `Tour.hero` или `Country.hero` автоматически отражается во всех вычисляемых появлениях этого asset. Архивные владельцы по-прежнему исключаются до формирования массовой очереди.
