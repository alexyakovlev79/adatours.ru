# Ada Tours — S3-допуск для приглашённых редакторов через GitHub Issue

**Назначение:** Анна и другие доверенные редакторы получают собственный зашифрованный допуск для прямой загрузки фотографий в `img.adatours.ru` без постоянных ключей Yandex Cloud, без записи изображений в Git и без права изменять `main` только ради загрузки.

## Кто может получить допуск

Авторизуется **GitHub-аккаунт, подключённый в конкретном ChatGPT Work/Codex-сеансе**, а не участие в общем ChatGPT Project. Приглашение в ChatGPT само по себе не является удостоверением для GitHub Actions.

Требуются одновременно:

1. GitHub-login редактора внесён владельцем в отдельный **список S3-загрузчиков** `data/media/authorized-uploaders.json → allowedGithubLogins` (на 30.10.2026: `alexyakovlev79`, `AnnaAdaTours`). Этот список **не даёт** полномочий на изменение сайта: `data/editorial/authorized-users.json` проверяется отдельно.
2. В собственном GitHub-аккаунте редактор может создать Issue этого **публичного** репозитория. Для выпуска токена **не требуется право записи в репозиторий**. Анна уже имеет право `write`, будущим редакторам предоставлять его ради S3 не нужно.
3. Работающий GitHub-коннектор у самого редактора и среда ChatGPT Work / Codex с локальным Node.js, файлами изображений и HTTPS-доступом к S3.

Добавление нового логина в `data/media/authorized-uploaders.json` — отдельное одобренное владельцем изменение. Права автора GitHub проверяются в отдельном job **без доступа к Yandex OIDC**. Не расширять список до `*`, не принимать имена или токены из свободного текста без проверки.

## Каждый чат получает отдельный допуск

1. Прочитай `docs/workflows/direct-s3-upload.md`; подготовь окончательные файлы **вне Git**. Сначала выполни GPT Image, когда изображение требует обработки. Не выдавай загрузку исходника за улучшение GPT Image.
2. На компьютере Work из актуального `main`:
   `node scripts/media-work-session.mjs init --out /tmp/adatours-media-session-<unique>`.
   Сохрани локальные `<requestId>.request.json` и `<requestId>.private.pem`. **Приватный PEM никогда не отправлять в чат, Issue или GitHub.**
3. Под своим GitHub-аккаунтом создай **один новый Issue** в `alexyakovlev79/adatours.ru`:
   - заголовок: `[ADA-MEDIA-TOKEN] <requestId>`, точный идентификатор из JSON;
   - тело: **только полное содержимое публичного `*.request.json` как JSON**, без Markdown-обрамления и лишних полей.
   Это публичный запрос; он содержит только версию, ID, время, название бакета и открытый X25519-ключ.
4. GitHub Actions `Request encrypted S3 session for authorized GitHub editors` сначала проверяет системный GitHub-login по отдельному списку **без доступа к облачным токенам**, затем строго проверяет requestId, JSON-поля, X25519 и возраст запроса (меньше 20 минут). Только после проверки он запускает **существующий проверенный** `Issue encrypted short-lived media upload token` через `workflow_dispatch` с публичным JSON. Именно этот штатный workflow выполняет GitHub OIDC → Yandex Cloud → шифрование токена, и в его лог/артефакт попадает только зашифрованный пакет.
5. Комментарий в Issue подтверждает **только принятие запроса**, а не выдачу токена. Найди в GitHub Actions отдельный запуск `Issue encrypted short-lived media upload token` с именем **`S3 media session <requestId>`**. Проверь, что он завершён с `success`. Только после этого бери `SEALED_MEDIA_TOKEN=...` из логов или зашифрованный артефакт `encrypted-media-session-...`. Пакет можно раскрыть только локальным приватным ключом соответствующего запроса. **Срок раскрытия пакета — 10 минут с его выпуска**; при истечении начать новый сеанс (не повторять старый Issue).
6. Выполни локально `node scripts/media-work-session.mjs upload` с параметрами `--request`, `--private`, `--envelope`, `--batch`, `--receipt`, как в `direct-s3-upload.md`. При прокси может понадобиться `node --use-env-proxy`. Подтверди фактический PUT, обратный GET, SHA-256 и receipt.
7. Только затем записывай текстовые ссылки, `src/data/media/direct-s3-uploads.json` и связанные MD/JSON через PR. Файл WebP/JPG/MP4 в Git не коммитить. `S3 upload` ≠ `Pages deployed`: публичную публикацию подтверждай отдельно.

## Разграничение доступа и ограничения

- Выпуск токена выполняет **только уже действующий, успешно проверенный GitHub Actions `issue-media-upload-token.yml`**, а не учётная запись Yandex Cloud Анны. Issue-workflow не запрашивает OIDC и никогда не видит IAM-токен; он только проверяет автора и передаёт публичный запрос в доверенный issuer. Сервисный аккаунт `adatours-media-publisher` не передаёт редактору свой постоянный ключ.
- Шифрование защищает пересылку. Важно: **10 минут — срок зашифрованного пакета, а не гарантированный срок действия самого IAM-токена Yandex Cloud**. Права сервисного аккаунта должны быть строго ограничены необходимыми операциями с бакетом `img.adatours.ru`; срок IAM-токена устанавливает Yandex Cloud.
- Не использовать `issue_comment`, `pull_request_target` или произвольные команды из текста Issue для выдачи токенов. Issue-маршрут включается только по `issues.opened` и коду зафиксированного коммита `main`. Первый job проверяет GitHub-автора без облачных полномочий, второй получает только `actions: write` и запускает штатный issuer с уже существующими проверками X25519. **Ни один job нового issue-маршрута не имеет `id-token: write`.** Повторный запуск ищет существующий запрос по точному requestId, чтобы не дублировать выдачу.
- Неуспех штатного issuer, ответ 401, отсутствие артефакта, просрочка или отсутствие receipt означают, что загрузка **не подтверждена**. Не заменяй ссылки на сайте фиктивным путём.
- После изменения прав GitHub или списка редакторов проверь доступ тестовым Issue от **самого нового аккаунта**. Успех тестового Issue владельца доказывает работоспособность механизма, но не проверяет авторизацию другого автора.
