# Ada Tours — резерв нового места и заполнение материалами

Адреса объектов и правила английских slug: `docs/workflows/urls.md`. Для существующего объекта использовать закреплённые `slug`, `url` и точный `contentPath`; русское название не транслитерировать заново.

Версия: 1.2 · 2026-10-05 · Репозиторий: `alexyakovlev79/adatours.ru`, ветка `main`.

## 1. Выбрать нужный режим

| Ситуация | Действие |
|---|---|
| Место уже имеет точную запись источников с подготовленным текстом/фото | Обычное добавление по `docs/workflows/destinations.md`; повторное резервирование не нужно |
| В конкретном туре/экскурсии найдено подтвержденное место без готового материала | Сопоставить с каталогом; при необходимости создать только резерв и связь, раздел 2 |
| Пользователь предоставил описание и фото для выбранного резервного места | Заполнить этот же ID по разделу 4; сохранить будущий URL |
| Пользователь прямо просит добавить новое место и сразу дает его описание/фото | Выполнить то же сопоставление; при уникальности зарезервировать ID с происхождением `user_request` и сразу заполнить его в одном проходе |

Резерв не создает Destination MD, публичный текст, фотографии или индексируемую пустую страницу. Упоминание места и описание экскурсии служат доказательством связи, но не становятся автоматически самостоятельной статьей о месте. До поступления материала резерв не объявляется опубликованным.

## 2. Сначала сопоставление, затем резерв

Единственный канонический каталог — `src/data/catalog/destinations.json`. Его `id`, `name`, `slug`, `countryId`, `countrySlug`, `url` и `aliases` определяют место. Очередь `src/data/catalog/destination-reservations.json` хранит его статус, происхождение и материалы по тому же ID; вторую независимую систему имен/URL не создавать. `data/source-index/reserved-destinations.json` — указатель на эти файлы, не список для отдельного редактирования.

Для нового названия из **текущего** тура/экскурсии либо прямого запроса пользователя:

1. Взять подтвержденные страну и название из уже выбранного текста; не открывать общий поиск мест или соседние туры. Если действительно новому месту ещё не закреплено принятое английское написание, подтвердить только это написание для точного объекта и записать его по `docs/workflows/urls.md`.
2. В пределах этой страны сопоставить название и уже известные aliases с каталогом. Сопоставление нормализует регистр, диакритику и разделители; разные страны не объединяются. Произвольные синонимы автоматически не распознаются.
3. Если место однозначно существует, использовать его stable ID, даже без MD. Не создавать новый резерв или ID из-за другого написания. Для уже имеющегося резерва допускается дополнить только подтвержденное `discoveredIn`, без второй записи.
4. Если несколько кандидатов, коллизия ID/URL или неясная география, сообщить конкретное название, страну и кандидатов. Не добавлять суффикс к ID, не выбирать случайное совпадение и не создавать вероятный дубль. Сохранить выполненную работу с выбранным туром, не начинать общий аудит.
5. Только для однозначного действительно нового места добавить каноническую запись и резерв, затем записать этот ID в `Tour.destinations`, основной `Excursion.destination` или дополнительные `Excursion.relatedDestinations` по фактической роли места. `destinationName` экскурсии — каноническое имя основного места. Основной `destination` задает URL; дополнительные посещаемые места дают обратные связи без переезда URL. Для прямого запроса без родительского тура/экскурсии такая связь не требуется.

Намеренно пустой `destinationIds` готовой экскурсии не является новым обнаружением места и не запускает этот процесс. Две стороны Игуасу сохраняют разные ID и страны.

### Инструмент и JSON-контракт

Заявка соответствует `data/schemas/destination-reservation-request.schema.json`:

- `countryId`, `name` — подтвержденные страна и публичное русское имя;
- `slug?` либо `englishName?` — для действительно нового места обязательно одно из полей: явный английский lowercase ASCII kebab-case slug либо принятое имя латиницей с допустимыми акцентами. Существующее совпадение по имени/aliases/ID работает без них и сохраняет прежнюю identity;
- `aliases?` — только известные варианты написания;
- `destinationId?` — уже установленный точный ID, если он известен;
- `discoveredIn` — для обнаружения в программе `{entityType: "tour" | "excursion", entityId, sourceUrl?, evidence}`: целевая сущность, точный источник при наличии и краткое фактическое основание связи; для прямого запроса — `{entityType: "user_request", sourceUrl?, evidence}` без выдуманного ID тура/экскурсии.

Не выдумывать `sourceUrl`, название продукта или цитату для заполнения полей. Допустим массив заявок как одна транзакция. CLI использует ту же чистую функцию `reserveDestinations()` из `src/lib/destination-reservations.mjs`:

```bash
npm run reserve:destination -- --input request.json --write
```

Без `--write` получается предварительный результат без записи; отдельный такой проход не обязателен. Возможные результаты — `existing`, `reserved`, `ambiguous`, `invalid`; при неоднозначности/ошибке пакет не записывается. Это адресное сопоставление в JSON без сети, а не дополнительная сборка сайта.

Если чат работает только через GitHub tools, подготовить те же изменения одним JSON patch: каноническая запись в `src/data/catalog/destinations.json`, запись по ID в `src/data/catalog/destination-reservations.json`, связь в целевом Tour/Excursion. Имена и aliases сопоставляются до добавления. Для нового места передать явный английский `request.slug` либо латинское `request.englishName` по `docs/workflows/urls.md`. `destinationSlug()` нормализует только `englishName`: нижний регистр, удаление диакритики, один `-` вместо разделителей; кириллица и другие нелатинские алфавиты отвергаются. Русское `request.name` не является источником slug. `englishName` добавляется к известным aliases; при наличии обоих полей явный `slug` задаёт адрес. Сначала всегда выполняется сопоставление существующего места, и для его переиспользования эти поля не нужны.

Для нового места ID имеет вид `destination_<countryId без country_>_<slug с дефисами, замененными на _>`; URL — `/<countrySlug>/place/<slug>/`. Существующие ID, закреплённые после миграции slug/URL и точные `contentPath` не пересчитываются. Исключение однократной явно заказанной миграции описано в `docs/workflows/urls.md`; прежние публичные пути сохраняются как redirects. При коллизии требуется адресное разрешение соответствия, а не произвольный суффикс. Проверку дубликатов и согласованности каталога выполняет существующий validator в штатном build.

Новая запись очереди: `{id, status: "needs_content", discoveredIn: [...]}`. Допустимы `materials: {textUrl?, repositoryPath?, imageUrls?: []}` и `notes` для реально полученных материалов/уточнений. Полная source entry и Destination MD на этапе резерва не создаются. Каталог, резерв и связь входят в один commit текущей задачи тура/экскурсии.

Если прямой запрос `user_request` уже содержит самостоятельный текст и фото, перейти к заполнению сразу. Не требовать выдуманного родительского тура, отдельной публикации резерва или промежуточного ожидания Анны. Сопоставление и защита от дублей остаются теми же; каталог, материал и полноценный MD публикуются вместе под одним ID.

После публикации задачи, добавившей резерв, отразить только затронутые ID одним пакетом. Новая строка получает `Нужен контент`, F остается пустой. Существующую строку искать по H: при повторной встрече дополняется D, а не создается дубль. Не сбрасывать внесенные материалы F или статус `Готово к добавлению` при очередном обнаружении места. Имя, страна и URL берутся из каталога, не из свободного комментария. В G используется полный текущий публичный URL; логический путь остается `/<countrySlug>/place/<slug>/`.

`Готово к добавлению` означает, что предоставлены самостоятельное описание и минимум одно фото; оно не публикует страницу автоматически. Текст/фото прямо в чате допустимы: непустая F не является обязательным условием заполнения. Заполнение выполняется по выбранному запросу. В JSON очереди статус остается `needs_content` до создания полноценного опубликованного MD; промежуточный рабочий статус таблицы не подменяет этот контракт. `Добавлено` ставится после успешной публикации заполненного места.

`npm run reserve:destination -- --export-queue` дает проекцию очереди без записи в Google Sheets и без получения материалов. Это служебная возможность; поштучная задача не требует общего экспорта или повторной сверки всей таблицы.

## 4. Заполнить выбранный резерв предоставленными материалами

Начать с точного ID, канонической записи и выбранной строки очереди. Нужны **содержательный самостоятельный текст о месте и минимум одна предоставленная фотография**. Если чего-то не хватает, назвать конкретный недостающий материал и сохранить резерв. Не публиковать пустой MD и не дописывать описание места из текста экскурсии, интернета или догадки.

Прямое описание и фотографии из сообщения пользователя — допустимые материалы; обязательного промежуточного сохранения в Google Drive нет.

| Предоставленный материал | Как закрепить |
|---|---|
| Текст прямо в чате или прикрепленном файле | Сохранить исходный материал в `data/source-index/materials/<destinationId>.md` |
| Точный документ Drive | Использовать данный file ID/URL; не искать похожие документы и не создавать обязательную копию |
| Готовый публичный URL изображения | Использовать предоставленный browser image-src напрямую |
| Прикрепленный файл фотографии | Сохранить исходные байты в `public/media/destinations/<destinationId>/original-01.<ext>` и следующие файлы по порядку |
| Точный приватный файл фотографии Drive | Одно первое получение предоставленного файла для того же размещения; имеющуюся локальную копию повторно не скачивать |

Viewer-ссылка Drive не является image-src. Расширение файла берется из реально предоставленного формата, без придумывания URL или конвертации ради стандарта. В MD локальный путь начинается с `/media/`, без `public`. Исходные фотографии сохраняются без GPT Image и визуальной приемки; последующее улучшение — отдельный Work-проход с уже сохраненным исходником.

Подготовить `data/source-index/entries/<destinationId>.json`, используя закрепленные ID/slug/URL/страну и полученные материалы:

- `text.selected` и `text.original` обязательны. У `selected.kind` — `provided_materials`; оба указателя могут ссылаться на один предоставленный материал, без объявления его снимком старого сайта;
- каждый указатель содержит либо `repositoryPath: data/source-index/materials/<этот destinationId>.md`, либо согласованные точные `driveId` и URL файла/документа Drive — не оба варианта одновременно. `name` и `mimeType` непустые; локальный текст — непустой UTF-8 Markdown с `mimeType: text/markdown`. Ссылка папки или URL другого Drive ID не заменяет ссылку файла;
- `sourceUrl: null` в JSON, если самостоятельного донорского URL нет; в production MD необязательное поле `sourceUrl` опустить;
- `media.status: provided_originals`, `media.provenance.kind: user_provided`; `media.images` содержит конкретные public image-src либо `/media/...`, минимум одну фотографию `hero`, остальные предусмотренные фото `gallery`, порядок и предоставленные подписи. Сохраненный локальный файл содержит исходные непустые байты;
- тип места и факты берутся из самого предоставленного описания; не подставлять `city` или дополнительные сведения по умолчанию.

По этой готовой записи создать один полноценный Destination MD согласно `docs/workflows/destinations.md`, сохранив ID, slug, URL и уже заданный `imageTextAlign`, если поле существовало. В `sourceSnapshot` использовать точный URL предоставленного документа либо сохраненный `repositoryPath`; новый сетевой адрес не выдумывать. Связанные туры/экскурсии не перечитывать: существующие ссылки на stable ID активируются сами.

Полученные указатели `textUrl` либо `repositoryPath` и `imageUrls` сохранить в `materials` выбранной записи очереди, не создавая второй системы имен или источников.

В том же commit добавить запись источников в `index.json` и `catalogs/destinations.json`; локально это делает `node scripts/sync-source-catalogs.mjs` из готовых entries. Без shell добавить только новую компактную запись в эти два файла по формату `data/source-index/README.md`. Обновить статус выбранного резерва на `added` вместе с полноценным MD; локально доступен `npm run reserve:destination -- --sync-status --write`. Статус `added` без опубликованного MD недопустим.

## 5. Один результат задачи

Резервирование в процессе тура/экскурсии входит в его общий commit и CI. Заполнение места включает материал, исходные приложенные фото при наличии, source entry/каталоги, MD и статус резерва **одним commit**. Сборка штатного Actions проверяет согласованность данных без поиска источников; отдельную локальную сборку, визуальную приемку или общий аудит не добавлять.

После успешного deploy обновить только строку очереди по H на `Добавлено` и зарегистрировать фактическую публикацию в реестре `Страницы` по правилам Destination. Существующую дату первой публикации и колонку G «Принята» основного реестра сохранить. Данные источников и очереди не требуют второго служебного commit после deploy.

В отчете различать результаты: «место зарезервировано, материалы ожидаются» и «страница места опубликована». При сбое продолжить конкретный ID и стадию; не повторять уже выполненные сопоставление, получение файлов и подготовку текста.

Неоднозначные случаи разовой подготовки сохранены в `data/source-index/preparation-notes/destinations-deferred-2026-10-02.json` только для отдельно заказанного административного разбора. Они не получают предполагаемых ID/резервов; обычный добавляющий чат этот файл не читает.

## Интересы после получения самостоятельного материала

Пустой резерв не участвует в визуальных историях, каталоге мест или счетчиках опубликованных мест. Когда предоставлены самостоятельные описание и фото, определить собственные `themes` нового места по этим материалам в рамках закрытого справочника 13 интересов и сохранить в MD, exact entry и компактном каталоге. Метки обнаружившего место тура/экскурсии не наследуются. При недостаточных основаниях допустим пустой массив.

После публикации тематические истории и счетчики активируются автоматически. Форма на странице готового места и его каталогах появляется через общий `BaseLayout`; новые локальные формы и отдельные счетчики не создавать.
