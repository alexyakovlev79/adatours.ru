# Ada Tours EN: массовое сопоставление Word ↔ Tour

Версия: 1.3 · 29.10.2026.
Репозиторий: `alexyakovlev79/adatours.ru`.
Код: `feat/english-site-foundation`. CAS-очередь: `i18n/matching-staging`.
Только сопоставление. Перевод, Tour MD, общие цены и `main` работник не меняет.

## Цикл одного чата

По решению Алексея один чат автоматически выполняет до **10 партий по 6 разных
туров**, максимум **60 уникальных Tour за весь чат**, без команды «дальше».
Каждый подтверждённый `complete` немедленно открывает следующий `claim`;
шестой результат — промежуточный отчёт, затем начинается следующая партия.
Прежний массовый лимит 6 на чат отменён. Пилотный лимит 3 сохранён.

Партия — единица отчёта, не предварительная бронь шести будущих заданий.
Одновременно у работника только **один текущий Tour** с резервом **60 минут**.
Через каждые **20 минут** незаконченной работы выполнить `renew` и сохранить
`checkpoint`. После сохранения результата резерв снят; следующий Tour получает
собственные 60 минут. Прежние действующие резервы не сокращаются задним числом.

`ownerId` и `token` постоянны для всего чата, включая все десять партий и
возобновление. `ownerAssignments.jobIds/completedJobIds` сохраняют квоту и прогресс
в CAS-index. Не создавать нового owner ради обхода лимита.
`workerProgress` в ответах содержит assignedCount, completedCount,
completedBatches, batchSize=6, maxBatches=10, limit=60.

## Команда для нового Work-чата

> Рой ADA: массовое сопоставление EN. Репозиторий alexyakovlev79/adatours.ru.
> Прочитай актуальные docs/workflows/english-site.md и
> docs/plans/english-site/14-matching-bulk.md из feat/english-site-foundation.
> Работай через CAS-диспетчер i18n/matching-staging. Сопоставляй назначенные
> туры с полными английскими Word 2027, затем 2026. Сохраняй источники,
> SHA-256, соответствия дней и новые тарифы Word 2027 как priceAmendments.
> После каждого saved/already_saved сразу бери следующий Tour. После партии
> из 6 автоматически начинай следующую: до 10 партий, максимум 60 разных
> туров за чат. Резерв текущего тура 60 минут, renew и checkpoint каждые
> 20 минут незаконченной работы. Сохраняй owner/token и submissionId при
> повторах. Не повторяй готовое, не переводи контент, не меняй main.
> При исчерпании квоты, отсутствии доступной работы или неустранимом сбое
> сохрани прогресс, покажи фактический остаток и заверши чат.

В уже начатом чате пользователь может дать эту же команду с «Продолжай».
Сначала сохранить текущий результат/lease, затем перезагрузить обе версии кода
из одного нового SHA; сохранить прежние owner/token. Ранее выполненные шесть
туров входят в общий лимит 60 и остаются завершёнными.

## Подготовка и состояние

1. Прочитать один актуальный HEAD `feat/english-site-foundation`; загрузить
   `scripts/i18n/matching-core.mjs` и `matching-remote.mjs` по этому одному SHA.
   Использовать Code Mode пример из `12-matching-pilot.md`, но режим должен быть
   `matchingEnabled=true`, `pilotOnly=false`, `translationEnabled=false`.
   Имена connector tools адаптировать к реально доступному namespace.
2. Сначала `status`, затем отдельный `claim`. Передавать owner/token в status
   для собственной сводки. Не редактировать index/state вручную.
3. `claim` выдаёт immutable descriptor и кандидатов 2027/2026.
   Они — предложения. Расширять поиск через `programme-sources.json` и
   допустимые отложенные программы. Filename score не доказывает соответствие.
4. Сравнивать маршрут, дни, длительность, страны и существенные услуги.
   Получать полный DOCX: readable preview может терять таблицы цен.
   Записывать fileId, modifiedTime, реальный SHA-256 байтов и XML locators.
5. Для уверенного Word 2027 сохранить все соответствующие строки тарифов в
   `priceAmendments`: amount, currency, priceBasis, sourceLocator, SGL/DBL/TPL,
   размещение, даты/сезон, минимум группы и доплаты. Без ручного review отличий
   от старой RU-версии. Сам работник цены сайта не применяет.
6. Для `selected_2026` записать отсутствие подходящего 2027; цены 2026 не
   переносить в текущие коммерческие поля.
7. Для `not_found_both` нужны checkedYears=[2027,2026],
   quarantinedCandidatesChecked=true и конкретные доказательства по обоим годам,
   не пустые списки manifest.
8. `complete` принимать только по `saved`/`already_saved`; сохранять
   неизменный submissionId и содержимое при повторе. Затем сразу следующий claim.
   Готовый результат не пересчитывать после потерянного ответа.
9. При промежуточном сбое сначала checkpoint/resume текущего задания.
   При возобновлении claim возвращает checkpoint receipt; читать сохранённый
   checkpoint по его blob SHA, проверяя jobId/sourceFingerprint.

## Конфликты, лимиты API и остановка

CAS обновляет только точные state/index/result, с expected_sha и fencing.
Диспетчер делает до 12 попыток при конфликте с нарастающей случайной паузой;
снимок и текущее время обновляются на каждой попытке. Blob результата
переиспользуется внутри повторов. Потерянный ответ проверяется тем же submit.

429/secondary rate limit возвращает `rate_limited` и `retryAfterMs`:
не вызывать claim/complete/status до истечения этой паузы. Минимум 60 секунд,
более длинный Retry-After провайдера сохраняется. После паузы повторить ТОТ ЖЕ
вызов с теми же идентификаторами; не более трёх таких отложенных повторов.
Если доступ не восстановился, сохранить имеющийся локальный/удалённый прогресс
и остановиться с блокером, без горячего цикла. 403 отказа в правах не считать
успехом или завершённым туром. Любые повторные действия остаются ограниченными.

`worker_quota_reached` после 60 разных Tour — штатное завершение.
`empty_or_busy` с чужими leases означает busy, а не завершение всей очереди.
При stale_source/blocked_external фиксировать точную причину через fail;
не выдавать её за готовый результат. При неисправимом сбое завершить чат после
сохранения прогресса, а не обещать бесконечную работу «пока не зависнет».

После зависания резерв освобождается по истечении 60 минут от claim/renew:
другой работающий чат через claim/reap вернёт Tour в очередь и продолжит по
checkpoint с новым generation. Пять неуспешных попыток по-прежнему дают
failed_final. Если все Work-чаты закрыты, новый сам не запускается; cron reaper
ещё не активирован в default main. Нужен новый запуск работника.

## Параллелизм и проверка

Модель CAS проверяется на 20 одновременных claim и complete, включая повтор
submit, и на полном цикле 60 Tour одного owner. Это проверка протокола,
не измерение доступного остатка живых GitHub/Drive квот. Первую реальную
расширенную волну запускать до восьми чатов; при 20 сначала проверить фактические
квоты с учётом остальных роёв. Если пользователь явно выбирает 20, сохраняются
обязательные паузы провайдера и остановка по rate_limited, без обхода лимитов.

Бюджет без конфликтов: claim 8 GitHub connector calls, complete 11, всего
19 на Tour без чтения Word/прочих материалов; запись — 7 Git-data mutations.
60 Tour одного чата — около 1140 calls; 329 оставшихся — около 6251 calls
до исследования источников и повторов. Это расчёт, не обещание прохождения
в один час. Фактические лимиты общие с другими задачами аккаунта.

`ready` означает только завершённое сопоставление. Переводчики получат
отдельную очередь с полными stable block maps после matching.
